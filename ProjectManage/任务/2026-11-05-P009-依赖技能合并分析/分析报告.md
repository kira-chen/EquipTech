# P009 分析报告：两个依赖技能能否合并进使用它们的技能

- 编写：SK 设备员skill开发会话，2026-11-05
- 范围：`work-permit-precheck` 与 `permit-precheck-bridge`、`overhaul-safety-check` 与 `overhaul-process-check-bridge`
- 依据：
  - 两个依赖技能的源码由用户本机提供，与 P006 打包时用的是同一份，下文称“依赖技能”。
  - 两个 bridge 技能在 `炼厂车间设备员/设备员skill/02-缺陷报修与检修管理/`。
  - 文中行号均指这些文件。

## 一、结论

**推荐方案 A：把两个依赖技能分别合并进对应的 bridge 技能。** 合并后设备员技能仍是 50 个，不再有“依赖技能”这一类。两对技能都可以合并，没有技术障碍。

理由：

1. **职责能接成一条流程。** 依赖技能负责读票或读方案、抽取字段、按规则判定；bridge 负责补车间侧信息，并把结果转达成车间自查报告。合并后是一条完整流程，职责仍然清楚。
2. **使用对象一致。** 依赖技能面向“作业负责人、属地安全员、审批人”，bridge 面向车间设备员。D002 把技能对象定为中石化体系车间设备员。方案 B 要么改写依赖技能的使用对象，要么让设备员技能包里出现两个不面向设备员的技能。
3. **不抢触发。** 两对技能的触发词高度重合，例如“作业票预检”和“用火票预检”、“检修方案安全措施核查”和“方案安全措施够不够”。合并后每类请求只对应一个技能；方案 B 会让平台在两个技能之间随机选择。
4. **去掉一整类问题。** 依赖查找、`SKILL_PACK_ROOT`、平台旧副本、并排安装，以及 P006、P008 为依赖所做的打包处理，合并后都不再需要。
5. **中石化口径只需在一处统一。** 依赖技能大量使用国标用词：作业票预检“动火”出现 292 次，检修方案核查“动火”235 次、“大修/中修”39 次。中石化口径要求写“用火”“装置大检修 / 日常维修”。合并后由一个技能统一输出口径；方案 B 要在两个技能里各改一遍。

主要代价：

- **合并工作量更大。** 两个 SKILL.md 和两套自测要重写成一份。
- **自测断言要先删后补。** bridge 里专测“依赖查找”的断言（各 31 条）随功能一起删除，再由依赖技能的自测补回，合计不会减少（见四、4）。

## 二、两个方案对比

| MCPServer | e2e 用例改为调用合并后的脚本；删掉“依赖缺失”用例；helpers.js 的默认 SKILL_PACK_ROOT（T06）可以去掉 | e2e 只需把依赖路径改到仓库内；helpers.js 同样可去掉 |
| 平台旧副本 | 合并后的技能不再查找依赖，旧副本不会被误用；只需通知卸载 | 同名旧副本可能与新版并存或被平台优先加载，要逐个平台确认覆盖 |
| 工作量 | 较大，约 2 个工作单元（一对一个） | 中等，约 1.5 个工作单元，主要是规范改造，外加 4 个技能的触发词调整 |
| 主要风险 | SKILL.md 变长；改技能名会牵动面很广（见六、2） | 触发冲突长期存在；依赖查找问题仍在 |

## 四、逐题回答

### 1. 职责与重叠

- **两边的分工与衔接点：**
  - 依赖技能做“读票或读方案、抽取、判定”。
  - bridge 做“补车间侧信息、逐条转达、按车间口径成文”。
  - 两边唯一的衔接点是 `result.json`：bridge 的 merge-report.js 读它，逐条深拷贝 findings、重新计数，不改判定（`permit-precheck-bridge/SKILL.md:14`、`:57`）。
- **重叠在入口：** 两边都从“用户给一张票或一份方案”开始，触发词也重合（见第 2 题）。规则逻辑没有重复，bridge 明确不实现规则引擎（`SKILL.md:14`）。
- **合并后职责仍然清楚，前提是保留两个脚本：**
  - `precheck.js` / `check.js` 只判定；
  - `merge-report.js` 只转达，并且照旧不改写判定。
  - SKILL.md 写成一条流程：读取 → 抽取并复述确认 → 判定 → 补车间侧信息（可选）→ 合并成报告。

### 2. 触发与上架

- **触发词重合：**
  - 作业票：work-permit-precheck 的“帮我检查这张作业票 / 预审作业票 / 作业票预检 / 作业票有没有漏项”，与 bridge 的“这张作业票帮我看一下 / 票填得对不对 / 用火票预检 / 作业许可票自查”基本是同一类请求。
  - 检修方案：overhaul-safety-check 的“检修方案审查 / 大修方案安全措施齐不齐 / 方案里还缺哪些安全措施”，与 bridge 的“方案安全措施够不够 / 有没有漏的 / 大检修方案安全措施核查”也重合。
- **合并后的 description：** 以 bridge 现有 description 为底，删掉“对接已有 xxx 技能”“只做转达”，改成“读取作业票并按 GB 30871-2022 整理的规则逐项预检，再按车间自查口径输出报告”。触发词取两边的并集。原有的排除说明保留（检修方案用另一技能、设备交出用 equipment-handover-check 等）。
- **与其他技能是否抢触发：** 作业票预检与 cross-operation-conflict（交叉作业）、equipment-handover-check（设备交出）的边界，bridge 的 description 里已经写明（`permit-precheck-bridge/SKILL.md:3`）；检修方案核查与 repair-plan-assistant（方案编制）的边界也已写明（`overhaul-process-check-bridge/SKILL.md:3`）。合并不引入新冲突。
- **上架数量：** 方案 A 仍是 50 个，清单不需要“依赖技能”一节，上架人员不必记“须同时上传”。方案 B 是 52 个。
- **只想做纯预检或纯核查：** 方案 A 下不填车间侧信息即可，`--notes` 是可选参数；SKILL.md 里写明“没有车间侧信息时跳过第 4 步，报告第五节写‘未提供’”。

### 3. 代码与数据

- **规则引擎与资料：** 方案 A 下整体搬入 bridge，规则逻辑一行不改。
  - `scripts/`：precheck.js 或 check.js、docx2text.js；
  - `scripts/lib/`：docx-lite.js；
  - `references/`：rules.json 与 rules-gb30871.md（或 checklist.json 与 checklist-ref.md）、extraction-guide.md、permit-schema.md（或 plan-schema.md）；
  - `assets/templates/`：permit.json 或 plan.json、report-template.md。
  - bridge 现有的 references（bridge-rules.md、input-spec.md、intake-questions.md、checklist.md、sample-output.md）保留。两份 sample-output.md 合成一份，展示合并后的报告。
- **JSON 输出都保留：**
  - **`result.json`：** 规则引擎的原始结果，merge-report 读它。依赖技能的 SKILL.md 写了它“可回填到 OA/审批系统”，不能丢。
  - **`bridge.json`：** 合并报告的结构化结果，MCPServer 的 `test/e2e-knowledge.js:511` 读它。
  - 50 个技能里没有其他读取方（检索 `bridge.json`、`result.json`，仓库内只有两个 bridge 自己）。
- **共享库：**
  - **docx-lite.js 不冲突：** 两个依赖技能的副本与设备员技能包内 9 份副本 md5 完全相同，都是 `9ecdf3ce…`，直接按共享库管理。
  - **common.js 不必强改：** bridge 已有 common.js；规则引擎可以继续不依赖它，强行改用会动判定代码，风险大于收益。
- **docx2text 的出错约定不一致：**
  - 依赖技能的 docx2text.js 出错时在 stderr 打文本；设备员规范要求末行输出 JSON。
  - completion-acceptance 里已有一份按规范改过的副本（`completion-acceptance/scripts/docx2text.js:25` 注明了差异）。
  - 合并时建议改用这一份，并核对两份的输出格式是否一致（`[x]`、`‹›`、文本框标记）。

### 4. 自测与样例

- **依赖技能现有的自测：**
  - 两份 selftest 用 `assert` 分组，作业票 24 组、检修方案 26 组，一组里有多个断言。
  - 运行时要读 `examples/`，没有就直接退出（作业票 selftest.js:16）。
  - 另有 run-examples.js 做端到端回归：docx → 文本 → 判定 → 与期望报告比对，作业票 9 份、检修方案 2 份。
- **方案 A 的合并方式：**
  - 并入 bridge 的 selftest.js，按《自测用例分级规范》分节定级。
    - 依赖技能的每个 `assert` 拆成一条 `ok`/`eq`，数量会多于 24、26。
    - run-examples 的 11 份端到端回归写成 selftest 的节，主链路定 A，其余定 B。之后 run-examples.js 可以删掉。
  - bridge 第 1~5 节是依赖探测与 `SKILL_PACK_ROOT`，各 31 条断言，测的是被删掉的 check-dependency.js，随功能一起删除。
    - 删除清单逐条列在回执里。
    - 节号：作业票 `selftest.js:59-152`，检修方案 `selftest.js:62-151`。
  - 原来依赖不在就跳过的 17 条断言（检修方案 6、15 节）改为总会运行。
  - **净断言数估算：** 作业票 133 − 31 + 依赖断言（≥24）+ 9 份回归，检修方案 180 − 31 + 依赖断言（≥26）+ 2 份回归。两者都不少于现在的数目。
  - **请 PM 确认验收口径：** “断言数不减”按合并后的总数计；删除的只限依赖探测断言。
- **样例迁移：**
  - 依赖技能的 examples/（json、docx、docx2text.txt、expected-report.md）迁到 `演示case/02-缺陷报修与检修管理/<bridge>/`，与现有 7 个文件放在一起，前缀区分来源。
  - 演示附件里的 docx 与 examples 重复，只保留一份。
  - selftest 按现有规则找演示case，在仓库外回落到包内 `examples/`。
  - make-sample-docx.js 的功能并进 bridge 的 make-sample.js；规范只认 make-sample.js 这个名字（目录与文件管理规范第 24 行）。
