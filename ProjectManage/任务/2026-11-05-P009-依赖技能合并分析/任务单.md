## 一、目标

给出明确结论：`work-permit-precheck` 能否合并进 `permit-precheck-bridge`，`overhaul-safety-check` 能否合并进 `overhaul-process-check-bridge`；能合并的给出合并方案，不能或不宜合并的给出理由，并给出“作为独立技能放进设备员skill”的方案作为对照。

**本任务只做分析，不改代码。**

## 二、要回答的问题

1. **职责与重叠：** 两对技能各自做什么，重叠在哪里，合并后一个技能是否仍然职责清楚。bridge 是“车间侧入口 + 合并报告”，依赖技能是“规则引擎 + docx2text”。
2. **触发与上架：** 合并后 SKILL.md 的 description 和触发词怎么写；会不会和其他技能抢触发；上架数量从 52 变成 50 是否有影响；用户只想做纯预检或纯核查时还能不能用。
3. **代码与数据：**
   - 规则引擎（作业票 130 条、检修方案 70 条）、references、模板怎么并入；
   - 两边的 JSON 输出（`result.json`、`bridge.json`）是否保留，下游有没有读取方；
   - 共享库是否冲突：目前两个依赖技能只用 `docx-lite.js`，与设备员版本相同；合并后是否需要 `common.js`。
4. **自测与样例：** 两边的 selftest（依赖技能 24、26 条，bridge 133、180 条）怎么合并、分级；依赖技能的 examples 怎么迁到演示case；断言数不能减少。
5. **规范符合度：** 依赖技能进入仓库后，是否满足目录与文件管理规范、技能实现规范、中石化口径对照（如“【炼化】”命名、上架信息与样例问题的格式、样例是否虚构、有无真实企业信息）；需要改哪些。
6. **外部影响：**
   - MCP 端到端用例和 MCP 工具：作业票 docx 样例生成脚本被 MCPServer 复制过；
   - 打包工具：P006、P008 的依赖处理怎么调整或移除；
   - 平台上已安装的旧副本怎么处理。
7. **工作量与风险：** 合并与独立放入两个方案分别要改哪些文件、大致工作量、主要风险。

## 三、输入

- 两个依赖技能：源码由用户本机提供，打包时用的同一份（P006 中 `SKILL_PACK_ROOT` 指向的位置）。
- 两个 bridge 技能：`炼厂车间设备员/设备员skill/02-缺陷报修与检修管理/` 下。
- 规范：目录与文件管理规范、技能实现规范、中石化口径对照、自测用例分级规范。
