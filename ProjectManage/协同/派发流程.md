# 派发流程

所有派发给责任方的任务按本流程执行，并在 [派发台账](../派发台账.md) 登记。责任方见 [责任方](责任方.md)。

## 状态

| 状态 | 含义 | 由谁改 |
|---|---|---|
| 待派发 | 任务单已写好，等用户确认或等前置任务 | PM |
| 已派发 | 已通知责任方 | PM |
| 进行中 | 责任方已确认接收并开始 | 责任方或 PM |
| 待验收 | 责任方已填回执 | 责任方或 PM |
| 已完成 | PM 验收通过 | PM |
| 退回 | 验收不通过，写明原因后重新派发 | PM |
| 取消 | 不再需要做，写明原因 | PM |

## 步骤

1. **拆解：** PM 在 `任务/YYYY-MM-DD-事项名/` 下写 `任务单.md`（模板见下），台账加一行，状态为“待派发”。需要用户拍板的事项（范围、优先级、影响平台配置的改动）先问用户。
2. **派发：** PM 通知责任方，台账改为“已派发”。
   - AI 会话：发会话消息，写明任务单路径和一句话目标。
   - 付晨：按用户确认的渠道。
3. **执行：** 责任方按任务单执行。遇到需要决策的问题回报 PM：PM 能定的直接定，写进决策记录；定不了的转给用户。
4. **回执：** 责任方在任务单的“执行回执”一节写明改了什么、提交号（或部署版本）、验证结果和遗留问题，台账改为“待验收”，并通知 PM。
5. **验收：** PM 按任务单的验收标准逐条复核（跑自测或测试、看改动、抽查产出），写“验收记录”。
   - 通过：台账改为“已完成”。需要合并的，PM 按协同规范合并到 `main` 并推送（需用户同意）。
   - 不通过：台账改为“退回”，写明原因和要补的内容，重新派发。
6. **归档：** 推进时间线加一行；遗留问题记入待办与风险。

## 任务单模板

```markdown
# <任务名>

| 项 | 内容 |
|---|---|
| 编号 | P0xx（与派发台账一致） |
| 责任方 | SK / MCP / FC |
| 派发日期 | YYYY-MM-DD |
| 期望完成 | YYYY-MM-DD 或“无” |
| 依据 | 用户要求 / 待办编号 / 决策编号 / 上游任务 |

## 一、目标
做完后应达到的状态，一两句话。

## 二、范围
- 要做：……
- 不做：……（避免范围扩大）

## 三、输入
相关文件、数据、上游产出的路径。

## 四、交付物
改哪些文件、产出什么、是否需要提交。

## 五、验收标准
逐条可核对，例如：某技能 selftest 全过且断言数不减；某命令输出与预期一致。

## 六、约束
需遵守的规范、禁止事项、需先确认的事项。

## 七、执行回执（责任方填写）
- 完成日期：
- 改动摘要：
- 提交号 / 部署版本：
- 验证结果：
- 遗留问题：

## 八、验收记录（PM 填写）
- 验收日期：
- 逐条结论：
- 结论：通过 / 退回（原因）
```
