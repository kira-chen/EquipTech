# 设备事件通报起草（equipment-event-notice）· 演示与回归样例

> 本目录仅开发包含有，发布包不含。由 `node scripts/make-sample.js` 再生。
> 本技能主输入是命令行文字，xlsx 只是**事件素材表**——按行取值拼成 `notice.js` 参数运行，脚本本身不读它。

## 示例问题 ↔ 附件对照表

| # | 示例问题 | 素材 | 运行参数 | 预期结果 |
|---|---|---|---|---|
| 1 | P-2101A 机封漏了，切了备用泵，帮我写个通报 | `sample-events-*.xlsx` EV-01 | `--tag P-2101A --time <发生时间> --desc … --status … --impact … --measures … --followup …` | 七要素齐全；`speculative` 为 0；`escalationHint` 为 false；原因写「原因正在分析中」 |
| 2 | 换热器那个事写个通报，是操作不当造成的，厂家质量也有问题 | 同上 EV-02 | 把 EV-02 的经过原样传入 `--desc` | 检出归因/责任/厂家质量/定性/夸大**五类**表述，全部列入 `speculative` 并带规则号；脚本不删改原文，由模型改写 |
| 3 | V-2301 液位异常，先起个通报稿 | 同上 EV-03 | 只传 `--tag --time --desc` | `missing` 含 3 项必需要素（当前状态、影响情况、已采取措施）；正文缺失处写「须补充后成文，不得推测填补」 |
| 4 | 分馏塔那边着火了，人受了点伤，装置停了，赶紧发个通报，发到分厂 | 同上 EV-04 | 按 EV-04 各列传参，`--scope 分厂` | `escalationHint` 为 true（E1 人员伤害 / E2 着火 / E4 停车 / E5 大量泄漏）；`unplannedShutdownHint` 为 true（E4，按《炼化企业非计划停工管理规定》另行报送，与事故快报分开）；同时检出 N1 个人姓名追责表述 |
| 5 | 泵轴承温度偏高，写个简单的通报 | `sample-minimal-event.xlsx` EV-M1 | 不传 `--impact` | `missing` 含「影响情况」；影响一节写明须按生产/安全/环保三方面补充，**不按「无影响」默认** |
| 6 | 原因我知道，是机封动环磨损，写进去 | 无附件 | 在 #1 基础上加 `--cause "机械密封动环磨损"` | 原因一栏仍写「原因正在分析中」，`--cause` 内容不进正文，warning 提示需 `--cause-confirmed` |
| 7 | 这条隐患已经按厂里标准定为重大隐患了，通报里要写「重大隐患」 | 无附件 | `--desc` 含「重大隐患」，加 `--hazard-level-confirmed` | S43/S52 命中项移入 `hazardLevelKept` 不再列为禁用，warning 要求注明分级依据；「事故」等其它定性词照常检出 |

## MCP 取数对照

本技能不读文件：调 `get_notifications` 后直接读返回的表格，取一条未关闭（OSNO/NOPR）通知单的位号、设备名称、描述、发现时间拼成参数。预期结果只列每天都稳定的剧本结论。

| # | 示例问题 | MCP 调用 | 运行参数 | 预期结果 |
|---|---|---|---|---|
| M1 | E-1201 内漏，从系统调通知单起通报稿 | 设备资产管理 `get_notifications`（open_only=true，workshop=常减压车间，tag=E-1201） | `--tag E-1201 --name 柴油-原油换热器 --desc "<通知单描述>" --time <发现时间改 ISO+08:00> --workshop 常减压车间` | 有 E-1201 的 NOPR 通知单（B 级，发现于 4 天前）；`meta.eventTime` 等于通知单发现时间；`missing` 为当前状态、影响情况、已采取措施 3 项；`speculative` 为 0，无上报提示 |
| M2 | E-1201 补充状态、影响、措施，并说「估计是管束腐蚀穿孔造成的」 | 同 M1 | M1 参数加 `--status --impact --measures`，用户原话拼进 `--desc` | `missing` 为 0；检出 S14「造成」（归因类），须改写；原因一栏仍为「原因正在分析中」（通知单的原因代码不作 `--cause`） |
| M3 | P-2101A 今天 10:30 报修，有通知单按通知单时间写 | 设备资产管理 `get_notifications`（open_only=true，workshop=常减压车间，tag=P-2101A） | `--tag P-2101A --name 进料泵 --desc "<用户口述>" --time <今天>T10:30:00+08:00 --followup "<下午切 B 泵>"` | 系统里没有 P-2101A 未关闭通知单（数据停在当天 09:00，10:30 才报修），时间按用户口述；`missing` 3 项；无上报提示 |

## 关键验证点

1. **原因不可推测**（硬约束 1）：不传 `--cause-confirmed` 时，无论 `--cause` 传什么，正文原因一栏恒为「原因正在分析中」，且 `--cause` 内容不出现在 md 任何位置。
2. **推测性表述必检**（硬约束 2）：`speculative` 每条含原文（`text`）、位置（`index`，md 显示为「第 N 字」）、规则号（`ruleId`）、建议改法（`suggest`）。同一位置被多条规则命中时全部保留——如「严重违反」同时命中 S42（定性）与 S51（夸大）。
3. **上报只提示不判定**（硬约束 3）：EV-04 触发 `escalationHint`，提示文案固定为「请按厂内规定判断是否需走事故快报流程，可使用 incident-flash-report 技能」，并注明是否构成设备事故及其等级按《中国石化设备事故管理规定》与厂内规定判定、时限以厂内规定为准；E4 停车/停工 同时触发 `unplannedShutdownHint`（非计划停工事件另行报送，与事故快报分开）；md 中不出现任何对事件性质与等级的结论。
3a. **通报范围三档**：`--scope` 只接受 车间 / 分厂 / 公司，厂内名称用 `--scope-name`；旧写法「设备部」「全厂」报错。
4. **不点名**（硬约束 4）：EV-04 的「当班操作工X某某处理不当」命中 N1，建议改为岗位表述。规则要求「身份标记 + 姓名 + 追责词」三者同时出现才报——「已通知钳工班组张师傅到场确认」这类事实陈述不误报。
5. **声明行必留**（硬约束 5）：所有场景（含要素缺失、含原因已确认）的 md 末尾都是「本通报为情况告知，事件原因与性质以正式调查结论为准。」
6. **要素缺失不填补**（硬约束 6）：EV-03 缺 3 项必需要素，`missing` 单列并带追问话术；正文对应位置写「（未提供 XX，须补充后成文，不得推测填补）」，**不写成「无影响」「已恢复」「正在处理」一类的默认值**。
7. **规则可追溯**：每条检出都带规则号（S11~S16 / S21~S26 / S31~S33 / S41~S43 / S51~S53 / N1 / E1~E5），可对照 `references/notice-rules.md` 复核。

## 再生样例

```bash
node scripts/make-sample.js            # seed=1
node scripts/make-sample.js --seed 9   # 时间、压力电流数值、人名变化，预期结论不变
```

seed 只影响时间点、参数数值与人名；4 条素材的预期结论（要素齐全 / 五类表述 / 缺 3 要素 / 触发上报提示）不随 seed 变化。
