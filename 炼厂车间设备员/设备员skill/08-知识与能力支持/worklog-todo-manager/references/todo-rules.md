# 待办汇集口径与日志表述规范

## 一、到期分桶

以 `--date` 为基准日，按到期日分五桶（`--horizon` 默认 7 天）：

| 桶 | 判据 | 报表章节 |
|---|---|---|
| `overdue` 已逾期 | 到期日 < 基准日 | 二、已逾期 |
| `today` 今日到期 | 到期日 = 基准日 | 三、今日到期 |
| `upcoming` 近期 | 基准日 < 到期日 ≤ 基准日 + horizon | 四、近期 |
| `later` 前瞻期外 | 到期日 > 基准日 + horizon | 九、前瞻期外（有则出） |
| `noDueDate` 无到期日 | 无到期日 | 五、无到期日 |

逾期天数 = 基准日 − 到期日（自然日，不扣周末与节假日）。

**每次运行都按当前基准日重算逾期天数，但到期日本身永不改写。** 结转项在第二天逾期天数 +1，到期日仍是原来那一天——这正是「不自动延期」的体现。上游 JSON 里写的逾期天数只作参考，不直接引用（上游可能是前几天跑的），清单里的「时限」列一律用本脚本按基准日算的值。

## 二、优先级口径

脚本按「来源性质 + 是否超期」定优先级，与到期日无关；到期日单独参与排序。

| 优先级 | 归入此级的事项 |
|---|---|
| **P1 最高** | 重大隐患（不论是否超期）；超期未整改隐患；特种设备定期检验超期；安全联锁类仪表（安全阀、联锁变送器等 `safetyCritical`）的校验事项；校验不合格未整改；A 级（重大）缺陷；SAP 优先级 1（非常高 / 紧急 / 抢修）的工单；SAP 优先级 2 且已超期的工单；交接记录中期限已过的未完成事项 |
| **P2 高** | 临期隐患、已整改未验收待销号；特种设备定检临期；非安全联锁类校验超期；SAP 优先级 3 及以下的超期工单、工单停滞；B 级（严重）缺陷；交接记录中未到期或无期限的未完成事项 |
| **P3 中** | 工单临期（SAP 2~4）；非安全联锁类校验临期；C 级（一般）及未定级缺陷；润滑逾期；待办表与文字待办的默认级别 |
| **P4 低** | 润滑临期 |

依据：**法定检验与安全联锁 > 隐患整改 > 交接未完成与工单缺陷 > 预防性维护**。特种设备定检和安全阀校验超期涉及法定符合性，一旦超期属于违规运行，故不论实际逾期天数多少一律 P1。

### 与上游分级口径的对齐（《中石化口径对照》第三节）

| 上游口径 | 脚本识别 | 映射 |
|---|---|---|
| SAP 工单优先级 | `1 非常高` / `2 高` / `3 中` / `4 低`，数字或带文字均可；中文 紧急/特急/抢修→1、高/较急/重要→2、中/一般→3、低/不急/计划性→4 | 见上表 |
| 缺陷等级 | `A` / `B` / `C`（或 `A 级（重大）` 等 levelCn） | A→P1、B→P2、C→P3；未定级→P3，不猜测 |
| 旧 I~IV 四级缺陷口径（已废止） | `I`/`II`/`III`/`IV`、Ⅰ~Ⅳ、一级~四级、`I 级（紧急）` | I→A、II→B、III/IV→C，**逐条 warning 提示旧口径并改写标题为新口径等级名** |
| 待办表「优先级/紧急程度/级别」列 | P1~P4、SAP 1~4、紧急/高/中/低、A/B/C 级、旧 I~IV 级 | 同上；无法归类按 P3 且 `prioFromUser: false` |
| 交接记录 `pending[]` | 按 `due` 与基准日比较 | 期限已过→P1，其余→P2 |

用户在待办表「优先级」列写明的等级**覆盖上述推断**（`prioFromUser: true`）；`--priority-rules` 传入的厂内口径写入 `meta.priorityRules` 供模型成文时引用，脚本不据此改判。

## 三、排序口径

同一桶内按以下顺序比较，前者相同才比后者：

1. 优先级（P1 → P4）
2. 逾期天数（多者靠前）
3. 到期日（早者靠前；无到期日按最晚）
4. 来源类型
5. 事项文字（中文排序）

桶之间固定为：已逾期 → 今日到期 → 近期 → 前瞻期外 → 无到期日。

## 四、结转规则

上一日 `todo.json` 中 `status !== 'done'` 的事项**全部结转**，一条不落。

结转时保留：原始到期日（`dueDate` 与 `originalDueDate`）、原始来源（`originalSource`，形如「隐患整改｜hazard.json」）、原始出处（`srcRef`，含 sheet 与行号）。追加 `carriedFrom`（首次结转自哪一天，多次结转保留最早的那天）与 `carriedRounds`（已结转次数）。

**禁止**：
- 把结转项的到期日改成今天或往后推（**不自动延期**）
- 因为「看着像已经做完了」而不结转（**不静默丢弃**）
- 判定某项待办「已经不用做了」并剔除——关闭事项只能由设备员在上游系统或下一次 `--done` 中确认

本日来源中同一事项再次出现时（`key` 相同），只保留一条并打上结转标记，不重复计数——这不是丢弃，是同一条事项的去重。

清单中结转项必须标注「结转自 X 月 X 日」，逾期项必须显示逾期天数。

## 五、无到期日处理

来源数据没给到期日的事项，单列「五、无到期日」一节，每项写明原因（表未填写 / 来源本就没有 / 写法无法解析并附原始写法）。

**禁止**：按发现日 + 默认天数推算、按「一周内」默认、按前瞻期末日填入、或因无到期日而不列入待办。

无到期日不等于不重要：校验不合格未整改是 P1，工单停滞是 P2，它们都在这一节。

## 六、疑似重复判定

两类情况会被标为疑似重复：

1. **跨来源同一对象**：同一位号或同一业务编号，在两个及以上不同来源中都有待办。例如 P-1101B 既在工单跟踪的超期清单里，又在缺陷跟进里——很可能是同一件事，也可能是两件（机封漏是缺陷，工单是为它开的；但也可能工单说的是另一处）。
2. **事项文字完全一致**：去掉标点空白后文字相同的多条待办。

判定结果只列出供确认，**绝不自动合并、绝不自动删除其中一条**。两条都保留在 `items[]` 里，都参与计数。设备员确认是同一件事后，自行在上游系统合并。

判定用的是位号与编号的精确匹配，不做语义相似度推断——宁可漏标，不可误合。

## 七、日志表述规范

### 「需协调事项」段
逐条写明：事项、卡在哪个环节、需要谁配合、希望什么时候有回音。只写来源数据里有的内容。

| 场景 | 应写 | 不得写 |
|---|---|---|
| 卡点 | 「WO-26090012 备件未到，需计划科确认到货时间」 | 「采购拖沓导致备件迟迟不到」 |
| 外委 | 「甲乙丙公司承接的 WO-26090007 已超期 2 天，原因未记录，需联系对方说明」 | 「外委单位不负责任」 |
| 上报 | 「YH-2609-03 属重大隐患且已超期，建议报车间主任并纳入周会督办」 | 「该隐患可延至下月整改」 |

### 「明日重点」段
按脚本排序的前若干项展开，说明安排思路、要提前准备的资料或备件、与生产计划的冲突点。

**不得调整脚本给出的优先级顺序**。认为顺序不合理时，在文字里说明理由并建议设备员复核，而不是改表。

### 硬约束

- **不判定某项待办可以不做**。看着不重要也要列，重要与否由设备员判断。
- **不自动延期、不自动关闭**任何事项。
- **不替设备员填写完成情况**。`--done` 没给就留空。
- **数字一律引用 `todo.json` 的 `counts`**，不自行统计。
- **覆盖范围要说清**：只汇集了所提供的来源，没提供的来源（如厂内业务系统 EM/SAP PM 里的通知单、工单待办）不在清单内。

### 必须保留的声明行

两份 md 产出均须包含（脚本已自动写入，成文时不得删改）：

> 待办汇集自所提供来源，覆盖范围见清单说明；厂内业务系统（EM/SAP PM）中的待办请以系统为准。
> 本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。

产出 md 不用 emoji，醒目提示用「【注意】」。

## 八、上下游衔接

- 工单超期与停滞的催办 → `work-order-tracker` 的「催办清单.md」
- 隐患超期的督办 → `hazard-closure-tracker` 的「督办清单.md」
- 定检与校验的送检准备 → `special-equipment-inspection-due` / `valve-instrument-calibration-ledger`
- 今日完成事项与待办概况进设备日报 → `equipment-daily-report`
- 值班 / 休假 / 调岗工作交接的未完成事项 → `shift-handover-record` 的 `handover.json`（约定：`meta.skill === 'shift-handover-record'` 且含 `pending` 数组；本技能把 `pending[]` 原样纳入待办，期限不改写，交接记录自身的结转次数 `carryTimes` 带入 detail；无 `meta.skill` 的旧版按结构推断并 warning）
- 本日产出的 `todo.json` 即次日运行的 `--prev` 入参
