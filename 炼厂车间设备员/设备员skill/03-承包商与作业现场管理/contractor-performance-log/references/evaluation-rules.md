# 四维度评价口径、默认分值表、分档标准与表述规范

## 一、默认评分口径

> **本表为脚本内置的默认口径，不是任何一家厂的正式规定。**
> 未通过 `--rules` 传入厂内口径时，产出中必须标注「**采用默认口径，非厂内正式口径，结果仅供参考**」，脚本已在 `performance.md` 开头、得分汇总表旁与 `performance.json` 的 `meta.rulesNotice` 三处写入该提示。
> 用户提供厂内正式口径时，用 `--rules "<厂内评分口径xlsx>"` 覆盖；覆盖后标注「厂内口径（文件名）」。

### 基准分

| 项目 | 默认值 | 说明 |
|---|---|---|
| 基准分 | **100 分** | 每家承包商在评价区间内从 100 分起算，按四个维度的记录逐条扣分 |

### 扣分表

| 维度 | 情形 | 默认扣分 |
|---|---|---|
| **安全违章** | 一般违章 | −2 |
| | 严重违章 | −5 |
| | 重大违章 | −10 |
| **施工质量** | 返工 | −3 |
| | 质量不合格 | −5 |
| **进度履约** | 延期（每次） | −2 |
| | 严重延期 | −5 |
| **现场配合与文明施工** | 文明施工差 | −1 |
| | 不配合 | −3 |

得分 = 基准分 − 该承包商在评价区间内全部可判定记录的扣分之和。**不设下限截断，得分可低于 0**（脚本如实输出，由安全环保部门按厂内制度处理）。

### 分档标准

| 分档 | 得分区间 |
|---|---|
| 优 | 90 分及以上 |
| 良 | 80 ~ 89 分 |
| 一般 | 70 ~ 79 分 |
| 差 | 70 分以下 |

**分档只是记录汇总的呈现方式，不构成对承包商的评级结论。** 厂内分档标准可用 `--rules` 文件的「分档标准」工作表覆盖（列：分档、最低分；最低分留空的一行为最低档）。

## 一之二、违章三档口径与制度出处

- 安全违章按《中国石化承包商安全管理规定》的**一般违章 / 严重违章 / 重大违章**三档记录；记录中写"严重违规"的归**严重违章**，不是重大违章；"A/B/C 类违章"按 A→重大、B→严重、C→一般识别（厂内若定义不同，用 `--rules` 的程度名称列覆盖）。
- 分档定性（哪些行为属于严重违章、重大违章）由安全环保部门按厂内制度掌握，脚本只按记录中填报的程度归类，**不按事项描述自行升降档**。
- 承包商考核归口：按《中国石化承包商安全管理规定》，承包商安全管理由安全环保部门归口、业务主管部门（设备、工程等）配合；车间（属地单位）负责属地监督与记录。本技能的产出是车间侧记录，报送对象写"安全环保部门（归口）/ 业务主管部门"。具体的考核办法、分值与处罚标准**以厂内制度为准，本文件不转述数值**。
- 施工质量维度中"不符合"一词在现场多作"不符合项"记录用语，不等于"质量不合格"，脚本不自动归档，进未判定并提示用户明确是返工还是质量不合格。

## 二、维度归类口径

脚本按「类型」列归入四个维度，无法归入任何一个维度的记录一律进 `undetermined`，**绝不按任一维度的最低档计分**。

| 维度 | 可识别的写法 |
|---|---|
| 安全违章 | 安全违章、安全、违章、违规、HSE、安全问题、三违 |
| 施工质量 | 施工质量、质量、返工、工程质量、质量问题 |
| 进度履约 | 进度履约、进度、履约、工期、延期、进度问题 |
| 现场配合与文明施工 | 现场配合、配合、文明施工、文明、现场管理、协调、配合度 |
| **类型缺失** | 空单元格、—、-、/ |
| **类型无法识别** | 以上都不匹配的其他文字（如「其他」「综合」） |

严重程度的取值枚举按维度分列，详见 `input-spec.md`。

## 三、严重程度缺失的处理（硬约束）

**严重程度为空、或填写的内容在该维度下无法归类时：**

1. 该条记录归入 `undetermined`，`deduction` 为 `null`
2. **绝不按该维度的最低档计分**，也不按最高档计分
3. 在「六、未判定记录」一节单列，注明缺哪个字段
4. 产生 warning，具体到 sheet 名与行号
5. 该条记录仍计入该承包商的「记录数」与「未判定条数」，但不进扣分合计

**禁止**：
- 严重程度为空时按「一般违章 −2」「返工 −3」等最低档兜底
- 按事项描述的文字自行推断严重程度
- 因「大概也就是一般违章」而给出估计扣分

## 四、承包商名称不一致的处理（硬约束）

同一单位在记录中常出现全称与简称混用（如「宏远建安工程有限公司」与「宏远建安」）。脚本的处理方式是：

1. **按名称字面量分组统计**——每个不同的名称各自成一行，各算各的得分与分档
2. 用名称核比对（去掉「有限公司」「工程队」等后缀与地域前缀）识别疑似同一单位的名称组，列入 `nameAmbiguity`
3. 在「五、承包商名称待确认」一节列出名称组、各自记录条数、疑似依据与对应行号
4. 在报告开头提示存在名称待确认项
5. 在得分汇总表中对涉及的名称标注「是（见第五节）」
6. 产生 warning

**脚本绝不自动合并统计。** 合并与否必须由用户人工确认——两个名称可能确实是同一家，也可能是两家不同单位（如「宏远建安」与「宏远建安装饰」）。确认为同一单位后，应回到源记录统一名称再重跑脚本，而不是在报告里手工加总。

**禁止**：
- 脚本自动把简称的记录并入全称
- 模型在成文时自行把两行相加
- 因「一看就是同一家」而跳过确认

## 五、区间与日期口径

- 评价区间由 `--from`、`--to` 指定，按「记录日期」过滤，两端均为闭区间
- 区间外的记录不计入统计，单列计数并 warning
- **记录日期缺失的记录不计分**，进 `undetermined`，原因写「记录日期缺失，无法确认是否属于本评价区间」——**不按区间内默认处理**

## 六、未整改项

整改情况填报为「未整改」「整改中」「待整改」等的记录，进 `unrectified` 单列一节。

- 整改情况为**空**的记录**不算未整改**，也不算已整改，不进 `unrectified`
- 整改情况填了无法归类的文字，按未确认处理并 warning
- 未整改**不额外扣分**（扣分只由维度与严重程度决定），但须在报告中单列跟踪

## 七、评价说明表述规范

撰写 250~400 字，结构固定为六段：

1. **评价区间与口径**：区间、车间、记录条数、承包商名称数、采用的口径来源与性质。
2. **各承包商记录与得分情况**：逐家写记录数、各维度扣分、得分与分档，数值一律引用 `performance.json`。
3. **违章记录情况**：按重大 / 严重 / 一般分组的条数与典型事项（陈述事实，不加评判）。
4. **未整改项**：条数、涉及单位与事项，说明须继续跟踪至闭环。
5. **名称待确认与未判定项**：名称组、未判定条数与缺哪个字段，说明未合并、未按最低档计分。
6. **提请安全环保部门/业务主管部门核实事项**：需要归口部门确认的口径、名称与缺失字段。

### 措辞对照表（硬约束）

| 场景 | 应写 | **不得写** |
|---|---|---|
| 得分较低的单位 | 「本区间内记录到安全违章 3 条（重大 1、严重 1、一般 1），按默认口径扣 17 分，得 83 分」 | 「该队伍能力差」「管理混乱」「素质低」 |
| 对后续合作的看法 | 「以上为车间（属地单位）侧记录，是否影响后续承揽由安全环保部门按厂内制度决定」 | 「不建议再用」「建议清退」「下次别找他们」 |
| 违章记录 | 「记录到受限空间作业未办票即入罐 1 条，严重程度填报为重大违章」 | 「该队伍安全意识薄弱」「屡教不改」 |
| 未整改项 | 「整改情况填报为未整改，须继续跟踪至闭环」 | 「整改不力」「敷衍了事」 |
| 名称待确认 | 「「宏远建安工程有限公司」与「宏远建安」疑似同一单位，脚本未作合并，请确认后统一名称重跑」 | 「这两个应该是一家，合起来算 12 分」 |
| 严重程度缺失 | 「因严重程度为空，该条未计分，须补齐后重新统计」 | 「按一般违章估计扣 2 分」「问题不大」 |
| 口径说明 | 「采用默认口径，非厂内正式口径，结果仅供参考」 | 「按厂里标准算下来是 83 分」 |
| 分档 | 「按默认分档标准归入「良」」 | 「评为良级承包商」「达到良好水平」 |
| 得分 | 引用 `performance.json` 的 `byContractor[].score` | 自行计算或调整分值 |

### 硬约束

- **只陈述记录事实，不作定性判断**。写「记录到 N 条 X 类问题」，不写「该队伍怎么样」。
- **不做考核、评级、黑名单与处罚建议**。分档只是记录呈现，不是评级结论。
- **不评价技术能力与商务报价**。
- **不合并名称**。疑似同一单位的名称在报告中始终分行呈现。
- **不给未判定项补分值**。
- **数量、分值、条数一律引用 `performance.json`**，不得自行统计。
- **声明行「本数据为车间（属地单位）侧记录汇总，承包商考核由安全环保部门归口、业务主管部门配合，分档定性与处罚按厂内制度决定；评分口径若非厂内正式口径，结果仅供参考」不得删除或改写。**
