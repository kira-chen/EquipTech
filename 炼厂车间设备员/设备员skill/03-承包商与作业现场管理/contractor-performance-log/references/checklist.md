# 交付自检清单

运行脚本后、交付前逐项核对。

## 脚本执行
- [ ] 末行 JSON 的 `ok` 为 `true`；若为 `false`，已把 `error` 原文告知用户并终止，未手工评分
- [ ] `warnings` 已逐条告知用户，未隐去任何一条（缺列 / 严重程度取值非法 / 承包商名称不一致 / 记录超出区间 / 日期缺失）
- [ ] `performance.json`、`performance.md`、`summary.json` 均已生成

## 承包商名称（最高优先级）
- [ ] `nameAmbiguity` 中的每一组名称都在「五、承包商名称待确认」一节列出，未遗漏
- [ ] **报告中没有任何一处把疑似同一单位的两个名称的记录数或扣分加总**
- [ ] 得分汇总表中疑似重复的名称各自单独成行，并标注「是（见第五节）」
- [ ] 已向用户明确提出：这几组名称是否为同一单位，须人工确认；确认后应统一源记录名称再重跑，而不是在报告里手工加总
- [ ] 未发现疑似重复时，第五节写明「本期未发现疑似重复的承包商名称」，未凭空生成待确认项
- [ ] 有「承包商编码」列时，同一编码下的不同名称写法已按编码合并为一行（名称以「/」并列展示），且 warnings 中已提示；无编码的记录仍按名称分组

## 严重程度与未判定
- [ ] 严重程度为空、或在该维度下无法归类的记录，均在 `undetermined` 中，**扣分为 `null`**
- [ ] **没有任何一条未判定记录按最低档（一般违章 −2 / 返工 −3 / 延期 −2 / 文明施工差 −1）兜底计分**
- [ ] 未判定记录未按事项描述文字推断严重程度
- [ ] 「严重违规」已归严重违章（不是重大违章）；施工质量维度填「不符合」的记录进未判定，未自动按质量不合格扣分
- [ ] 每一条未判定记录都注明了缺哪个字段
- [ ] 记录类型缺失或无法归类的记录同样进 `undetermined`，未计分
- [ ] 记录日期缺失的记录进 `undetermined`，未按区间内默认处理

## 评分口径与免责
- [ ] 未传 `--rules` 时，`performance.md` 开头出现「**采用默认口径，非厂内正式口径，结果仅供参考**」，未删除或弱化
- [ ] 得分汇总表旁同样标注了口径性质
- [ ] 传入 `--rules` 时，已写明「厂内口径（文件名）」，且口径文件中被忽略的行已作为 warning 告知用户
- [ ] 报告中的基准分、扣分表、分档标准与 `performance.json` 的 `rules` 段一致

## 数字一致性
- [ ] 报告中每个数字都能在 `performance.json` 的 `counts` / `byContractor` / `rules` 中找到对应，未自行统计
- [ ] 各承包商得分 = 基准分 − 扣分合计，与 `byContractor[].score` 一致
- [ ] 分档与 `byContractor[].grade` 一致，未自行调档
- [ ] 区间外记录、日期缺失记录未混入本期统计

## 未整改项
- [ ] 「四、未整改项」一节列出全部 `unrectified` 条目
- [ ] 整改情况为空的记录未被写成未整改
- [ ] 已提示这些条目须继续跟踪至整改闭环

## 评价说明（表述规范）
- [ ] 已替换 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字
- [ ] 字数 250~400
- [ ] 六段结构齐全：评价区间与口径、各承包商记录与得分、违章记录情况、未整改项、名称待确认与未判定项、提请安全环保部门/业务主管部门核实事项
- [ ] **只陈述记录事实**：写「记录到 N 条 X 类问题」，未写「该队伍怎么样」
- [ ] **未出现定性判断用语**：「该队伍能力差」「管理混乱」「素质低」「安全意识薄弱」「屡教不改」「整改不力」「敷衍了事」一律不得出现
- [ ] **未出现对后续合作的建议**：「不建议再用」「建议清退」「下次别找他们」一律不得出现
- [ ] 未把分档写成对承包商的评级结论（不写「评为良级承包商」）
- [ ] 未评价技术能力与商务报价
- [ ] 未提考核、处罚、黑名单建议
- [ ] 产出中不含 emoji，醒目提示用「【注意】」
