# 与 `work-permit-precheck` 的衔接口径（作业票）

## 一、本技能的定位

**入口与衔接层，不是判定层。** 作业票的合规判定由 `work-permit-precheck` 的规则引擎（GB 30871-2022 规则表）完成，本技能负责：

1. 车间侧前置信息的补全与提示（设备交出、交叉作业、承包商资质）
2. 判定结果的转达（`scripts/merge-report.js` 逐条深拷贝）
3. 车间关注项的补充（与规则判定严格分开成节）

## 二、术语：作业许可八大类

按《中国石化作业许可管理规定》，车间口径统一写：**用火作业**、受限空间作业、高处作业、吊装作业、临时用电作业、动土作业、断路作业、**盲板抽堵作业**。

- 源技能 `work-permit-precheck` 的 `type` 取值按 GB 30871 写"动火"，票面也常印"动火安全作业证"。**转达时 `type` 与 findings 原词照搬**（例如"受限空间内动火，未关联受限空间作业票"），本技能只在源技能字段表里另加一行"作业许可八大类（本技能加注）：用火作业"，不改源值。
- 用火按特级 / 一级 / 二级，高处一~四级，吊装一~三级：**级别以票面与审批人为准**，本技能与源技能都不自判级别（源技能只核对级别与票面要素是否相符）。
- 拆装盲板的作业必须办理盲板抽堵作业许可，源技能有对应交叉票规则；本技能不另加规则。
- 监护按**双监护**（属地监护人 + 作业单位监护人）；源技能查"监护人"栏，车间侧提示里可补"属地监护人是否到位"，但这是车间自查项，不是规则判定。

## 三、依赖不可用时的处理（硬规则）

运行 `node scripts/check-dependency.js` 确认依赖可用性（支持 `--skill-root`、环境变量 `SKILL_PACK_ROOT`、WorkBuddy / Claude Code / 豆包默认技能目录、技能包一级子目录扫描）。

`available: false` 时：

1. 明确告知用户「需先安装特殊作业票预检技能」
2. **终止本次任务**
3. **不得用本技能自行判定票据合规性**
4. **不得降级为人工判断或凭经验给结论**

这条没有例外。作业票合规判定涉及安全红线，宁可不给结论，也不能给一个没有规则引擎支撑的结论。

## 四、结果转达规范（merge-report.js 已固化）

### 必须照搬的内容

| 来源字段 | 转达要求 | 脚本实现 |
|---|---|---|
| `findings[]` 每条的 `rule_id / severity / message / detail / basis` | 原文照搬，不改写措辞、不合并、不归类、不简化 | 逐条 `JSON.parse(JSON.stringify())` 深拷贝 |
| `severity: undetermined` | 保留「未判定」状态与缺失字段说明 | 单列「三、未判定项」，附【未判定】说明 |
| 不在四级（must_fix / should_improve / undetermined / pass）内的 severity | 原样保留，单列并 warning | `counts.other` |
| `summary` | 原值保留；报告按 findings 重新计数，不一致只 warning | `sourceSummary` 与 `counts` 并存 |
| `extraction_notes` | 原文附在报告末尾 | 「附：源技能抽取说明（原文）」 |
| `disclaimer` | **全部保留**，置于本技能声明行之前 | `meta.sourceDisclaimer` + md 末尾 |

### 禁止的操作

- 把「未判定」改写为「符合」或「不符合」
- 把多条不符合项合并成一条概括
- 调整不符合项的严重程度
- 因为「看起来问题不大」而弱化表述
- 删除源技能的任何声明行
- 把源技能的"动火"改写成"用火"（票面原词必须可追溯）

## 五、车间侧补充提示

本技能可以补充以下车间关注项，但**必须单独成节**，标题写「车间侧补充提示（非规则判定）」：

| 补充项 | 可接的技能 | 状态取值 |
|---|---|---|
| 设备交出条件 | `equipment-handover-check` | 已核实 / 未核实 / 不适用 |
| 同区域交叉作业 | `cross-operation-conflict` | 同上 |
| 承包商资质 | `contractor-qualification-check` | 同上 |
| 其它车间自查项（脚手架验收牌、属地监护人到位等） | 车间自查 | 同上 |

- 不传 `--notes` 或某项未给 → 一律「未核实」，脚本**不替用户推测为已核实**。
- 状态写成「大概没问题」「应该交出了」等不在三值内 → 按「未核实」处理并 warning。
- **这些信息不进入规则判定，不影响源技能的结论。** 分节呈现是为了避免用户把车间提示误当成合规判定结果。

## 六、双重声明

交付时必须同时保留：

1. **源技能的全部声明行**（原文，脚本从 `disclaimer` 读入）
2. **本技能的声明**：「预检为辅助自查，不替代安全部门审批；票据是否签发以审批人意见为准。」

源技能结果没有 `disclaimer` 字段时脚本 warning，不伪造源声明。

## 七、制度引用

- 《中国石化作业许可管理规定》：八大类命名、双监护、作业票审批层级（数值与层级以厂内制度为准）。
- GB 30871-2022：源技能规则表的依据，条款号以正式文本为准（源技能声明行已注明）。
- 本技能不转述任何法规数值。

## 八、与 `overhaul-process-check-bridge` 的边界

| | 本技能 | overhaul-process-check-bridge |
|---|---|---|
| 对象 | 作业票（一处一票） | 检修方案的安全措施章节 |
| 依赖 | `work-permit-precheck` | `overhaul-safety-check` |
| 输出 | 必须整改 / 建议完善 / 未判定 / 通过 | 缺失 / 建议完善 / 未判定 / 已有 |

两者都不做技术内容正确性审查；方案里"各专项措施以开工时逐票办理的作业票为准"，所以方案核查通过不等于作业票通过。
