# 重复故障判定口径与表述规范

> 依据《中国石化设备管理规定》《炼化企业设备管理技术规定》中设备故障管理与重复故障分析的要求整理，不转述具体数值；默认阈值为常见口径，厂内可配置。
> **本结果为频次统计与文本相似匹配，重复故障的根本原因须由设备工程师组织专项分析确定。**
> 这句话与通用声明行「本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。」必须原样保留在每一份交付的 `repeats.md` 中，脚本已自动写入，不得删改。

## 一、统计区间怎么定

| 区间 | 后果 |
|---|---|
| 过短（< 6 个月） | 间隔较长的重复故障看不出来，**会漏判**。一台半年坏一次的泵，用 3 个月区间统计只会看到 1 次 |
| 过长（> 12 个月） | 会把**已经整改完成**的历史问题重新算进来，得出「这台设备老坏」的错误印象，误导检修排程 |
| **建议 6~12 个月** | 兼顾覆盖与时效。脚本默认建议 180~365 天，超出该范围会 warning 提示 |
| **默认「一年内」** | 不传 `--from` 时取 `--to`（默认当日）往前 12 个自然月，对应「同一设备同一部位一年内 ≥2 次」的口径，报告抬头注明「起始日按默认口径推算」 |

脚本在 `repeats.json` 的 `meta.periodAdvice` 与 `repeats.md` 抬头处**注明本次实际统计区间与天数**，交付时必须一并说明。

区间起点还应避开大检修节点：跨越一次装置大检修（停工检修）的区间，大检修前后的故障不具可比性，应向用户确认是否按大检修后重新起算（显式传 `--from`）。

## 二、判定规则表（可追溯规则号）

| 规则号 | 名称 | 判定条件 | 默认阈值 |
|---|---|---|---|
| D1 | 同设备同部位重复故障 | 区间内同一位号、故障部位（SAP 对象部件）归一后相同的记录数 ≥ 阈值 | **≥2 次**（同一设备同一部位一年内 ≥2 次；`--min-count` 可调） |
| D2 | 同设备同现象/同代码重复故障 | 区间内同一位号、SAP 损坏代码相同或相似度 ≥ 阈值的记录聚成一组，组内记录数 ≥ 阈值 | ≥2 次（= max(2, `--min-count` - 1)） |
| D3 | 同型号/同类设备共性故障 | 同型号（或同设备类型 / 同部位，随 `--by`）下相似故障组涉及 ≥2 台设备且组内 ≥3 次 | 台数 ≥2 且次数 ≥3 |
| D4 | 故障间隔缩短 | 相邻故障间隔序列单调不增、末次间隔严格小于首次且 ≤ 首次的 60% | 至少 3 次故障（2 个间隔） |
| U1 | 故障现象无信息量 | **无 SAP 损坏代码**且现象为空、仅泛指故障词、泛指主语+泛指词、过短且无现象词 | 一律排除出判定 |

`--min-count` 同时抬高 D1 与 D2 的阈值。厂内有正式的重复故障口径时以用户为准，并在交付说明中注明「按厂内口径 XX 次」。

## 三、相似匹配是怎么算的（必须向用户讲清楚）

**SAP 损坏/故障代码优先。** 中石化炼化厂 SAP PM 通知单的损坏代码（目录代码）是结构化的故障归类，比文本相似更可靠：

| 情形 | 相似度 | matchBasis |
|---|---|---|
| 两条都有代码且相同 | 1 | 「SAP 损坏/故障代码同为「X」（代码优先于文本相似）」 |
| 两条都有代码且不同 | 0（不归组，不靠文本硬凑） | 「SAP 损坏/故障代码不同（A / B），不归为同一相似组」 |
| 仅一方有代码 | 按下式文本比对 | 加注「仅一方有 SAP 损坏/故障代码，退回文本与字段比对」 |

无代码时，两条故障记录的相似度：

```
相似度 = 0.5 × 故障现象文本 bigram Dice 系数
       + 0.3 × 故障部位（归一后）是否相同
       + 0.2 × 现象类型是否相同
```

- **bigram Dice**：把两段描述切成相邻两字的片段集合，算交集占比。「机封处滴漏」与「机封泄漏滴漏」共享「机封」「滴漏」等片段，得分较高。
- **故障部位**：按 `input-spec.md` 的归一表比对，「机封」与「机械密封」视为同一部位；任一方为空则该项不得分，并在 matchBasis 中写明「故障部位字段有缺失，未参与比对」。
- **现象类型**：泄漏 / 振动 / 异响 / 温升 / 腐蚀 / 变形开裂 / 堵塞结焦 / 性能下降 / 电气异常 / 仪表异常 / 卡涩抱死 / 失效拒动，按关键词匹配；归为「其他」的不得分。

默认阈值 0.55（`--similarity` 可调），达到即归入同一相似故障组（单链聚类：与组内任一成员相似即入组）。

### matchBasis：每一条判定都要说明依据

脚本在 `byEquipment[].hits[].matchBasis` 与 `byModel[].matchBasis` 中逐项列出相似依据，例如：

```
- 现象文本 bigram 相似度 0.59
- 故障部位同为「机械密封」
- 现象类型同为「泄漏」
```

报告中必须把 matchBasis 呈现给设备员，让他能自己判断这几次故障是不是真的一回事。

### 硬约束：相似 ≠ 同因

**这是基于文本与字段的机械匹配，不是失效机理分析。** 描述写法相近的两次故障，可能是完全不同的原因（一次是备件质量、一次是操作不当）；描述写法不同的两次故障，也可能是同一个根因。

| 应写 | 不得写 |
|---|---|
| 「区间内机封部位故障 4 次，现象描述相似（bigram 0.59、部位同为机械密封）」 | 「机封反复失效，说明是同一个问题」 |
| 「两台换热器均报管束内漏，属共性线索，建议核实」 | 「同型号换热器存在设计缺陷」 |
| 「间隔由 90 天缩短至 30 天」 | 「设备已进入劣化期」 |

## 四、无信息描述：绝不据此判定（最重要的一条）

故障现象为空或只写「故障」「坏了」这类描述，**不含任何可供匹配的信息**。如果把它们当作「同一类故障」来计数，会得出完全虚假的重复故障结论——一台设备报修 4 次全写「故障」，看上去是严重的重复故障，实际可能是 4 个毫不相干的问题。

因此脚本：

1. 把这类记录整条移出判定流程，列入 `uninformative`；
2. 在 `repeats.md` 第六节**单列一张表**，注明原始写法、无信息原因与出处行号；
3. 在 warning 中逐行提示，具体到 sheet 与行号；
4. 这些记录**不计入** `byEquipment`、`byModel`、`shorteningInterval` 的任何计数。

交付时必须明确告诉用户：「有 N 条记录因故障现象无信息量未参与判定，补填具体现象后重新统计才能得到完整结论。」**不得把这 N 条按某一类重复故障归类，也不得以它们的条数暗示重复严重程度。**

## 五、故障间隔与间隔缩短

- **故障间隔**：同一位号相邻两次故障的日历天数，按故障时间升序两两相减。
- **平均间隔 / 最短间隔**：只有 1 次故障时为 `null`，报表显示「—」，**绝不显示为 0**。
- **间隔缩短（D4）**：要求间隔序列单调不增、且末次间隔 ≤ 首次间隔的 60%。先缩后扩（如 50→190）不算缩短。

间隔缩短是统计现象，不是劣化判定。**是否真的存在劣化趋势，须结合振动、温度、油液等状态数据由工程师判断。** 报告中只写「间隔由 X 天缩短至 Y 天，建议关注」。

## 六、三个归类维度（`--by`）

| 取值 | 第三节按什么归类 | 适用场景 |
|---|---|---|
| `equipment`（默认） | 型号 / 设备类型 | 常规：先看单台设备，再看同型号有没有共性 |
| `model` | 型号 / 设备类型 | 用户明确问「同型号设备是不是都这个毛病」 |
| `part` | 故障部位（归一后） | 用户问「哪个部位最容易坏」「机封问题是不是普遍」 |

三种维度下第二节（同设备重复故障）口径不变，只有第三节的归类键改变。`byModel[].dimension` 字段写明本次用的是哪个维度。

## 七、分析段表述规范

撰写 250~450 字，结构固定为六段：

1. **总体情况**：统计区间与天数、区间内故障记录数、涉及设备台数、命中重复故障的设备数。
2. **同设备重复故障与建议**：逐台说明位号、次数、命中的规则号与 matchBasis 依据、建议动作（安排专项分析 / 列入下次检修重点）。
3. **同型号共性问题**：涉及几台、累计几次、共性线索是什么，建议扩展排查同型号其余设备。
4. **故障间隔缩短设备**：位号、间隔序列、缩短幅度，建议结合状态监测数据核实。
5. **建议开展根因分析的对象与理由**：点名设备，理由只引用统计结果（次数、间隔、涉及台数），**不写原因推测**。
6. **数据质量问题**：无信息量记录条数、部位缺失条数、区间外被跳过条数，以及这些缺口对结论的影响。

### 用词要求

| 场景 | 应写 | 不得写 |
|---|---|---|
| 重复判定 | 「区间内机封部位故障 4 次，达到同部位阈值 2 次（规则 D1）」 | 「机封老是坏」 |
| 相似依据 | 「现象描述 bigram 相似度 0.59，部位同为机械密封」 | 「都是机封失效」 |
| 原因 | 「建议组织专项分析确定根本原因」 | 「原因是备件质量问题」「是安装不对中造成的」 |
| 共性 | 「2 台同型号换热器均报管束内漏，属共性线索」 | 「该型号换热器存在设计缺陷」 |
| 间隔 | 「间隔由 90 天缩短至 30 天，建议结合状态数据核实」 | 「设备寿命已到，需整体更换」 |
| 无信息记录 | 「2 条记录现象未填具体内容，未参与判定，需补填」 | 把它们算进重复次数，或据此说「还不止这些」 |
| 数字 | 引用 `repeats.json` | 自行统计或估算 |

### 硬约束

- **不得给出具体根本原因结论**。只能说「需要分析」「建议组织专项分析」，不能说是什么原因。
- **不得声称相似即同因**。必须把 matchBasis 摆出来，让设备员自己判断。
- **不得据无信息描述判定重复故障**。这类记录只出现在第六节。
- **不做可靠性建模**。MTBF、失效率、威布尔分布这类结论超出本技能范围。
- **不评价维修质量与承修单位**，不把重复故障归因于某个班组或某家承包商；承包商考核由安全环保部门归口。
- **数字一律引用 `repeats.json`**，不得自行统计。

## 八、下游衔接

- 需要立即处理的重复故障 → `defect-intake-grading` 登记缺陷、`work-order-generator` 出维修通知单草稿
- 需要跟踪在途工单 → `work-order-tracker`；检索历史同类故障案例 → `failure-case-retrieval`
- 需要纳入检修计划 → `maintenance-demand-rollup`
- **备件消耗异常的设备可能来自 `05-备品备件与物资/spare-parts-consumption-analysis`**：该技能的消耗排行与本技能的故障频次排行可互相印证。同一台设备既在故障频次前列、又在备件消耗前列，是优先安排根因分析的强线索；反之，若消耗高但本技能未识别出重复故障，多半是故障现象填写质量不足，应先补数据。
- 重复故障涉及设备事故 → `failure-investigation-assistant` 或厂内事故调查流程，本技能不适用
- 建议开展根因分析的清单报车间设备主任 / 公司设备管理部门（机动部/设备部），分析结论由设备工程师出具
