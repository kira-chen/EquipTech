# 交付自检清单

运行脚本后、交付前逐项核对。

## 脚本执行
- [ ] 末行 JSON 的 `ok` 为 `true`；若为 `false`，已把 `error` 原文告知用户并终止，**未手工统计频次**
- [ ] `warnings` 已逐条告知用户，未隐去任何一条
- [ ] `repeats.json` 与 `repeats.md` 均已生成

## 统计区间
- [ ] 报告中注明了**实际统计区间与天数**（起止日期 + 共 N 天）
- [ ] 区间在建议的 6~12 个月范围内；超出范围时已把 warning 中「会漏判 / 会掺入已整改的历史问题」的提示转达用户
- [ ] 未传 `--from` 时已说明起始日按默认「一年内」口径推算
- [ ] 若区间跨越大检修节点，已向用户确认是否需要按大检修后重新起算
- [ ] 多文件输入时已核对 `meta.fileStats`，被跳过的文件已告知用户

## 判定阈值与依据
- [ ] 报告中写明了本次使用的阈值（同部位 ≥N 次、同现象 ≥M 次、相似度阈值）
- [ ] 采用默认口径（同一设备同一部位一年内 ≥2 次）时已明确标注，厂内有正式口径时已按用户口径并注明
- [ ] 带 SAP 损坏代码的记录已说明按代码归类，代码不同的未被文本硬凑到一组
- [ ] 每一条重复判定都带规则号（D1~D4、U1），可对照 `references/detection-rules.md` 复核
- [ ] **每一条判定的 `matchBasis` 都已呈现给用户**，写明是文本相似度多少、部位是否相同、现象类型是否相同

## 无信息描述（关键）
- [ ] 无 SAP 代码且故障现象为空或只写「故障」「坏了」的记录，全部出现在第六节 `uninformative` 中
- [ ] **这些记录未被计入任何重复故障组、共性故障组或间隔统计**
- [ ] 已向用户说明「有 N 条因现象无信息量未参与判定，补填后重新统计才完整」
- [ ] 未以这些记录的条数暗示重复故障的严重程度

## 相似判定的表述
- [ ] 已说明相似度是**文本与字段的机械匹配**，不代表各次故障同因
- [ ] **未出现「都是同一个问题」「反复失效说明是同一原因」这类表述**
- [ ] 共性故障只写「共性线索，建议扩展排查」，未断言型号缺陷或设计问题

## 根本原因（硬约束）
- [ ] **全文未给出任何具体根本原因结论**（如「轴承质量问题」「不对中」「设计缺陷」「操作不当」）
- [ ] 只写「建议组织专项分析确定根本原因」
- [ ] 间隔缩短只写统计现象，未断言「已进入劣化期」「寿命到期」
- [ ] 未评价维修质量、承修单位或班组

## 数字一致性
- [ ] 报告中每个数字都能在 `repeats.json` 的 `counts` 中找到对应，未自行统计
- [ ] 只有 1 次故障的设备，平均间隔显示「—」，**未出现 0**
- [ ] 区间外被跳过的记录数已告知用户

## 声明行
- [ ] **`repeats.md` 中保留了两行声明原文**：「本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。」与「本结果为频次统计与文本相似匹配，重复故障的根本原因须由设备工程师组织专项分析确定」
- [ ] 未出现旧称「机动处」「EAM」；公司层写「公司设备管理部门（机动部/设备部）」

- [ ] 六段结构齐全：总体情况、同设备重复故障与建议、同型号共性问题、故障间隔缩短设备、建议开展根因分析的对象与理由、数据质量问题
