# 重复故障识别（repeat-failure-detector）

面向中石化体系炼化厂车间（运行部）设备员与设备工程师，从 SAP PM 通知单/订单导出或车间故障记录中识别重复发生的故障，提示哪些设备需要做根因分析而不是反复修复。**频次统计、相似判定与阈值比对一律由脚本完成，模型只负责解读；不得手工归类或断言根本原因。**

## 适用条件
- 用户说"这台设备老坏 / 重复故障有哪些 / 故障频次统计 / 哪些该做根因分析 / 修得最多的设备"，并给出（或即将给出）工单台账、故障记录或 SAP 通知单/订单导出（按装置分成多个文件也可以，逗号分隔一起传）。
- 支持两个维度：同一设备的重复故障、同型号或同类设备的共性故障。
- **车间设备员可做**：重复故障筛查、频次统计、提出根因分析建议清单并报车间设备主任/公司设备管理部门（机动部/设备部）。**由 XX 归口**：根因分析结论、失效机理判定与设备事故定性由设备工程师、公司设备管理部门与事故调查流程负责。
- 不适用：单次异常的现场初判；设备事故的正式调查；可靠性建模与寿命分析。

## 前提条件
- 输入：一个或多个 `.xlsx`（或同结构 CSV 目录，UTF-8 或 GBK），含工作表「工单台账」「故障记录」或「通知单」，字段见 `references/input-spec.md`。支持 SAP PM 通知单导出列名（通知单、功能位置、设备、设备描述、对象部件、损坏代码、原因代码、通知单短文本、通知日期）。
- 必填信息：车间名称。可选：统计区间（默认截止当日、往前 12 个自然月，即"一年内"）、重复判定阈值（默认同设备同部位 ≥2 次、同现象/同代码 ≥2 次）、相似度口径、设备台账（用于按型号归类）。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得手工统计频次。**

## 数据获取（MCP）

平台接入了业务系统 MCP 服务时，按下表调用工具取数，不再请用户上传导出文件；未接入时按操作步骤请用户提供系统导出文件。工具全部只读，不在业务系统里创建或修改任何单据。

| 服务 | 工具 | 参数 | 交给脚本 |
|---|---|---|---|
| 设备资产管理 | `get_failure_history` | `for_skill=repeat-failure-detector`；`workshop`：车间（只看单台设备时改用 `tag`：位号） | `--input`（目录 A） |
| 设备资产管理 | `get_equipment_ledger` | `workshop`：车间 | `--ledger`（目录 B） |

取数后：

1. 工具返回下载链接（60 分钟内有效，过期重新调用）。csv 按原文件名放进新建的空目录，不改文件名，不与其他技能的文件混放；表中目录字母相同的放同一个目录，不同字母分开放，把目录作为“交给脚本”一列的参数值。
2. 两个工具都要带 `workshop`（与 `--workshop` 相同）：脚本的 `--workshop` 只写报告标题、不筛选记录，不带时其他车间的故障会算进本车间报告，同型号共性故障也会跨车间归组。

## 操作步骤
1. **确认统计区间与判定阈值** —— 默认按"一年内"（截止日往前 12 个自然月）；区间过短会漏判，过长会掺入已整改的历史问题，跨大检修节点时建议按大检修后重新起算。判定阈值按 `references/detection-rules.md`（默认同一设备同一部位一年内 ≥2 次），用户指定厂内口径时以用户为准并注明。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/detect.js" --input "<xlsx路径[,xlsx路径2,...]>" --workshop "<车间名>" --to <YYYY-MM-DD> --out "<工作目录>/重复故障"
   ```
   可选：`--from <起始日期，默认 --to 往前 12 个自然月>`、`--min-count <同部位重复次数阈值，默认 2>`、`--ledger "<设备台账xlsx>"`（按型号归类，支持 SAP 技术对象列名）、`--by <equipment|model|part>`、`--similarity <现象相似度阈值，默认 0.55>`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（缺表/缺列/故障现象描述过于笼统/时间超出区间/位号缺失/某文件被跳过等）。脚本用法详见 `scripts/README.md`。
   - 故障现象字段为空或只写"故障""坏了"这类无信息描述、且无 SAP 损坏代码：归入 `uninformative` 单列一节并 warning，**不得据此判定为某类重复故障**。
   - 记录带 SAP 损坏/故障代码时按代码归类（代码相同即同组、不同即不同组）；无代码时按文本与部位字段的机械匹配，脚本在 `matchBasis` 中给出判定依据，**模型不得声称相似即同因**。
3. **读取 repeats.json** —— 从 `<输出目录>/repeats.json` 获取：`byEquipment`（同设备重复故障组：位号、SAP 设备编号、次数、故障间隔、现象/代码列表、匹配依据）、`byModel`（同型号共性故障）、`topFrequency`（故障频次排行）、`shorteningInterval`（故障间隔缩短的设备）、`uninformative`、`counts`、`meta.fileStats`（逐文件行数）。
4. **撰写"重复故障分析"** —— 读 `references/detection-rules.md` 的表述口径，撰写 250~450 字，按"总体情况 → 同设备重复故障与建议 → 同型号共性问题 → 故障间隔缩短设备 → 建议开展根因分析的对象与理由 → 数据质量问题"结构，替换 `repeats.md` 中 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字。**次数、间隔一律引用 repeats.json；不得给出具体根本原因结论，只提示需要分析。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `repeats.md` 与 `repeats.json`。**必须保留两行声明："本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。"与"本结果为频次统计与文本相似匹配，重复故障的根本原因须由设备工程师组织专项分析确定"。**

## 预期结果
- `repeats.md`：重复故障识别报告，含统计概览、同设备重复故障、同型号/同类设备共性故障、故障频次排行、故障间隔缩短设备、故障现象无信息量清单、重复故障分析七个部分，开头带两行声明。
- `repeats.json`：分组与统计结果；`summary.json`：脚本末行摘要。
- 交付时向用户说明：统计区间（含是否默认推算）与阈值、数据文件数、识别出的重复组数、建议做根因分析的设备数、带 SAP 代码的记录占比、数据质量问题、脚本 warnings（如有）。

## 不适用范围
- 不给出故障根本原因结论，不做失效机理判定。
- 不做设备更新改造决策与选型建议。
- 不评价维修质量与承修单位水平，不用于考核。
- 不替代可靠性专业的 RCM、FMEA 等分析方法。
- 默认阈值与"一年内"区间为常见口径，厂内可配置。
