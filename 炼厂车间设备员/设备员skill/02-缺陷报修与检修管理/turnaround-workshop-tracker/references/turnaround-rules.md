# 大检修跟踪口径与表述规范（中石化炼化厂）

## 零、最高原则：脚本不替指挥部拿主意

本技能只做**车间侧的进度呈现与缺口暴露**。所有滞后天数、工期影响都是**按计划节点的测算值**，不是结论。

> **滞后天数与工期影响均基于计划节点测算，最终以指挥部判定为准。**

这句声明行由脚本写入 `progress.md` 头部、关键路径滞后节与滞后节末尾，并固化在 `progress.json` 的 `meta.disclaimer`、`overall.disclaimer` 与每个 `lagging` 条目的 `disclaimer` 中。**撰写进度说明时凡提到滞后影响工期，必须原样带出这句话，不得删改、不得弱化成「预计影响 X 天」。**

## 一、状态枚举（七态）与大检修节点

大检修关键节点（《炼化企业设备管理技术规定》与厂内大检修管理制度，节点名以厂内为准）：开工前条件确认（设备交出、盲板、作业票）→ 施工 → **三查四定** → **中交（中间交接）** → 试压 / 试运 / 投料前条件确认 → **开工（开车）**。

项目状态只认七态：**未开工、施工中、已完工、已中交、已开工、已中止、取消**（同义词见 `input-spec.md`）。

| 状态 | 含义 | 不得混用为 |
|---|---|---|
| 已完工 | 施工完工，尚未中交 | 已中交 |
| 已中交 | 中间交接：检修完工、三查四定问题关闭或经指挥部确认留项后交付工艺 | 已完工 |
| 已开工 | 中交后装置 / 设备开工（开车投用） | 施工中（"已开始施工"应填施工中） |

脚本对「已开工」出现时 warning 提示语义；三者在总体表分列，`counts.finished` 为三者之和。

取值不在枚举内（含空值）时：warning 指明 sheet、行号、项目编号与台账原文；归入 `unknownStatus` 单列；不参与总体加权、滞后判定、开工判定任何一项。**禁止**把「挂起」「待定」「已上报」映射到最接近的状态。取消项目如实列入项目总数，但不参与加权与滞后判定。

## 二、完成比例：三条铁律

### 1. 为空 → 显示「—」，按状态给定性进度

| 状态 | 定性进度表述 |
|---|---|
| 未开工 | 按状态为「未开工」，未填报完成比例 |
| 施工中 | 按状态为「施工中」，已开工但未填报完成比例 |
| 已完工 | 按状态为「已完工」，未填报完成比例 |
| 已中交 | 按状态为「已中交」（中间交接），未填报完成比例 |
| 已开工 | 按状态为「已开工」（中交后开车投用），未填报完成比例 |
| 已中止 | 按状态为「已中止」，未填报完成比例 |

**绝对禁止**：按 0 计；按工期线性推算；用应有进度回填；按状态推「未开工就是 0、已完工就是 100」。

### 2. 超出 0~100 → 置 null，不截断

warning + `percent` 置 `null`，`percentOutOfRange` 为 `true`，台账原文留在 `rawPercent`。**绝对禁止**截断或自行换算。

### 3. 与状态矛盾 → 单列，不修正任一字段

相容关系：未开工 = 0；施工中 0 ≤ 比例 < 100；已完工 / 已中交 / 已开工 = 100；已中止 / 取消不校验。越出即矛盾：warning + `inconsistent` 单列 + 列入 `undetermined` + 不参与加权与滞后判定。**绝对禁止**改任一字段或替设备员取舍。

正确写法：「T-09 状态填报为『未开工』但完成比例填报 50%，两项互相矛盾，脚本未作修正，需回项目清单核实后重跑。」

## 三、总体完成比例：按工期加权

```
总体完成比例 = Σ(工期 × 完成比例) ÷ Σ(工期)
```

参与加权须**同时满足**：状态在六个有效态内（未开工 / 施工中 / 已完工 / 已中交 / 已开工 / 已中止）、无状态-比例矛盾、工期为有效正数、完成比例非空。不满足的在 `overall.excludedNoDuration / excludedNoPercent / excludedInconsistent` 单列。报告必须同时给出**加权样本占比**（X / Y）。没有样本时为 `null`（显示「—」），**不输出 0%，也不退化成按项目数简单平均**。

**日历进度**（大检修计划期已过百分比）仅作参照，**不得据此回填完成比例**，也不得据此判滞后。

## 四、滞后判定：三类口径，第三类可选

滞后阈值默认 1 天，`--lag-days` 可调。按以下优先级取第一个命中的：

| # | 类型 | 判定 | 滞后天数 | 是否默认 |
|---|---|---|---|---|
| ① | 已过计划完工日未完工 | 状态在未开工 / 施工中 / 已中止，且统计日 > 计划完工 | 统计日 − 计划完工 | 是 |
| ② | 超计划开工日未开工 | 状态为未开工，且统计日 − 计划开工 ≥ 阈值 | 统计日 − 计划开工 | 是 |
| ③ | 完成比例落后应有进度 | 实际比例 < 应有进度，且折算滞后天数 ≥ 阈值 | (应有 − 实际)÷100 × 工期 | **仅 `--linear-check`** |

**应有进度**按计划开工~计划完工的日历线性推算，封顶 100%、保底 0%，只在 `--linear-check` 启用时计算；它**只用于滞后判定，绝不回填完成比例**。线性推算假设进度随日历均匀推进，与大检修实际的"前慢后快"不一定相符，所以默认不启用，由用户决定是否开启，报告抬头注明是否启用。

**不做滞后判定的情形**（进 `undetermined`）：状态不在枚举内、状态与完成比例矛盾、计划完工早于计划开工、计划节点缺失；启用 `--linear-check` 时完成比例未填报的在办项（不按 0 也不按推算值判）。

每个滞后条目都带 `basis`（测算依据）与 `disclaimer`。

## 五、关键路径

`--critical "T-01,T-05"` 指定关键路径项目编号，脚本**不自行判断**。关键路径滞后项归入 `criticalLagging`，在 md 中单独成节并置于滞后节最前，标题带【注意】，表中用 ★。

正确表述：「T-02 常压炉炉管更换位于关键路径，已过计划完工日 2 天仍未完工，该项滞后直接影响大检修总工期，基于计划节点测算，最终以指挥部判定为准。」**禁止**替指挥部给出"总工期将延后 X 天"的结论。

## 六、开工条件与材料缺口

`readyGap` 与 `materialGap` 分别单列，**互不合并**；`judged: null` 的条目写明「未判定（取值缺失或无法识别）」，**绝不按已具备或已到货处理**。缺可选表时对应章节写「未提供 XX 数据」，总体表显示「未提供」而非 0。人员到位只做呈现；计划或到位人数任一缺失 → 缺口「—」，是否缺员「未判定」。

## 七、三查四定问题

三查：查设计漏项、查未完工程、查工程质量；四定：定任务、定人员、定时间、定措施。中交前三查四定问题应关闭，或经指挥部确认留项。

| 判定 | 口径 |
|---|---|
| 关闭状态 | 已关闭 / 已整改 / 已完成 / 已销项 → 已关闭；未整改 / 未关闭 / 整改中 → 未关闭（否定前缀先判）；其它（如「已上报」「待确认」之外的无法识别值、空）→ **未判定，不按已关闭** |
| 四定 | 整改措施（定任务 / 定措施）、责任人（定人员）、整改期限（定时间）任一缺失 → 四定不全，写明缺哪几定 |
| 超期 | 未关闭且整改期限早于统计日 → 超期，给超期天数 |
| 项目关联 | 项目编号在清单中不存在 → warning，问题保留但不关联 |

`byProject.tcfdOpen` 为该项目未关闭（含未判定）问题数，中交前应为 0 或有留项批准。进度说明里写：「三查四定问题 6 项，未关闭 3 项（其中超期 1 项），关闭状态未判定 1 项，四定不全 1 项（Q-03 缺措施、责任人、期限，为中交留项，需指挥部确认）」。**不得**把未判定写成已关闭。

## 八、日进度（`--prev`）

增量 = 本日完成比例 − 上一日完成比例；任一日未填报 → `null`，**绝不按 0 增量**。`statusChanged` 标记状态变更；`nodeChanged` 单列本日到达已中交 / 已开工节点的项目；`stagnant` 为施工中 / 已中止但比例未变；`dropped` 为上一日有、本日缺的项目，**绝不按完工或取消处理**。

## 九、分析段表述规范

撰写 250~400 字，结构固定为六段：

1. **总体进度**：统计日期、项目总数与各状态分布（已完工 / 已中交 / 已开工分列）、总体完成比例（注明加权样本占比）、日历进度对照、是否启用线性核对。
2. **滞后项目与影响**：关键路径优先，逐项写滞后类型、天数、测算依据、责任方；提到工期影响必须带免责声明。
3. **资源与条件缺口**：开工条件未具备与未判定各几项、材料未到货与未判定各几项、人员缺员情况。
4. **三查四定问题**：未关闭 / 超期 / 未判定 / 四定不全各几项，点名中交前须关闭或批准留项的。
5. **本日完成情况**：有 `--prev` 时写进度增量、本日中交 / 开工节点、零进度项目、新增与缺失项目；无 `--prev` 时写「未提供上一日进度，本次不做日对比」。
6. **明日重点**：需优先跟进的项目与责任方，以及项目清单需补录的字段。

### 用词要求

| 场景 | 应写 | 不得写 |
|---|---|---|
| 滞后影响 | 「T-02 滞后 2 天，基于计划节点测算，最终以指挥部判定为准」 | 「大检修总工期将延后 2 天」 |
| 状态-比例矛盾 | 「T-09 状态『未开工』与完成比例 50% 互相矛盾，脚本未作修正，需核实」 | 「T-09 实际应为施工中，进度 50%」 |
| 比例未填报 | 「T-12 完成比例未填报，按状态为施工中」 | 「T-12 进度约 62%（按工期推算）」 |
| 中交 / 开工 | 「T-20 已中交（中间交接），尚有 1 项三查四定留项待指挥部确认」 | 「T-20 已完工」 |
| 三查四定未判定 | 「Q-06 整改状态『已上报』无法判定是否关闭，不能视为已关闭」 | 「Q-06 基本已关闭」 |
| 滞后原因 | 「备注记录为『塔盘到货晚，人员未满编』」「原因未记录」 | 「估计是承修单位窝工」 |
| 关键路径 | 「按 --critical 指定的关键路径项目」 | 自行判断「这个塔应该是关键路径」 |
| 数字 | 引用 progress.json 的 counts / overall / lagging / tcfd | 自行统计或估算 |

### 硬约束

- **不修正任何台账字段**；**不推测滞后原因**；**不判定工期能否按时完成**；**不调整计划节点、不重排工序、不做资源平衡**；**不替指挥部认定关键路径**；**不把三查四定未判定写成已关闭**；**数字一律引用 progress.json**。
