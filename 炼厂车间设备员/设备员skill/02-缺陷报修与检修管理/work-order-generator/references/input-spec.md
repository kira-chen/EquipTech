# 输入规格：维修通知单草稿生成

## 三条输入路径

### 1. 接上游 defect-intake-grading（推荐）

```bash
node scripts/workorder.js --defect "<defects.json 路径>" \
  --applicant "<报告单位>" --due 2026-09-28 \
  --ledger "<设备台账xlsx>" --history "<历史维修记录xlsx>"
```

`--defect` 传 `defect-intake-grading` 产出的 `defects.json`，脚本直接读其中 `defects` 数组，带出缺陷登记号、位号、SAP 设备编号（`equipNo`）、功能位置（`funcLoc`）、设备名称、部位、描述、介质、现象类型、缺陷等级（A/B/C，兼容旧 I~IV）、定级依据与规则号、发现时间（作要求开始）、发现人（作报告人）。**一条 JSON 里有几条缺陷就出几张草稿。** 上游批量登记时带出的原记录编号 `sourceNo` 且 `sourceNoKind` 为 `notification`（来源是通知单号列）的，作「已有通知单号」带出；`sourceNoKind` 为 `defect`（缺陷编号）的不算。 上游等级为「未判定」的条目，优先级与通知单类型同样未判定。

也接受裸的缺陷数组 `[{...}]` 或单条对象 `{...}`。

### 2. 文字描述

```bash
node scripts/workorder.js --defect "<一段故障描述>" --tag "<功能位置>" \
  --applicant "<报告单位>" --due 2026-09-28
```

文字描述路径**必须用 `--tag` 指定功能位置**（通知单不能挂空功能位置），脚本从描述里识别现象类型，介质、等级等字段留空。

判别规则：`--defect` 的取值是一个存在的文件时按 JSON 读，解析失败**报错终止**，不静默当成文字描述；不是文件路径时按文字描述处理。

### 3. 批量缺陷表 / SAP 通知单导出

```bash
node scripts/workorder.js --input "<缺陷记录xlsx>" --applicant "<报告单位>" --due 2026-09-28
```

## 缺陷记录工作表（`--input`）

sheet 名匹配「缺陷记录」「缺陷」「记录」「通知单」。

| 列名 | 必需 | 说明 |
|---|---|---|
| 位号 | 是 | SAP 功能位置；为空的行跳过并 warning |
| 缺陷描述 | 是 | 为空的行跳过并 warning，**不凭位号编造故障现象**；SAP「通知单短文本」可直接用 |
| 设备编号 | 否 | SAP 8 位设备流水号，**不是位号**，单独成列写入草稿；可由设备台账带出 |
| 设备名称 | 否 | 可由设备台账带出（SAP「设备描述」） |
| 缺陷部位 | 否 | SAP「对象部件」可直接用 |
| 缺陷编号 | 否 | 缺陷登记号，写入草稿便于与缺陷台账对账 |
| 通知单号 | 否 | 系统里已有的 SAP 通知单号（如 `get_notifications` 导出）：原样带到「已有通知单号」列（`orders[].existingNotifNo`），md 注明「系统已存在，勿重复创建」；「通知单号(SAP生成)」列仍留空 |
| 等级 | 否 | A/B/C（兼容 I~IV），用于推默认优先级；缺失且未指定 `--priority` 时优先级判未判定 |
| 介质 | 否 | 可由设备台账带出 |
| 发现时间 | 否 | 作要求开始日期；SAP「通知日期」可直接用；缺失时取生成当日 |
| 发现人 | 否 | 作报告人；SAP「报告人」可直接用 |

## 设备台账（`--ledger`，强烈建议提供）

sheet 名匹配「设备台账」「台账」「设备清单」「技术对象」。用于带出 **SAP 设备编号、规格型号、安装位置、所属专业、投用日期、介质**。

| 列名 | 必需 | SAP 技术对象导出常见写法 |
|---|---|---|
| 位号 | 是 | 功能位置 |
| 设备编号 | 否 | 设备 |
| 设备名称 | 否 | 设备描述 |
| 规格型号 | 否 | 型号编号 |
| 安装位置 | 否 | 工厂区段 |
| 专业 | 否 | 专业类别；有值时优先于位号推断 |
| 投用日期 | 否 | 开始日期 / 建造年份；无法解析时 warning + 留空 |
| 介质 | 否 | |

**位号不在台账中时**：warning，设备编号/规格型号/安装位置/投用日期一律留空标「待补充」，列入信息缺口清单。**脚本绝不按设备名推测规格型号**——「进料泵A」推不出 ZA50-250。

**未提供 `--ledger` 时**：warning，全部设备信息标「待补充」，不中断。

**位号与设备编号不混**：台账只有「设备编号」列而没有功能位置列时，报「缺少列: 位号」warning，不把 8 位流水号当作位号。

## 历史维修记录（`--history`）

sheet 名匹配「维修记录」「检修记录」「历史维修」「订单」「记录」。用于附该设备近 N 次维修背景，默认近 3 次（`--history-n` 可调）。

| 列名 | 必需 | SAP 订单历史导出常见写法 |
|---|---|---|
| 位号 | 是 | 功能位置；为空的行跳过并 warning |
| 维修日期 | 否 | 基本开始日期 / 实际结束日期 / 技术完成日期；用于排序取近 N 次，无法解析时 warning + 排在有日期的之后 |
| 维修内容 | 否 | 订单描述 / 短文本 |
| 承修单位 | 否 | 主工作中心 / 工作中心 |
| 工单号 | 否 | 订单 / 订单号，作为原订单号写入 |

**未提供 `--history` 时**：该章节写「未提供历史维修记录」。
**提供了但该位号无记录时**：warning，章节写「历史维修记录中无位号「XXX」的记录」。

两种情况下都**绝不编造检修履历**，历史章节只引用表里实际存在的记录，逐条带日期、内容、工作中心、原订单号。

## 必填参数

| 参数 | 说明 |
|---|---|
| `--defect` 或 `--input` | 缺陷来源，二选一，都没有则报错 |
| `--applicant` | 报告单位（车间），**缺失报错**，通知单必须写明报告单位 |
| `--due` | 要求结束日期 YYYY-MM-DD，**缺失或非法日期报错** |

`--due` 早于当前日期时：warning + 草稿标注，**仍正常生成**，由用户决定是否改期。

## 会被跳过的行

| 情形 | 处理 |
|---|---|
| 位号为空 | 跳过 + warning（带 sheet 名与行号） |
| 缺陷描述为空 | 跳过 + warning |
| 合计/小计/总计行 | 跳过 + warning |
| 整行空白 | 静默跳过 |

## 产出

| 文件 | 内容 |
|---|---|
| `notifications.json` | 逐张草稿（设备信息、故障描述、通知单抬头、归口建议、优先级、历史摘要）、missingInfo、undetermined、counts、meta |
| `notifications.md` | 三节报告：通知单草稿清单概览、通知单草稿正文、信息缺口清单 |
| `notifications.csv` | SAP 通知单草稿列，带 BOM，通知单号列留空由系统生成；输入已带通知单号的写在「已有通知单号」列 |
| `summary.json` | 末行摘要落盘 |
