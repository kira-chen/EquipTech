# 通知单要素清单与追问话术

## 必需要素

| 要素 | 为什么必需 | 缺失时的追问 |
|---|---|---|
| 功能位置（位号） | 通知单必须挂到具体技术对象，不能挂空功能位置 | 「这张通知单报哪台设备？功能位置是多少？」 |
| 故障现象 | 决定故障代码建议与专业归口 | 「具体什么现象？漏、响、振动还是指示不准？」 |
| 报告单位 | 通知单的报告方，脚本缺此参数直接报错 | 「这单以哪个车间/运行部的名义报？」 |
| 要求结束日期 | SAP 通知单的要求结束，脚本缺此参数直接报错 | 「希望什么时候前处理完？」 |

## 可选要素（缺了照常出草稿，但会列入信息缺口清单）

| 要素 | 什么情况下要问 | 追问 |
|---|---|---|
| **SAP 优先级** | 缺陷等级也拿不到时**必须问**，否则判未判定 | 「这单按什么优先级报？1 非常高、2 高、3 中还是 4 低？」 |
| 通知单类型 | 厂内 M1/M2 定义与默认映射不同时 | 「你们厂维修申请是 M1 还是 M2？」 |
| 建议承修单位 | 车间已定好承修方时 | 「承修单位定了吗？还是等计划员派？」 |
| 停机需求 | 现象涉及解体、用火、盲板抽堵时 | 「这活需要停机吗？要不要联系工艺做切除？」 |
| 对象部件 | 便于承修单位现场定位 | 「具体哪个部位？机封、轴承、法兰还是壳体？」 |
| 报告人 | 批量表没有发现人列时 | 「报告人写谁？」 |

## 可以不问的（有台账就自动带出）

SAP 设备编号、规格型号、安装位置、所属专业、投用日期、历史维修记录——这些**一律从台账读**，不要向用户口头确认后填进草稿。用户说得出的，也要以台账为准。

- 有台账、位号查得到 → 自动带出。
- 有台账、位号查不到 → 标「待补充」，可以问用户「台账里没查到这个功能位置，是新上的设备还是位号写法不同？」
- 没台账 → 提示用户「有 SAP 技术对象导出的话一起给我，设备编号、规格型号和投用日期能自动带出，不然草稿上这几项是空的」。

## 追问原则

1. **一次性列出所有缺项**，不要挤牙膏式逐个追问。
2. **不得替用户决定优先级与要求结束日期**。这两项是车间的管理决定，不是技术推断。缺陷等级能推出优先级时要说明「这是按 A/B/C 级缺陷的默认口径推的（A→1、B→2、C→3），车间可以改」。
3. **不得凭设备名猜规格型号、备件型号**。「那台泵的机封是不是 104 型的」——不知道就是不知道，写「待补充」。
4. **不得编造历史检修履历**。没有历史维修记录表就写「未提供历史维修记录」，不要用「这台泵去年大修过」之类的印象填。
5. **不给工时与备件**。用户问「工时你给估一个」，答复「工时由承修单位在工单（订单）里填，通知单不填」。
6. 生成的是**通知单草稿**，交付时必须说明「本通知单草稿由车间设备员核对后在 SAP 中创建，通知单号由系统生成；维修工单（订单）、工时与备件由计划员或承修单位编制，本草稿不替代审核派发」，不要说成「已开工单」「已派工」。

## 常见口语化表述与结构化对应

| 用户可能这样说 | 结构化 |
|---|---|
| 「把 QX-20260921-001 那条转个通知单」 | `--defect defects.json`，脚本按缺陷登记号带出全部字段 |
| 「这几条一起报了」 | 多条缺陷的 defects.json 或 `--input` 批量表 |
| 「越快越好」 | 追问是否按「1 非常高」，不要自行按 1 |
| 「下周之前弄完」 | 追问具体日期，`--due` 要 YYYY-MM-DD |
| 「让检修一班干」 | `--vendor 检修一班`（仅建议，派工由厂内流程定） |
| 「报成故障报告」 | `--notif-type M2`（厂内目录为准） |
| 「工时你给估一个」 | 说明工时由承修单位在工单中填写，草稿不给数值 |
