# 检修需求汇总口径

> 依据《中国石化设备管理规定》《炼化企业设备管理技术规定》中检修计划申报（车间申报 → 公司设备管理部门审核批复）的流程口径整理，不转述具体数值。**本表为默认参考口径。** 各厂申报表格与要求不同，厂内有正式规定时以厂内为准，并在交付时注明采用的口径来源。申报对象统一写「公司设备管理部门（机动部/设备部）」，旧称「机动处」不用。

## 一、四类来源的合并口径

汇总范围包含四类，**逐条平铺，不跨来源自动合并**：

| 来源 | 纳入什么 | 不纳入什么 |
|---|---|---|
| 未闭环缺陷 / SAP 通知单 | 状态为未闭环（OSNO/NOPR、待处理、处理中……）的条目 | 已闭环（NOCO/CLSD、已消缺、已验收）的；**已完成/TECO 为待验收，本期不重复申报** |
| 未闭环工单 / SAP 订单 | 状态为 CRTD/REL/PCNF 等未闭环的条目 | 同上 |
| 周期性检修项 | 到期或本周期应做的预防检修项 | 未加 `--include-cyclic` 时一律不纳入 |
| 隐患整改项 | 隐患台账中未整改且有位号（设备类）的条目 | 已销号/已整改的；无位号的管理类隐患 |

状态无法判断是否闭环的记录**不按未闭环纳入**，也不按已闭环剔除，列入「未判定项」待核实。

同一台设备在缺陷台账挂一条、工单台账又开一张，是车间最常见的重复形态。脚本**保留两条**、只在「疑似重复」里提示，由设备员确认后再决定是否合并申报——**脚本绝不自动合并，也绝不自动剔除**。

## 二、依据要求（硬性）

**每项需求必须注明依据**，即对应的缺陷编号或通知单号 / 工单号（订单号） / 周期项编号 / 隐患编号。

- 有依据 → 进正式清单，`basis` 字段同时记录来源工作表与行号，可回溯
- **无依据 → 一律进「建议核实区」（`noBasis`），不得进正式上报清单**

理由：上报给公司设备管理部门（机动部/设备部）的每一条都要能对得上台账或 SAP 原始记录，否则审核时无从核实，也容易被质疑是车间"凑项目"。补齐编号后重新运行即可进正式清单。

## 三、优先级与检修类别

| 优先级 | 来源判据 |
|---|---|
| 紧急 | 缺陷等级 A 级（重大）/ SAP 优先级 1 / 旧 I 级 / 含「紧急」「特急」；重大隐患 |
| 高 | 缺陷等级 B 级（严重）/ SAP 优先级 2 / 旧 II 级 |
| 中 | 缺陷等级 C 级（一般）/ SAP 优先级 3 / 旧 III 级；一般隐患 |
| 低 | SAP 优先级 4 / 旧 IV 级 / 含「轻微」 |
| **未判定** | **工单无等级且无优先级（不按「高」默认）；周期性检修项（不按「中」默认，按应完成日期安排）；隐患等级为「A/B/C 级」「公司级/厂级/车间级」等管理层级写法（不直接映射）；等级栏为空或无法识别** |

排序规则：优先级升序（未判定排最后）→ 需停机项在前 → 应完成/计划结束日期 → 位号字典序。序号按排序后连续编号，**序号不代表台账顺序**。

优先级只是车间申报时的建议轻重缓急，**实际排期以公司设备管理部门（机动部/设备部）结合全厂停工窗口批复为准**。

检修类别（建议）按中石化分级 装置大检修（停工检修）/ 日常维修 / 抢修 / 专项：

| 检修类别 | 判据 |
|---|---|
| 抢修 | 工单类型 PM03/抢修；A 级缺陷 |
| 日常维修 | 工单类型 PM01/日常维修；B/C 级缺陷 |
| 计划检修 | 工单类型 PM02/计划检修/定期；周期性检修项 |
| 专项（隐患整改） | 隐患台账来源 |
| 专项（技改技措） | 工单类型含「专项/技改/技措」 |

PM01/PM02/PM03 编码为常见口径，厂内可配置；装置大检修项目另走大检修项目计划，不在本技能月度申报范围。

## 四、停机需求判定

「是否需停机」三态，**绝不二值化**：

| 取值 | 处理 |
|---|---|
| 是 | 进「需停机项」专列，工期计入停机窗口核对 |
| 否 | 不进专列 |
| **空 / 无法识别** | **记「未填写」，在「是否需停机未填项」中单列**，不计入需停机汇总，也不按不需停机处理 |

停机窗口核对（`--window`）：只有在窗口说明能提出天数、且所有需停机项都填了预计工期时才给出结论；否则一律「未判定」并 warning。**不得因为算不出来就写"不冲突"。**

## 五、备件到位口径（最易出错）

上报表里的「备件是否到位」栏直接影响设备部排期。填错的代价是：到了检修窗口才发现备件没有，白占一个停机窗口。

**铁律：未提供备件库存表时，该列一律写「未核实」，绝不写「有库存」「已到位」或留空。**

| 情形 | 应写 | 绝不能写 |
|---|---|---|
| 未提供 `--spare` | 未核实 | 有库存 / 已到位 / 空白 |
| 提供了表但查不到该型号 | 未核实 | 无库存 / 有库存 |
| 库存数量栏无法解析 | 未核实 | 按 0 当作无库存 |
| 库存 ≥ 需求 | 到位（库存 N） | — |
| 库存 < 需求 | 不足（库存 N / 需 M） | 到位 |
| **有库存但需求数量未填** | **未判定（库存 N，需求数量未填）** | 按 1 件算成「到位」 |

「未核实」「未判定」和「不足」都计入 `spareGap` 备件缺口，但含义不同：**「不足」是已核实确实缺货，「未核实」是还没查，「未判定」是查到了但数量没填**。交付时要分开说，不能笼统说"缺 N 项备件"。

## 六、查重口径

相似度 = 0.7 × 文本 bigram Dice 系数 + 0.3 × 检修部位/现象关键词重合度，阈值 0.45。

- 只在**同一位号**内两两比对
- **不能**把"来源类别相同"作为加分项：跨来源（缺陷 + 工单）的重复恰恰是最该提示的一类，按来源相同加分会把它压到阈值以下
- 命中时列入 `possibleDuplicate`，给出两条的序号、依据单号、来源与描述
- **两条全部保留在正式清单中**，由用户确认是否合并
- 相似度是文本匹配结果，**不代表两条确为同一项需求**

`netDemand` 给出的 `netIfAllMerged` 只是「若疑似重复全部确认合并」的条数下界，是给设备员做预判用的参考值，**不是脚本已经合并后的结果**。

## 七、申报理由表述规范

申报理由由脚本按来源自动生成，格式为「来源单号 + 状态/周期信息 + 记录原文」。成文时**须引用来源记录中的原文要点，不得夸大紧急程度**。

| 场景 | 应写 | 不应写 |
|---|---|---|
| 缺陷来源 | 「缺陷 QX-XXX（II 级）于 X 月 X 日发现未闭环，机封处持续滴漏」 | 「机封严重泄漏，随时可能着火，必须立即安排」 |
| 工单来源 | 「工单 GD-XXX 未闭环，计划完成 X 月 X 日」 | 「工单一直拖着没人干」 |
| 周期项 | 「周期项 ZQ-XXX，周期 180 天，上次检修 X 月 X 日，应于 X 月 X 日前完成」 | 「到期必须修，不修要出事」 |
| 隐患 | 「隐患 YH-XXX（重大隐患）未整改，整改期限 X 月 X 日，责任人 XX」 | 「隐患很危险，必须马上停工」 |
| 未判定 | 「工单 GD-XXX 无等级，优先级未判定，请车间确认缓急」 | 「工单默认按高」 |
| 备件未核实 | 「备件到位情况未核实，需与仓储确认后补填」 | 「备件应该有库存」 |
| 疑似重复 | 「与序号 X 疑似重复，请确认是否合并申报」 | 「已合并为一条」 |
| 优先级 | 「按缺陷等级建议为高，实际排期以公司设备管理部门批复为准」 | 「这条必须排在第一个」 |

## 八、说明行（必须保留）

`需求汇总.md` 与 `检修需求表.xlsx` 中必须保留：

> **本清单为车间申报稿，最终计划以公司设备管理部门（机动部/设备部）批复为准**

`需求汇总.md` 开头另有通用声明行「本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。」，同样不得删改。

这句不是客套话：车间上报的是需求，不是计划。漏掉这句，下游可能把申报稿当成已批复的检修计划去安排资源。

## 九、汇总说明段的写法

200~400 字，结构固定：

1. **本期需求总数与来源构成** —— 总数、四类来源各多少、检修类别分布、无依据项与未判定项多少
2. **需停机项与停机窗口衔接** —— 需停机几项、合计工期、与给定窗口是否冲突；未填停机与否的项要点名
3. **备件缺口与到货跟催** —— 区分「已核实不足」与「未核实」，点名需要跟催的型号
4. **与上期遗留项的衔接及需公司设备管理部门协调事项** —— 哪些是上期未完成顺延的、哪些需要公司统筹

数量一律引用 `demands.json`，**不得自行统计或调整**。
