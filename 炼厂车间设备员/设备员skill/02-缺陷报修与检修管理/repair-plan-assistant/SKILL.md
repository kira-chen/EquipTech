# 检修方案辅助编制（repair-plan-assistant）

面向中石化体系炼化厂车间（运行部）设备员与检修技术人员，按设备类型与检修范围生成检修方案初稿，含 JSA/风险分析与 HSE 措施占位、作业步骤、工机具、备件、质量控制点与验收标准。**本技能只生成初稿或审查要点，方案必须经技术负责人审核批准后方可实施；模型不得省略质量控制点与验收标准。**

## 适用条件
- 用户说"写个检修方案 / 检修步骤怎么排 / 作业指导书 / 这台设备怎么拆检 / 帮我审一下这份方案"，并说明设备类型、位号与检修内容。
- 覆盖设备类型：离心泵/往复泵、压缩机与机组、塔器容器换热器、阀门与安全阀、电机电气、**加热炉（炉管/烧嘴/衬里）、空冷器（管束/风机）、仪表回路（变送器/调节阀/联锁回路）**。
- **车间设备员可做**：日常维修、消缺类小项目自编方案初稿；大检修、专项、承包商编制的方案由设备员用本技能产出的步骤与质量控制点**审查初稿**（对照是否缺停工待检点、数值是否有出处、JSA/HSE 是否齐全）。**由 XX 归口**：方案的审核批准由技术负责人与公司设备管理部门（机动部/设备部）负责；安全措施审查与作业票签发由安全部门与属地单位负责；联锁定值变更由工艺/仪表归口。
- 不适用：安全措施的合规性判定；作业票办理；非常规、首次实施或无标准规程可依的检修项目（此类须由技术人员专门编制）。

## 前提条件
- 输入：用户说明的设备类型、位号、检修内容与范围（必需）。**强烈建议同时提供厂内检修规程或设备说明书**（`.docx`/`.md`/`.txt`），脚本会优先引用厂内规程而非通用口径。**PDF 先用平台 pdf 技能转为 txt/docx 再传入，脚本不读 PDF；扫描件需 OCR。**
- 必填信息：设备类型、位号、检修内容、检修分级（大检修/日常维修/抢修/专项，旧口径 大修/中修/小修 自动归并）、计划工期。可选：设备规格型号、上次检修记录、是否解体、备件到位情况。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得凭记忆撰写检修步骤。**

## 数据获取（MCP）

平台接入了业务系统 MCP 服务时，按下表调用工具取数，不再请用户上传导出文件；未接入时按操作步骤请用户提供系统导出文件。工具全部只读，不在业务系统里创建或修改任何单据。

| 服务 | 工具 | 参数 | 交给脚本 |
|---|---|---|---|
| 设备资产管理 | `get_equipment_ledger` | `workshop`：车间 | 填命令行参数（见下） |

取数后：

1. 工具返回的表格内容直接读取即可，不需要保存为文件。
2. `get_equipment_ledger`：台账只用来读取该位号的设备类型、设备名称、规格型号和车间，作 `--equip-type`、`--name`、`--model`、`--workshop`，不作为文件传入。

设备检修规程（md 或 docx）来自平台知识库，作 `--spec`；没有规程时生成基线方案，待确认项会明显增多。

## 操作步骤
1. **确认检修范围** —— 按 `references/intake-questions.md` 核对：设备类型、检修内容与分级、是否解体、是否用火、是否进受限空间、是否吊装、是否拆装盲板、备件是否到位、计划工期。**范围不清时必须追问，不得按最常见情形假定。**
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/plan.js" --equip-type "<设备类型>" --tag "<位号>" --scope "<检修内容>" --out "<工作目录>/检修方案"
   ```
   可选：`--spec "<厂内规程或说明书路径>"`、`--model "<规格型号>"`、`--duration <计划工期天数>`、`--start <YYYY-MM-DD>`、`--last "<上次检修记录>"`、`--level <大检修|日常维修|抢修|专项>`、`--dismantle <是|否>`、`--name`、`--workshop`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（无匹配的标准步骤/厂内规程无法解析/设备类型不在覆盖范围/旧口径分级已归并等）。脚本用法详见 `scripts/README.md`。
   - 设备类型不在覆盖范围内：脚本只输出通用框架并 warning，**模型不得凭通用知识填充具体拆装步骤、力矩值与间隙标准**，须标注"待技术人员补充"。
   - 厂内规程与通用口径冲突：一律以厂内规程为准，冲突点在 `conflicts` 中列出供用户确认。
3. **读取 plan.json 并匹配口径** —— 从 `<输出目录>/plan.json` 获取 `hse`（JSA/风险分析、八大类作业许可、双监护、HSE 措施占位）、`steps`（作业步骤）、`tools`、`spares`、`qcPoints`（质量控制点）、`acceptance`（验收标准）、`toBeConfirmed`、`conflicts`。再按设备类型读 `references/` 下对应口径文件（`procedure-pump.md`、`procedure-rotating.md`、`procedure-static.md`、`procedure-valve.md`、`procedure-electrical.md`、`procedure-furnace-aircooler-instrument.md`，无对应类型读 `procedure-generic.md`）。
4. **撰写方案正文** —— 按 `assets/templates/plan-template.md` 成文，结构为"检修概况 → 检修范围与内容 → JSA/风险分析与 HSE 措施（占位，由安全员/属地单位与作业单位填写）→ 施工准备（工机具、备件、人员）→ 作业步骤 → 质量控制点 → 验收标准 → 待确认事项"。**具体数值（力矩、间隙、公差、壁厚、水平度、试压值、校验精度）只引用厂内规程或说明书原文并注明出处；无出处的一律标"待查规程确认"，绝不填写凭经验的数值。条款须命中该项本身才算出处：壁厚、水平度不借用平面度公差条款，「转子轴向窜量与机封压缩量」两项都找到才算有出处。作业级别与风险等级不自判，以作业票与厂内风险分级为准。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `plan.md` 与 `plan.json`。**必须保留声明行"本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。"与"本方案为辅助生成的初稿，须经技术负责人审核批准、并按厂内规定完成安全措施审查与作业许可后方可实施"，不得删除或改写。安全措施章节须提示接 overhaul-process-check-bridge 核查。**

## 预期结果
- `plan.md`：检修方案初稿，含 检修概况、检修范围与内容、JSA/风险分析与 HSE 措施（占位）、施工准备、作业步骤、质量控制点、验收标准、待确认事项 八个部分，开头与末尾含固定声明行。
- `plan.json`：结构化步骤、控制点与 HSE 占位；`summary.json`：脚本末行摘要。
- 交付时向用户说明：引用了哪些规程来源、哪些项标注了"待确认"、与厂内规程的冲突点、JSA/HSE 占位需由谁填写、脚本 warnings（如有）。

## 不适用范围
- 不做安全措施合规性判定（用 overhaul-process-check-bridge），不签发或预检作业票，不自判用火/高处/吊装作业级别与风险等级。
- 不给出无出处的技术数值（力矩、间隙、试压压力、校验精度等）。
- 不编制首次实施、无规程可依或涉及重大技术改造的方案；不涉及联锁定值变更（工艺/仪表归口）。
- 不替代技术负责人审核与厂内方案审批流程。
