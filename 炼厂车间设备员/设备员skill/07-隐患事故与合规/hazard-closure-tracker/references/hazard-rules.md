# 整改期限口径、等级识别、五定核对、闭环判定规则与表述规范

> 制度依据：《中国石化安全隐患管理规定》（隐患分级为 重大隐患 / 一般隐患；整改落实「五定」：定整改方案、定资金、定责任人、定期限、定应急措施；旧口号「三定四不推」废止）。本文件只记口径，不转述制度中的数值；凡厂与厂之间有差异的项，用 `--rules` 接厂内口径，脚本默认不替用户选。

## 一、整改期限口径（无统一天数）

> **《中国石化安全隐患管理规定》对一般隐患没有统一的整改天数，整改期限由整改方案确定**，台账「要求整改期限」即方案期限。脚本内置的默认口径就是「以台账期限为准，台账无期限 → 未判定」，不是任何一家厂的正式规定。
> 厂内另有天数规定时，用 `--rules "<厂内口径xlsx>"` 的「整改时限」表传入；覆盖后报告中标注「厂内口径（文件名）」，未覆盖时标注「默认口径（references/hazard-rules.md，非厂内正式口径：无统一天数，期限以整改方案/台账为准）」。

| 等级 | 默认期限口径 | 说明 |
|---|---|---|
| 重大隐患 | **按整改方案期限** | 重大隐患须制定专项整改方案并明确期限，脚本不代为设定天数。台账「要求整改期限」为空时，该项标 `undetermined`，原因写「重大隐患未填写要求整改期限，整改方案期限未知」 |
| 一般隐患 | **按整改方案期限（无统一天数）** | 台账「要求整改期限」为空时标 `undetermined`，原因写「一般隐患无统一整改天数，台账未填要求整改期限，整改方案期限未知」；仅当 `--rules` 给出厂内天数时，才按「发现日期 + N 天」推算并注明口径来源 |
| 等级缺失 / 无法识别 | **不适用** | 台账有期限按期限判，无期限标 `undetermined`，**绝不套用任何默认天数** |

临期阈值：距要求整改期限 **7 天**以内且尚未整改完成的项列入「临期清单」（`metrics.dueSoonDays`）。

期限推定优先级：
1. 台账「要求整改期限」非空 → 直接采用，依据记为「台账『要求整改期限』」
2. 台账期限为空、等级为一般隐患、`--rules` 给了厂内天数、发现日期可解析 → 发现日期 + 时限天数，依据记为「发现日期 + N 天（厂内口径（文件名））」
3. 其余情况 → `undetermined`，在报告「六、未判定项」中注明缺哪个字段

**禁止**：等级缺失时按一般隐患推算期限；重大隐患无方案期限时按任何天数推算；无厂内口径时给一般隐患套默认天数；发现日期缺失时按台账录入顺序估算。

## 一之二、等级识别口径

- 只认「重大 / 一般」字样（含「重大隐患」「一般隐患」「普通」）。
- **「一级/二级/三级」「A 级/B 级/C 级」「公司级/厂级/车间级」在多数厂是隐患的管理层级（谁挂牌督办），不是严重度**，脚本**不直接映射**为重大/一般：等级记为「等级无法识别」，计入 `metrics.byLevel.unknown`，不触发重大隐患提示；台账有期限的仍按期限判超期/临期（期限判定不依赖等级），无期限的进 `undetermined`。warning 提示「疑似管理层级写法」。
- 厂内确有「A 级 = 重大隐患」之类的对应关系时，用 `--rules` 的「等级映射」表声明（格式见 `input-spec.md`），映射后才按重大/一般处理，报告标注「厂内口径（文件名）」。

## 一之三、五定核对

对**未闭环**的每一项核对「五定」是否落实，缺哪项列哪项，进「八、五定不全」一节与 `fiveFixedIncomplete[]`（`missing` 数组）：

| 五定 | 台账依据列 | 判「未落实」 |
|---|---|---|
| 定整改方案 | 整改措施（整改方案） | 为空或占位写法 |
| 定资金 | 整改资金（资金落实） | 为空或占位写法；台账无此列时 warning 一次，全部按未落实 |
| 定责任人 | 责任人 | 为空或占位写法 |
| 定期限 | 要求整改期限（或 `--rules` 推算出的期限） | 无法确定 |
| 定应急措施 | 应急措施（应急管控措施） | 为空或占位写法；台账无此列时 warning 一次，全部按未落实 |

已闭环项不核对。重大隐患五定不全的，督办清单事由追加「重大隐患五定不全（缺：…）」；一般隐患五定不全只在报告列出，不单独进督办（避免噪声）。**脚本不补填任何一项**；「不需要资金」应在台账填「不需要」而不是留空。占位写法指「—」「-」「/」「无」「暂无」「待定」「未定」「未落实」「待落实」，与留空同样按未落实处理；「不需要」「车间费用」等明确结论算已落实。

## 二、闭环判定规则

| 归类 | 判定条件 | 说明 |
|---|---|---|
| `closed` 已闭环 | 整改状态 = 已整改 **且** 有验收记录 | 唯一计入闭环率分子的情况 |
| `unverified` 已整改未验收 | 整改状态 = 已整改 **且** 无验收记录 | **绝不计入已闭环**，单列一节，须安排验收销号 |
| `overdue` 超期未整改 | 未闭环 **且** 期限可确定 **且** 截止日期 > 要求整改期限 | 输出超期天数与责任人 |
| `dueSoon` 临期 | 未闭环 **且** 距期限 ≤7 天 | |
| `inProgress` 整改中 | 未闭环 **且** 在期限内 | |
| `undetermined` 未判定 | 整改状态缺失或无法识别 / 台账无期限且（重大隐患 / 一般隐患无厂内天数 / 等级缺失或无法识别） / 一般隐患有厂内天数但缺发现日期 | 单列一节并注明缺哪个字段 |

「有验收记录」= 验收情况判为合格 **或**（验收情况不是「不合格 / 未通过 / 待验收」等否定写法 **且** 验收人或验收日期非空）。验收情况明确为否定写法时，即使填了验收人、验收日期也归 `unverified`（就严）。验收情况填了无法归类的文字（既非合格也非未验收）时，**按无验收记录处理（就严）** 并 warning。

**禁止**：
- 把「已整改未验收」并入已闭环，或在闭环率分子中计入该项
- 把整改状态填报为「已整改」直接当作闭环依据
- 未判定项按最宽松（或最严格）时限默认处理
- 因验收字段空白而推测「大概率已验收」

## 三、闭环率算法

```
闭环率 = 已整改且已验收项数 / 统计范围内隐患总数 × 100%
```

- 分母为统计范围内（含 `--from`、`--level`、`--owner` 筛选后）的全部隐患，**包含 `unverified` 与 `undetermined`**
- **分母为 0 时输出 `null`，报告显示「—」，不得写 0%**
- 按等级分布的闭环率同理：该等级总数为 0 时显示「—」

平均闭环时长 = 已闭环项的（验收日期或整改完成日期 − 发现日期）均值，仅纳入两端日期均可解析且非负的项；无可计算项时输出 `null`，显示「—」。

## 四、重大隐患处理要求

重大隐患在本技能中享有三项固定待遇，**任何情况下不得删减或弱化**：

1. **开头提示**：报告与督办清单开头写明重大隐患项数与未闭环项数，并提示「须按重大隐患管理程序上报分厂/公司安全部门并挂牌督办」，由脚本直接写入（不是占位符，用「【注意】」不用 emoji）。**无论重大隐患处于何种状态——包括已闭环——都必须提示。**
2. **单独成节**：「二、重大隐患专列」逐项列出编号、描述、来源、发现日期、责任人、责任单位、要求整改期限、整改状态与当前归类。
3. **进入督办**：未闭环的重大隐患一律进督办清单，督办事由写「重大隐患（当前归类）」。

无重大隐患且无超期项时，开头改写为「本期无重大隐患，亦无超期未整改项」，**不得凭空生成告警**。

本技能不替代重大隐患上报分厂/公司安全部门与挂牌督办的法定程序，报告中应提示按重大隐患管理程序办理；上报时限以厂内规定为准，脚本不判定。

## 五、状态与验收矛盾

整改状态填报为「未整改」或「整改中」，却已填写验收情况、验收人或验收日期时：

1. 进「七、状态与验收矛盾」一节，写明具体矛盾内容（哪几个验收字段有值）
2. 产生 warning，具体到 sheet 名与行号
3. **脚本不作任何取舍**——既不按验收记录认定已闭环，也不删除验收记录；由设备员核实台账后修正
4. 该项按其整改状态归桶（未整改 / 整改中），因此不进闭环率分子

## 六、说明段表述规范

撰写 250~400 字，结构固定为七段（无重大隐患时第二段可略，无五定不全时第五段可略）：

1. **总体情况**：统计范围、隐患总数、各归类分布、采用的期限口径。
2. **重大隐患**：项数、各项当前状态、未闭环项的责任人与期限情况，提示上报分厂/公司安全部门并挂牌督办。
3. **超期未整改项与责任**：逐条或分类说明，含超期天数与责任人、责任单位。
4. **已整改未验收项**：项数、涉及责任人，说明为何不计闭环、须安排验收。
5. **五定不全项**：项数与主要缺项（资金/应急措施最常见），须由责任单位补齐。
6. **闭环率与趋势**：引用闭环率与平均闭环时长；有 `--prev` 时说明环比方向。
7. **督办重点**：建议优先督办的项与依据。

### 用词要求

| 场景 | 应写 | 不得写 |
|---|---|---|
| 未验收项 | 「整改状态填报为已整改，台账无验收记录，暂不计入闭环，须安排验收销号」 | 「实际已完成，验收只是手续」「可视同闭环」 |
| 未判定项 | 「因隐患等级缺失，整改时限无法确定，须补齐后重新跟踪」「台账未填整改期限，一般隐患无统一天数，须按整改方案补填」 | 「按一般隐患计约已超期」「按 30 天算早就超了」「估计不严重」 |
| 层级写法 | 「台账等级填『A 级』，属厂内管理层级写法，未映射为重大/一般；厂内对应关系请提供口径表」 | 「A 级就是重大隐患」 |
| 五定不全 | 「YH-XXX 未落实资金与应急措施，须责任单位补齐后更新台账」 | 「资金应该不需要」（替台账补填） |
| 超期原因 | 「台账记录整改状态为整改中，已超出要求整改期限 12 天」 | 「责任人拖延」「车间不重视」 |
| 重大隐患 | 「按重大隐患管理程序上报分厂/公司安全部门并挂牌督办」 | 「风险可控，可延期」 |
| 闭环率 | 引用 hazard.json 的 `metrics.closureRate` | 自行计算或换算口径 |
| 分母为 0 | 「统计范围内无隐患，不计算闭环率」 | 「闭环率 0%」「闭环率 100%」 |

### 硬约束

- **不认定隐患、不判定等级、不做整改验收**。等级以台账填报为准，验收以安全部门意见为准。
- **不判定责任归属，不提考核与处罚建议**。只陈述台账记录的责任人与责任单位。
- **不放宽时限**。用户口头说「这条可以缓一缓」时，仍按台账与时限口径判定，可在说明段注明用户诉求。
- **数量、天数、比率一律引用 hazard.json**，不得自行统计。
- **声明行「隐患认定、等级与整改验收以安全部门意见为准」与通用声明「本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准」不得删除或改写。**
- 产出 md 不用 emoji，醒目提示用「【注意】」。

## 七、下游衔接

- 隐患涉及设备缺陷需登记（维修通知单）→ `defect-intake-grading`
- 整改涉及用火/受限空间等作业 → `permit-precheck-bridge`（车间作业票预检）
- 整改工单超期催办 → `work-order-tracker`
- 日报：`equipment-daily-report` 读本技能 `hazard.json`（`counts`、`majorHazards`、`overdue`、`unverified`）生成日报的「隐患」一节，由日报侧实现，本技能不另出日报片段
- 个人待办：`worklog-todo-manager` 读 `hazard.json` 的 `overdue[]`、`dueSoon[]`、`unverified[]`
