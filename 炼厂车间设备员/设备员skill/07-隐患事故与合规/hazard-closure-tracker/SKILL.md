# 隐患整改闭环跟踪（hazard-closure-tracker）

面向中石化体系炼化厂车间（运行部）设备员，跟踪本车间设备类隐患从发现到整改验收的闭环过程，识别超期项、核对「五定」并生成督办清单，交付对象为车间设备主任 / 公司设备管理部门。**时限判定、五定核对与闭环率统计由脚本完成，模型只负责成文；不得放宽时限或替安全部门判定已闭环。**

设备员可做：隐患台账整理、整改进度跟踪、督办清单、报表汇总。由安全环保部门归口：隐患认定与等级判定、重大隐患上报与挂牌督办、整改验收销号。

## 适用条件
- 用户说"隐患整改进度 / 隐患台账 / 哪些超期了 / 闭环率多少 / 督办清单"，并给出（或即将给出）隐患台账。
- 覆盖隐患来源：日常巡检、车间自查、公司/分厂安全部门检查、政府与集团督查、HSE 审核、第三方诊断、事故与险肇后整改要求。
- 不适用：设备缺陷的登记与 A/B/C 分级（缺陷与隐患是两个体系，用 defect-intake-grading）；隐患等级的重新判定；安全部门的隐患认定与整改验收。

## 前提条件
- 输入：一个 `.xlsx`（或同结构 CSV 目录，UTF-8 或 GBK），含「隐患台账」，字段见 `references/input-spec.md`（隐患编号、描述、等级、来源、发现日期、责任人、责任单位、要求整改期限、整改措施、整改资金、应急措施、整改状态、验收情况）。EM/HSE 系统导出的列名（隐患内容、检查类型、属地单位、整改方案、资金落实、应急管控措施等）按别名表自动识别。
- 必填信息：车间名称、统计截止日期（YYYY-MM-DD）。可选：厂内口径文件（整改时限 + 等级映射）、统计起始日期、上期 hazard.json（对比）。
- PDF 形式的检查通知、隐患整改通知书：先用平台 pdf 技能转为 txt/docx，再由用户整理进台账；脚本不读 PDF，扫描件需 OCR。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得手工判定超期。**

## 数据获取（MCP）

平台接入了业务系统 MCP 服务时，按下表调用工具取数，不再请用户上传导出文件；未接入时按操作步骤请用户提供系统导出文件。工具全部只读，不在业务系统里创建或修改任何单据。

| 服务 | 工具 | 参数 | 交给脚本 |
|---|---|---|---|
| HSE管理平台 | `get_hazards` | `workshop`：车间（按责任单位筛选，不填会混入其他车间的隐患；隐患导出没有「车间」列，脚本无法按车间核对）；可选 `level`：重大 / 一般 | `--input` |

取数后：

1. 工具返回下载链接（60 分钟内有效，过期重新调用）。csv 按原文件名放进新建的空目录，不改文件名，不与其他技能的文件混放；把目录作为“交给脚本”一列的参数值。
2. 脚本只在输入带车间列时按 --workshop 核对（剔除其他车间的行；车间列全不一致时不筛并在报告开头提示）；MCP 导出多数不带车间列，取数时仍必须带 workshop。脚本只认「车间」列，「责任单位」「属地单位」可能是部门或班组，不拿来核对。

## 操作步骤
1. **确认统计范围与口径** —— 车间、起止日期；整改期限以台账「要求整改期限」（即整改方案期限）为准，《中国石化安全隐患管理规定》无统一天数，厂内另有天数规定或「A/B/C 级」「一级/二级」等厂内等级写法时，用 `--rules` 传入「整改时限」与「等级映射」表（格式见 `references/input-spec.md`）；未提供时按 `references/hazard-rules.md` 默认口径并在产出中注明。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/hazard.js" --input "<xlsx路径>" --workshop "<车间名>" --date <YYYY-MM-DD> --out "<输入同目录>/隐患跟踪"
   ```
   可选：`--from <起始日期>`、`--rules "<厂内口径xlsx：整改时限 + 等级映射>"`、`--level <重大|一般>`、`--owner "<责任人>"`、`--prev "<上期 hazard.json>"`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（缺列/等级取值非法/整改期限缺失/状态与验收矛盾/编号重复/按车间剔除的行数与车间名/车间列为空的行数等）。warning 以【注意】开头说车间列取值与 --workshop 不一致时，多半是传错了文件，先请用户核对输入再交付。脚本用法详见 `scripts/README.md`。
   - 整改状态为"已整改"但无验收记录：标 `unverified` 单列一节，**绝不计入已闭环**。
   - 等级缺失、或填的是「一级/A 级/厂级」等管理层级写法（非严重度）：等级记为无法识别，不映射为重大/一般；台账无期限时归入 `undetermined`，**绝不按最宽松时限处理**；一般隐患台账无期限同样 `undetermined`（无统一天数）。
   - 重大隐患：单独成节并醒目标注，**无论状态如何都必须在报告开头提示**，并提示上报分厂/公司安全部门并挂牌督办。
   - 五定不全：未闭环项缺整改方案/资金/责任人/期限/应急措施任一项的，单列「八、五定不全」，脚本不补填。
3. **读取 hazard.json** —— 从 `<输出目录>/hazard.json` 获取：`overdue`（超期未整改，含超期天数与责任人）、`dueSoon`（临期）、`inProgress`、`closed`（已整改已验收）、`unverified`（已整改未验收）、`majorHazards`（重大隐患专列）、`undetermined`、`conflicts`、`fiveFixedIncomplete`（五定不全，含缺项）、`metrics`（闭环率、按等级/责任单位/来源分布、平均闭环时长）、`counts`。
4. **撰写"隐患整改情况说明"** —— 读 `references/hazard-rules.md` 的表述口径，撰写 250~400 字，按"总体情况 → 重大隐患（如有）→ 超期未整改项与责任 → 已整改未验收项 → 五定不全项 → 闭环率与趋势 → 督办重点"结构，替换 `hazard.md` 中 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字。**数量、天数、比率一律引用 hazard.json。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `hazard.md`、`hazard.json` 与 `督办清单.md`（按责任人分组）。**存在重大隐患或超期未整改项时，必须在开头醒目提示（「【注意】重点提示」），该提示不得删除或弱化。必须保留声明行："隐患认定、等级与整改验收以安全部门意见为准"与通用声明"本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准"。**

## 预期结果
- `hazard.md`：隐患跟踪报告十节：一、总体概览；二、重大隐患专列；三、超期未整改清单；四、临期清单；五、已整改未验收；六、未判定项；七、状态与验收矛盾；八、五定不全；九、闭环指标（按等级/责任单位/来源分布、与上期对比）；十、隐患整改情况说明（模型填写）；有 warnings 时附「数据提示」。
- `督办清单.md`：按责任人分组（责任人为空或填「待定 / 无 / —」等占位写法的归入「（未填责任人）」组，排在最后），可直接转发车间设备主任；`hazard.json`；`summary.json`。
- 交付时向用户说明：隐患总数、重大隐患数、超期数、未验收数、五定不全数、闭环率、采用的口径（默认 / 厂内文件名）、脚本 warnings（如有）。

## 不适用范围
- 不认定隐患、不判定隐患等级（含不把「一级/A 级」等厂内层级写法自行映射为重大/一般）、不做整改验收。
- 不判定责任归属，不做考核与处罚建议。
- 不替代重大隐患上报分厂/公司安全部门与挂牌督办的法定程序。
- 不做设备缺陷的登记与跟踪（用 defect-intake-grading）；不做工单催办（用 work-order-tracker）。
