# scripts 使用说明

## compliance.js —— 主脚本

```bash
node "<技能目录>/scripts/compliance.js" \
  --rules "<条款文本或条款清单路径>" \
  --materials "<本车间资料目录或清单xlsx>" \
  --workshop "<车间名>" \
  --date <YYYY-MM-DD> \
  --out "<输出目录>"
```

### 参数

| 参数 | 必需 | 说明 |
|---|---|---|
| `--rules` | **是** | 条款文本或条款清单：`.docx` / `.xlsx` / `.md` / `.txt`；法规标准与企业制度同一口径。**缺失时报错终止**；传 `.pdf` 时报错并提示「先用平台 pdf 技能转为 txt/docx」 |
| `--materials` | 是 | 本车间资料目录（递归扫描），或资料清单 `.xlsx` |
| `--workshop` | 是 | 车间名称 |
| `--date` | 否 | 自查时点 `YYYY-MM-DD`；不提供不报错，报告写「未指定」并 warning，**绝不默认取当天** |
| `--scope` | 否 | 自查范围说明，仅写入报告头部 |
| `--internal` | 否 | 企业制度（集团/公司/分厂/厂内）目录或清单，作为已有材料并入对照并标记归属「厂内制度」；路径不存在时报错 |
| `--last` | 否 | 上次自查结果，仅登记；路径不存在时报错 |
| `--out` | 否 | 输出目录，默认系统临时目录 `<os.tmpdir()>/rcc-out`，建议始终传 `--out` |

### 产出

| 文件 | 内容 |
|---|---|
| `compliance.json` | items、hasEvidence、noEvidence、partialEvidence、needInterpretation、unmatched、materials（每份带 `categories`、`categoryFrom`）、counts、meta（statement / statementFill / internalNotice / statusNotice） |
| `compliance.md` | 五节报告；开头带四档口径提示与企业制度说明；末尾固定声明行两句；醒目提示用「【注意】」；分析段留占位 |
| `对照表.xlsx` | 五个工作表：条款对照、未见材料与材料不完整、需进一步确认、未对应材料、状态口径与声明 |
| `summary.json` | 末行摘要落盘（Windows 控制台乱码兜底） |

### 退出码
- `0`：成功，末行输出 `{"ok":true,...}`
- `1`：失败，末行输出 `{"ok":false,"error":"...","warnings":[...]}`
  （含**未提供 `--rules`**、条款文件不存在、解析不出任何条款、条款/资料工作表无法识别、条款格式不支持、日期非法、`--internal` / `--last` 路径不存在）

### 关键行为（不得靠模型绕过）

1. **状态只有四档**：`已见对应材料 / 未见对应材料 / 材料不完整 / 需进一步确认`。
   脚本写入的 `statusCn`、md 状态列、xlsx 状态列**只可能是这四个值之一**，
   **任何位置都不出现「符合」「不符合」作为判定结论**。`selftest.js` 用正则扫描全文核验。
2. **条款必须由用户提供**：未给 `--rules` 时脚本报错终止，错误信息写明
   「条款文本须由用户提供，本技能不从记忆中引用条款编号与原文」。
   条款编号与原文**逐字搬运**，不改写、不补全、不纠错，每条带来源行号。
3. **笼统条款单列**：条款未指向任何具体资料类别与特征词时进 `needInterpretation`，
   **即使名下挂到了名称相关的资料也不改判**，资料仅作「供人工核对参考」列出。
   脚本不解释条款含义，一次都不解释。
4. **未见对应材料**：`noEvidence` 项的 `evidence` 恒为空数组，说明里写「按『未见对应材料』一档记录，
   正式判定由监管部门、内审或法务作出」，**既不写「不符合」也不写「符合」**。
5. **材料不完整只采信填报**：判定来源唯一是资料清单「完整性说明」列的用户填报内容，
   脚本不自行推断；名下部分材料齐备、部分不完整的，**仍判材料不完整**。
6. **声明行**：`compliance.md` 末尾固定写入
   `本对照为辅助自查，仅反映所提供材料与条款的对应情况，不构成合规达标结论与法律意见；正式判定以监管部门、内审或法务意见为准`，
   同句也写入 `compliance.json` 的 `meta.statement` 与 `对照表.xlsx`；其后固定补一句
   `最终符合性结论由自查责任人按厂内审核表口径填写，本技能不代填`（`meta.statementFill`）。
8. **企业制度同一口径**：md 第一节之后写入「企业制度……与法规标准同样通过 --rules / --internal 传入，条款原文由用户提供」（`meta.internalNotice`）。
9. **别名表**：`RULE_ALIASES` / `MAT_ALIASES` 经 `C.mergeAliases` 与共享 `SYSTEM_ALIASES` 合并，局部优先；「标准名称」别名补「制度名称」「制度」。
10. **资料归类先读资料类型**：资料清单有「资料类型」列时先按该列归类，再按资料名称归类，两者合并；`materials[].categories` 记归类结果，`categoryFrom` 记每个类别由哪一列认出（资料类型 / 资料名称 / 资料名称+资料类型）。目录扫描没有资料类型，只看文件名。系统导出文件名走 `FILE_ALIASES`：故障记录（含处理措施）同时算检修记录与缺陷与故障记录，通知单算缺陷与故障记录，隐患台账单独归隐患排查治理记录（通知单、故障记录不能顶替隐患台账），作业清单算作业许可。「台账」「记录」这类泛称不落任何类别，认不出的资料进「未对应材料」，**不按信息缺失推断**。
7. **不提供法律意见**：脚本不输出任何法律后果、处罚、责任追究、适用性判断与风险等级。

## lib/compliance-spec.js —— 对照规则表

```js
const S = require('./lib/compliance-spec');
S.ruleCategories('使用单位应当建立设备台账');          // → ['ledger']
S.fileCategories('故障记录.csv');                     // → ['maintenance', 'defect']（FILE_ALIASES 补充）
S.materialCategories('PM导出01.csv', '检修记录');   // → {keys:['maintenance'], from:{maintenance:'资料类型'}}
S.matchRule('人员应当持证上岗', '设备台账.xlsx');       // → {matched:false}
S.vagueness('使用单位应当加强管理，确保工作有效开展。'); // → {vague:true, reason:'...'}
S.STATUS_CN;  // → 四档状态文字，不含「符合/不符合」
```

口径见 `references/compliance-rules.md`，两者同源。对照从严：只认「同一具体资料类别」与
「具体特征词直接命中」两种依据，泛词（设备/记录/资料/管理）一律不构成对应。

条款侧的词表刻意比资料侧收得更紧：用「设备台账」而非「台账」（隐患台账、持证台账都带「台账」二字），
用「维修记录」而非「维修」（「维修人员」说的是人不是记录）。

## docx2text.js —— docx 文字层导出（排障用）

```bash
node scripts/docx2text.js --input <条款文本.docx>
```

主脚本内部直接调用 `lib/docx-lite.js` 解析 docx；本脚本用于人工确认 Word 条款文本的文字层读出效果。

## make-sample.js —— 样例生成

```bash
node scripts/make-sample.js --out examples [--seed <n>]
```

生成 8 份样例：主条款清单（12 条，含标题行与标准名称列，其中两条来源为虚构企业制度 Q/XX-虚构-00N，演示制度与法规同一口径）、主资料清单、笼统条款变体、
条款与资料齐备变体、资料极少变体、Markdown 条款文本、企业制度清单（含公司级制度）。

> **样例中的标准名称、条款编号与条款原文全部为虚构**，形如 `XX/T 9xxx—2026（本样例虚构标准，非真实标准）`，
> 不对应任何真实法规与标准，仅用于验证脚本的解析与对照逻辑。**不得当作真实条款引用。**

seed 改变虚构文号与措辞，但结论不变：主样例恒为
**6 条已见对应材料、2 条未见对应材料、2 条材料不完整、2 条需进一步确认、1 份未对应材料**。

## selftest.js —— 自测

```bash
node scripts/selftest.js
```

209 条断言，覆盖：规则表与笼统性判定单元测试、**「符合/不符合」禁用词全文扫描**、
条款必须由用户提供（4 种缺失路径）、笼统条款不自行解释、未见材料的表述、材料不完整不被齐备材料掩盖、
不提供法律意见、声明行与四档口径提示、md/目录/合计行/别名表头/空行解析、14 条参数校验、
`--internal` 归并、正反对照、产出结构完整性、PDF 前置步骤提示、声明补充句、企业制度说明、无 emoji、别名合并、系统导出文件名别名与资料类型列归类（Q 组，含停电通知单、检修作业清单、故障率统计、泛称类型等反例）、「用火」与「动火」并列识别为作业许可、「备用火炬 / 使用火炬 / 备用火嘴」不误归作业许可（R 组）。全绿退出 0。

禁用词扫描器只放行三种位置：技能自身标题、明确的禁用/免责语句、用户条款原文被逐字搬运的行。
