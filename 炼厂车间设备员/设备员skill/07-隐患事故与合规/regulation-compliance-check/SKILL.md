# 法规标准符合性自查（regulation-compliance-check）

面向中石化体系炼化厂车间设备员，对照法规标准与企业制度条款梳理设备管理应做事项，识别本车间的执行缺口。**只做条款与现状的对照，不出具合规达标结论与法律意见；条款引用必须准确，不得凭记忆引用条款编号。** 企业制度（《中国石化设备管理规定》《炼化企业设备管理技术规定》《中国石化安全隐患管理规定》及公司/分厂/厂内制度）与 TSG、GB 同一口径处理：都通过 `--rules`（作为条款来源）或 `--internal`（作为已有制度材料）传入，**条款原文一律由用户提供**。

## 适用条件
- 用户说"对照标准查一下我们缺什么 / 法规要求做哪些 / 合规自查 / 这条标准要求什么 / 中石化设备管理规定要求我们做什么"，并提供条款原文与本车间设备管理资料。
- 覆盖范围：特种设备法规（TSG 系列）、设备管理国家与行业标准、集团/公司/分厂/厂内设备管理制度——**三者一律由用户提供条款原文**。
- 车间设备员可做的部分：整理本车间资料清单、按条款逐条对照、列出未见/不完整材料、形成跟进事项。
- 由他人归口的部分（技能只提示，不代做）：符合性最终结论由自查责任人按厂内审核表口径填写；合规认定由公司设备管理部门（机动部/设备部）、安全环保部门、内审或法务归口。
- 不适用：合规达标与否的结论；法律意见；监管部门与内审的正式判定；迎检资料的归集（`inspection-evidence-package`）；自查表逐栏填报（`self-audit-form-filler`）。

## 前提条件
- 输入：法规标准或企业制度的条款文本/条款清单（`.docx`/`.xlsx`/`.md`/`.txt`），以及本车间的设备管理资料或制度清单。**条款文本须由用户提供，本技能不从记忆中引用条款原文与编号。**
- **PDF 统一前置步骤**：PDF 先用平台 pdf 技能转为 txt/docx 再传入，脚本不读 PDF；扫描件需 OCR。传入 `.pdf` 时脚本会报错并提示此步骤。
- 必填信息：车间名称、自查范围（涉及哪些法规标准）、自查时点。可选：厂内管理制度、上次自查结果。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得凭记忆对照条款。**

## 操作步骤
1. **确认自查范围与条款来源** —— 涉及的法规标准或企业制度、条款文本来源、自查范围。**用户未提供条款文本时（包括只说了"按中石化设备管理规定查"这类制度名称），必须说明"无法从记忆中准确引用条款，请提供标准/制度文本或条款清单"，不得凭印象列举条款编号与要求。** 条款文件为 PDF 的，先按前置步骤转为 txt/docx。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/compliance.js" --rules "<条款文本或清单路径>" --materials "<本车间资料路径或清单>" --workshop "<车间名>" --date <YYYY-MM-DD> --out "<工作目录>/合规自查"
   ```
   可选：`--scope "<自查范围>"`、`--internal "<企业制度目录或清单>"`（制度作为已有材料并入对照；制度作为条款来源时改走 `--rules`）、`--last "<上次自查结果>"`。未传 `--out` 时产出写入系统临时目录 `<os.tmpdir()>/rcc-out`，建议始终传 `--out`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（条款无法解析/条款表述笼统难以对照/资料无法匹配等）。脚本用法详见 `scripts/README.md`。
   - 条款要求笼统无法直接对照：归入 `needInterpretation` 单列，**不得自行解释条款含义后判定符合与否**。
   - 找不到对应资料：标 `noEvidence`（未见对应材料），**绝不表述为"不符合"，也不得表述为"符合"**。
3. **读取 compliance.json** —— 从 `<输出目录>/compliance.json` 获取：`items`（逐条款：条款编号与原文、应做事项、对应资料、状态）、`hasEvidence`（有对应材料）、`noEvidence`（未见材料）、`needInterpretation`（需解释）、`partialEvidence`（材料不完整）、`counts`。
4. **生成对照表** —— 按 `assets/templates/compliance-template.md` 成文，含：自查范围与条款来源、逐条款对照表（条款原文、应做事项、现有材料、状态）、未见材料清单、需进一步解释的条款、建议跟进事项。**状态只用"已见对应材料 / 未见对应材料 / 材料不完整 / 需进一步确认"四种表述，不得用"符合 / 不符合"。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `compliance.md` 与 `compliance.json`。**必须保留声明行："本对照为辅助自查，仅反映所提供材料与条款的对应情况，不构成合规达标结论与法律意见；正式判定以监管部门、内审或法务意见为准"，以及其后的补充句"最终符合性结论由自查责任人按厂内审核表口径填写，本技能不代填"，均不得删除或改写。** 产出 md 不用 emoji，醒目提示用「【注意】」。

## 预期结果
- `compliance.md`：符合性对照表，含自查范围与来源、逐条款对照、未见材料与材料不完整清单、需确认条款、跟进事项与未对应材料五个部分，末尾含固定声明行（两句）。
- `compliance.json`：逐条款对照结果；`summary.json`：脚本末行摘要。
- 交付时向用户说明：条款总数、已见材料数、未见材料数、需确认数、条款来源、脚本 warnings（如有）。

## 不适用范围
- 不出具合规达标与否的结论，不使用"符合/不符合"表述。
- 不提供法律意见与法律责任分析。
- 不凭记忆引用条款编号与原文（法规、标准、企业制度一视同仁）。
- 不替自查责任人填写厂内审核表的符合性结论。
- 不替代监管检查、内部审计与法务审查。
