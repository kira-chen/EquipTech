# 检索口径与表述规范

> **案例中的原因是当时该案例的结论，不代表当前故障的原因；是否适用须结合当前设备实际情况判断。**
> 这句话必须原样保留在每一份交付的 `cases.md` 与对话回答的结尾，脚本已自动写入 md，不得删改。
> 同时写入的通用声明行：「本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。」

## 一、相似度怎么算

### 完整口径（提供了 `--part` 时）

```
相似度 = 0.55 × 现象文本 bigram Dice 系数
       + 0.30 × 设备类型是否匹配（归一后相同 → 1，否则 0）
       + 0.15 × 故障部位是否匹配（归一后相同 → 1，否则 0）
```

### 未提供 `--part` 时

部位维度**完全不参与计算**，剩余两项权重归一化重分配：

```
相似度 = 0.647 × 现象文本 bigram Dice + 0.353 × 设备类型是否匹配
```

不按「部位默认匹配」（会虚高）也不按「部位默认不匹配」（会虚低），而是把它从公式里拿掉。`cases.json` 的 `meta.weights` 记录本次实际生效的权重，交付时须一并说明。

### `--weights` 调权（厂内可配置）

默认 `text=0.55,type=0.30,part=0.15` 是本技能的口径，不是厂内标准。案例库现象描述写得很规范、或者希望更看重设备类型时，可用 `--weights "text=0.45,type=0.40,part=0.15"` 调整：

- 键只能是 text / type / part，三项之和须为 1，缺省项取默认；
- text 必须大于 0，否则检索退化为「按设备类型分组」，不再是案例检索；
- 用了自定义权重，脚本 warning「本次使用了自定义权重……交付时须说明」，md 抬头标「（自定义）」，`meta.weightsCustom` 为 true。**不得为了凑出命中而调权**，与不得自行调低 `--min-score` 是同一条红线。

### SAP 损坏/原因代码（`--fault-code`）

SAP PM M2 故障报告通知单带「损坏代码 / 对象部件 / 原因代码」，这是比文本相似度更可靠的归类依据：

- 给了 `--fault-code` 且案例代码相同 → `codeHit: true`，排序优先于文本相似度，matchBasis 加注「故障代码同为「X」」，md 命中标题带「【注意】故障代码相同」；
- 代码**不计入相似度数值**，相似度下限仍先分层：代码相同但设备类型不同、相似度低于下限的案例留在低相似度节，不被代码抬进命中（例：同一 TEMP02 轴承温度高代码，离心泵与离心压缩机不互通）；
- 案例库没有代码列时 warning「代码维度未比对」，不报错。

### 各项含义

- **bigram Dice**：把两段现象描述切成相邻两字的片段集合，算交集占比。「机封处滴漏，泵体下方有油渍」与「机封处持续滴漏，泵体下方有油渍」共享「机封」「滴漏」「油渍」等大量片段，得分高。标点与空白在切分前已清除。
- **设备类型**：按 `input-spec.md` 的归一表比对。归一表刻意把「离心压缩机」与「往复压缩机」分开——机型不同，故障机理与处置方式不可互通。任一方为空则该项不得分，并在「不同点」中写明「设备类型字段有缺失，未参与比对」。
- **故障部位**：按归一表比对，「机封」与「机械密封」视为同一部位。
- **型号**：**不计入相似度**。型号相同只在匹配依据中加注一行，并作为同分时的排序次序。理由：同型号不等于同工况，把型号计入权重会让「同型号但现象完全不同」的案例挤掉真正相似的案例。

### 阈值

| 参数 | 默认 | 含义 |
|---|---|---|
| `--min-score` | 0.3 | 达到才算命中，进 `matches` |
| `--top` | 5 | 命中最多呈现几条 |

0.3 的含义：在设备类型匹配（得 0.30）的前提下，现象描述几乎无重合的案例刚好卡在边界。低于 0.3 基本是"只是同类设备"，谈不上类似案例。

## 二、四条不可退让的红线

### 红线一：没有案例库，这个技能就用不了

脚本在五种情况下直接 `ok:false` + `exit 1`（见 `input-spec.md`）。收到 `ok:false` 时，**唯一正确的回答是告诉用户技能不可用及原因，然后终止**。

| 应回答 | 绝不可写 |
|---|---|
| 「没有案例库，这个技能没法用。我不能凭通用知识给你编案例——那会把不存在的经验当成本厂历史。请提供案例库或历史故障记录后再来。」 | 「案例库暂时没有，不过一般来说离心泵机封泄漏常见原因有……」 |
| 「案例库里这张表一条现象描述都没填，检索无从谈起。」 | 「案例库信息不全，我按经验补充几条典型案例供参考」 |

**"通用知识 + 免责声明"不是折中方案，仍然违规。** 用户要的是本厂真实发生过的事，模型记忆里的"典型案例"既无出处也无法核实，在事故调查与检修决策中会被当作证据误用。

### 红线二：命中为空就说命中为空

`counts.matches` 为 0 时，回答必须是「**案例库中未检索到类似案例**」，并说明检索了多少条、最高相似度是多少。

| 应回答 | 绝不可写 |
|---|---|
| 「案例库 13 条案例全部检索，按相似度下限 0.3 一条都没达标，最高仅 0.03。案例库中未检索到类似案例。」 | 「最接近的是 FC-006 富气压缩机轴承温度案例，虽然不太像，但可以参考一下」 |
| 「建议补充现象关键特征后重检，或确认案例库是否覆盖该设备类型。」 | 「我把相似度标准放宽一点，这样能找到 3 条」 |

**不得自行调低 `--min-score` 来"凑出"结果。** 确需放宽时必须先告诉用户当前下限、放宽到多少、为什么，由用户决定。

### 红线三：低相似度的只能当背景，不能当主角

`lowSimilarity` 中的案例，每条都带 `note: "相似度较低，仅供参考"`。呈现时：

- 必须放在命中案例**之后**，单独成节；
- 必须逐条带上「相似度较低，仅供参考」的标注；
- **不得**把它们混进正文按类似案例逐条展开讲处置经验；
- 若 `matches` 为空而 `lowSimilarity` 非空，先说「未检索到类似案例」，再说「另有 N 条低相似度记录，仅供参考」，顺序不能颠倒。

### 红线四：案例的原因是那次的结论，不是这次的原因

案例库里的「原因」字段，是当时那起故障经过检修确认后的结论。它对当前故障只有**线索**价值：

| 应写 | 不得写 |
|---|---|
| 「FC-001 的现象与你描述的高度相似（bigram 0.65），当时确认的原因是动环端面划伤、冲洗液带固体颗粒」 | 「你这台泵是动环端面划伤了」 |
| 「两起案例处置都是更换机封，FC-001 还加装了冲洗液过滤器」 | 「按 FC-001 的做法换机封加过滤器就行了」 |
| 「当前故障的原因判定建议接 `anomaly-triage-advisor`」 | 「原因基本可以确定了」 |

## 三、匹配依据与不同点：每一条都必须标注

`matches[]` 与 `lowSimilarity[]` 的每条案例都带两个数组，**呈现时两个都不能省**：

- `matchBasis`（匹配依据）——哪些特征相似，例如：
  ```
  现象文本 bigram 相似度 0.65
  设备类型同为「离心泵」
  故障部位同为「机械密封」
  型号同为「IH100-65-250」
  ```
- `differences`（不同点）——哪些条件不同，例如：
  ```
  型号不同（当前 ZA80-250 / 案例 IH100-65-250）
  故障部位不同（当前 轴承 / 案例 机械密封）
  未提供当前设备型号，型号未比对
  案例未记录发生工况，工况差异无法判断
  现象描述用词重合度低，文本相似主要不成立
  ```

只讲相似不讲差异，会让设备员误以为这就是同一回事。**「不同点」为空时也要说明**「所比对字段均一致，但工况与设备实际状态仍须自行核实」，不能留白。

特别注意最后一条：**相似度 0.3~0.45 区间的案例，往往是"设备类型对上了、现象其实不像"**（文本项得分极低，分数全靠类型那 0.30 撑着）。这类案例的 `differences` 会出现「现象描述用词重合度低，文本相似主要不成立」，交付时必须把这句话讲给用户，不能只报一个相似度数字了事。

## 四、措辞对照

| 场景 | 本技能写法 | 不应写成 |
|---|---|---|
| 相似度 | 「现象文本 bigram 相似度 0.65，设备类型与故障部位均相同」 | 「跟你这个基本一样」 |
| 案例原因 | 「当时判定原因是动环端面划伤」 | 「原因是动环端面划伤」 |
| 处置参考 | 「该案例的处置是更换机封并加装冲洗液过滤器，是否适用请结合本台泵的冲洗方案判断」 | 「建议更换机封并加装过滤器」 |
| 命中为空 | 「案例库中未检索到类似案例」 | 「案例库里没找到，不过按常理……」 |
| 低相似度 | 「以下 5 条相似度低于下限，仅供参考，不作为主要依据」 | 「还有几条勉强能参考的案例」 |
| 无案例库 | 「无案例库，本技能不可用」 | 「我先按通用经验说几条，回头你再拿案例库来核」 |
| 下游衔接 | 「当前故障的原因初判建议接 `anomaly-triage-advisor`」 | 「综合来看你这台泵应该是……」 |

## 五、交付时必须说清的四件事

1. **检索范围**：案例库文件名、可检索案例总数、跳过了几条以及为什么。
2. **相似度情况**：下限是多少、达标几条、最高相似度、本次生效的权重（有没有用上部位维度）。
3. **逐条的匹配依据与不同点**：一条都不能省。
4. **免责说明**：结尾原样写出声明行，并提示当前故障的原因判定走 `anomaly-triage-advisor`；同一位号反复出同类故障走 `repeat-failure-detector`；没有案例库的原理问题走 `equipment-knowledge-qa`。
