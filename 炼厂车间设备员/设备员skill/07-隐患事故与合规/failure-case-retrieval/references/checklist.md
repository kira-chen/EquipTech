# 交付自检清单

运行脚本后、回答用户前逐项核对。

## 前置：案例库是否存在

- [ ] 用户确实提供了案例库或历史故障记录；**没有则已明确告知「本技能不可用」并终止，未列举任何通用知识案例**
- [ ] 案例库是 PDF 时，已先用平台 pdf 技能转为 txt/docx 并整理成表格，未声称脚本读了 PDF
- [ ] 脚本末行 `ok` 为 `true`；若为 `false`，已把 `error` 原文告知用户并终止
- [ ] `ok:false` 时未做任何形式的降级补位（含"先按经验说几条""加个免责声明再说"）

## 脚本执行

- [ ] `warnings` 已逐条告知用户，未隐去任何一条
- [ ] `cases.json` 与 `cases.md` 均已生成
- [ ] 回答中的案例编号、相似度、条数全部取自 `cases.json`，未自行统计或估算

## 命中为空

- [ ] `counts.matches` 为 0 时，回答中出现「**案例库中未检索到类似案例**」这句话
- [ ] 已说明检索了多少条案例、最高相似度是多少
- [ ] 未把 `lowSimilarity` 中的案例提上来充当命中结果
- [ ] 未自行调低 `--min-score` 凑结果；确需放宽已先征得用户同意并说明原下限

## 低相似度

- [ ] `lowSimilarity` 单独成节，排在命中案例之后
- [ ] 每条都带「相似度较低，仅供参考」标注
- [ ] 未按类似案例的规格逐条展开讲处置经验
- [ ] 相似度靠设备类型撑起来、现象其实不像的案例，已把「现象描述用词重合度低」这句差异讲给用户

## 逐条案例

- [ ] 每条都呈现了：现象、当时判定的原因、处置方式、效果、案例来源
- [ ] 每条都标注了**匹配依据**（哪些特征相似）
- [ ] 每条都标注了**不同点**（哪些条件不同）；无差异项时也写了「所比对字段均一致，但工况与设备实际状态仍须自行核实」
- [ ] 案例来源为空时，已明确告知用户该案例出处不可核实
- [ ] 缺失字段显示「—」，未臆造内容填空

## 免责与边界

- [ ] 结尾原样写出声明行：「案例中的原因是当时该案例的结论，不代表当前故障的原因；是否适用须结合当前设备实际情况判断。」
- [ ] 未把任何案例的原因表述为当前故障的原因（未出现「你这台泵是××坏了」）
- [ ] 未把案例处置直接表述为当前的行动指令（未出现「按××做法换掉就行」）
- [ ] 未引用案例库以外的任何案例或行业经验
- [ ] 已说明本结果是现象文本与字段的机械匹配，不是失效机理分析

## 分析段

- [ ] 已替换 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字
- [ ] 字数 200~400
- [ ] 四段结构齐全：命中情况与相似度水平、逐条可参考之处与不同点、与当前故障的关键差异、下一步建议
- [ ] 未在分析段引入案例库以外的信息

## 交付说明

- [ ] 已说明本次检索的权重口径（是否用上了故障部位维度；用了 `--weights` 自定义权重已说明非默认口径）
- [ ] 给了 `--fault-code` 时，已说明代码相同只影响排序、不计入相似度；代码相同但留在低相似度节的案例未被抬进命中
- [ ] SAP 通知单导出作案例库时，位号（功能位置）与设备编号（8 位流水号）分别呈现，未混用
- [ ] 通用声明行「本材料由脚本汇总、模型成文……厂内制度与系统数据为准。」保留
- [ ] 已提示：当前故障的原因初判可接 `01-日常运行监控与巡检/anomaly-triage-advisor`
- [ ] 案例较少或命中为空时，已建议补充现象关键特征（声音、温度、振动方向、发生时机）后重检
