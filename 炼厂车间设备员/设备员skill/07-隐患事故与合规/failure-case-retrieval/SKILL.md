# 故障案例检索（failure-case-retrieval）

面向中石化体系炼化厂车间（运行部）设备员，从本厂历史故障记录、SAP PM 通知单导出、集团或兄弟厂案例汇编中检索类似案例，提供处置经验参考。**只返回案例库中实际存在的案例；模型不得凭通用知识编造案例，也不得把案例结论直接套用为当前故障的原因。**

## 适用条件
- 用户说"有没有类似案例 / 以前出过这种问题吗 / 案例库查一下 / 案例汇编里有没有这种现象"，并描述现象、提供案例库。
- 检索维度：现象描述（主维度）、设备类型、故障部位；可选型号、SAP 损坏/原因代码（M2 故障报告通知单常带）。
- 车间设备员可做的部分：检索、整理类似案例与处置经验，作为缺陷处理与检修方案的参考线索。
- 由 XX 归口：当前故障的原因判定与失效分析由设备工程师/专业技术部门归口；事故定性与责任认定由公司设备管理部门（机动部/设备部）与安全环保部门归口，本技能不做。
- 不适用：当前故障的原因判定（用 anomaly-triage-advisor）；同一位号重复故障统计（用 repeat-failure-detector）；没有案例库的原理性问题（用 equipment-knowledge-qa）；引用无出处的外部案例。

## 前提条件
- 输入：案例库或历史故障记录（`.xlsx` / 同结构 CSV 目录 / `.docx` Word 表格 / `.md` 管道表格），以及当前故障的现象描述。SAP PM 通知单导出（IW28/IW29 列名：通知单、功能位置、设备、设备描述、描述、损坏代码、对象部件、原因代码）可直接作案例库。**无案例库时本技能不可用，须明确告知用户，不得用通用知识替代。**
- **PDF 先用平台 pdf 技能转为 txt/docx 再传入，脚本不读 PDF；扫描件需 OCR。** 转出的文本须整理成表格（一行一案例、首行列名）才能检索。
- 必填信息：当前现象描述、设备类型。可选：位号、型号、故障部位、SAP 损坏/原因代码、发生工况。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得凭记忆列举案例。**

## 操作步骤
1. **确认检索条件** —— 现象描述、设备类型、部位、型号、故障代码。**描述越具体检索越准；描述笼统时提示用户补充关键特征（声音、温度、振动方向、发生时机）。** 大机组（汽轮机、离心/往复/螺杆压缩机、挤压造粒机）按机型分别归类，不互通。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/retrieve.js" --cases "<案例库路径>" --symptom "<现象描述>" --equip-type "<设备类型>" --out "<工作目录>/案例检索"
   ```
   可选：`--part "<故障部位>"`、`--model "<型号>"`、`--fault-code "<SAP 损坏/原因代码>"`（代码相同者排序优先，不计入相似度）、`--top <返回条数，默认 5>`、`--min-score <相似度下限，默认 0.3>`、`--weights "text=0.55,type=0.30,part=0.15"`（三项之和须为 1，默认口径见 `references/retrieval-rules.md`）、`--all-fields`。默认输出目录为系统临时目录 `<os.tmpdir()>/fcr-out`，建议始终传 `--out`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（案例库无法解析/字段缺失/命中为空/相似度普遍偏低/自定义权重等）。脚本用法详见 `scripts/README.md`。
   - 命中为空：明确回答"案例库中未检索到类似案例"，**绝不降低标准返回不相关案例，也不得用通用知识补充**。
   - 相似度低于下限的结果：标注"相似度较低，仅供参考"，**不得作为主要参考呈现**。
3. **读取 cases.json** —— 从 `<输出目录>/cases.json` 获取：`matches`（命中案例：案例编号/通知单号、位号与设备编号、现象、原因、处置方式、效果、来源、相似度、匹配依据与不同点）、`lowSimilarity`、`counts`、`meta.weights`（本次生效权重）。
4. **组织回答** —— 逐条呈现案例：现象、当时判定的原因、处置方式、效果、案例来源。**每条必须标注匹配依据（哪些特征相似）与不同点（哪些条件不同）。结尾必须说明："案例中的原因是当时该案例的结论，不代表当前故障的原因；是否适用须结合当前设备实际情况判断。"**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后回答用户，必要时输出 `cases.md`。当前故障的原因初判接 `anomaly-triage-advisor`。

## 预期结果
- 直接回答用户问题（对话形式），逐条呈现类似案例与匹配依据；必要时输出 `cases.md`（五节：检索概览、命中案例、低相似度案例、检索结果解读、使用说明；有 warning 时附数据提示）与 `cases.json`。
- 回答中说明：检索案例总数、命中数、相似度情况与生效权重、案例与当前情况的差异点。
- 产出带两行声明：案例结论免责声明行，以及"本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。"

## 不适用范围
- 不编造案例，不引用无出处的外部经验。
- 不把案例结论作为当前故障的原因判定；不做事故定性与责任认定。
- 不替代专业诊断与失效分析。
- 无案例库时不降级为通用知识问答。
