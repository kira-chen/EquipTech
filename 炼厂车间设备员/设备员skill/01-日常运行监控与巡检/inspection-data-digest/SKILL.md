# 巡检点检数据汇总（inspection-data-digest）

面向中石化体系炼化厂车间（运行部）设备员，把操作工巡检（智能巡检 APP 导出，一行一检查项）、专职点检（点检仪导出，含测值与是否报警）、状态监测（测振/测温/油液，只有测值与限值）三条线的记录合并成一份车间设备日状态一览，交车间设备主任复核、必要时报公司设备管理部门。**合并、按位号聚合、异常判定与计数一律由脚本完成，模型只负责解读与成文；不得手工统计或改写判定结果。**

## 适用条件
- 用户说"汇总今天的巡检 / 点检数据汇总 / 智能巡检导出表并一下 / 设备状态一览 / 巡检发现了哪些问题"，并给出（或即将给出）一份或多份巡检记录表。
- 支持多来源合并：智能巡检 APP 导出（功能位置-检查项-测值-是否报警）、点检仪导出、状态监测（无"检查结果"列，用是否报警或测值对限值判异常）、传统一行一设备的巡检表；字段口径见 `references/input-spec.md`。
- 车间设备员可做：巡检点检数据汇总、异常项整理、漏检与特护设备提示、转缺陷登记（维修通知单）建议。
- 不适用：只有口头描述无记录表；生成待执行任务清单；单台设备的深度故障诊断；重新判定执行人填写的巡检结论（巡检结论以执行人为准，异常定性由专业工程师归口）。

## 前提条件
- 输入：一个或多个 `.xlsx`（或同结构 CSV 目录，UTF-8 或 GBK），可含工作表「巡检记录/巡检明细」「点检记录/点检数据」「状态监测」，至少提供其中一张；工作表名不同时用 `--source-type` 指定来源类型。
- 必填信息：车间名称、汇总日期（YYYY-MM-DD）。可选：设备台账（识别漏检与特护标记，可直接用 SAP PM 技术对象清单）、上一日 status.json（状态变化对比）、班次说明、班次日起算时刻（夜班跨 0 点记录归属）。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得手工汇总任何数据。**

## 数据获取（MCP）

平台接入了业务系统 MCP 服务时，按下表调用工具取数，不再请用户上传导出文件；未接入时按操作步骤请用户提供系统导出文件。工具全部只读，不在业务系统里创建或修改任何单据。

| 服务 | 工具 | 参数 | 交给脚本 |
|---|---|---|---|
| 点检巡检App | `get_inspection_records` | `workshop`：车间名；`for_skill=inspection-data-digest` | `--input`（目录 A） |
| 设备资产管理 | `get_equipment_ledger` | `workshop`：车间名；`for_skill=inspection-task-dispatch` | `--ledger`（目录 B） |

取数后：

1. 工具返回下载链接（60 分钟内有效，过期重新调用）。csv 按原文件名放进新建的空目录，不改文件名，不与其他技能的文件混放；表中目录字母相同的放同一个目录，不同字母分开放，把目录作为“交给脚本”一列的参数值。
2. `get_inspection_records`：只返回 `end_date` 当天的记录（默认今天）；汇总别的日期时传 `end_date`=汇总日。两个工具都要传 `workshop`（与 `--workshop` 一致），不传会把全厂各车间的记录和台账混在一起。
3. `get_equipment_ledger`：`for_skill=inspection-task-dispatch` 输出带「特护」「是否需巡检」列的精简台账，不需巡检、停用的设备不进漏检清单；特护以「特护」列为准，重要度 A 不等于特护。

## 操作步骤
1. **确认车间与汇总日期** —— 从用户消息或文件名中提取；不明确时向用户确认一次。多文件时逐一说明各文件对应的来源类型，来源不明确时向用户确认一次。夜班记录跨 0 点时，问清班次日起算时刻（常见 08:00）。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/digest.js" --input "<xlsx路径>[,<xlsx路径2>...]" --workshop "<车间名>" --date <YYYY-MM-DD> --out "<输入同目录>/巡检汇总"
   ```
   可选：`--ledger "<设备台账xlsx>"`（识别漏检、特护标记）、`--prev "<上一日 status.json>"`（状态变化）、`--shift "<班次说明>"`（仅写入报告头）、`--shift-window HH:MM`（班次日起算时刻，早于该时刻的记录归前一班次日）、`--source-type patrol|spotcheck|monitor`（工作表名无法识别时指定来源类型）。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（缺表/缺列/记录时间超出日期范围/带单位测值已剥离单位/同一检查项多条记录冲突等）。脚本用法详见 `scripts/README.md`。
   - 判定依据按优先级：检查结果 → 是否报警 → 测值对上限/下限 → 运行状态列；四者都没有的设备进**未判定**，脚本不默认为正常。
   - 同一设备同一检查项结论冲突（一条正常一条异常）：脚本按 `references/digest-rules.md` 的就严原则取异常，并在 `conflicts` 中单列，**不得静默取其一**；不同检查项一正常一异常不算冲突，是正常的"一台设备多项检查"。
   - 同一设备没有异常项、但有检查项未判定（如「法兰泄漏 待查」）：整机判未判定，进 `unknownState` 单列并写明哪一项，**不得按其余检查项正常就判设备正常**。
   - 未提供设备台账时不输出漏检清单，改为 warning 提示"未提供台账，无法识别漏检"，**不得按记录表倒推设备总数**。
3. **读取 status.json** —— 从 `<输出目录>/status.json` 获取：`byEquipment`（逐台设备：位号、设备编号、名称、特护标记、`state` 正常/异常/未判定、`stateCn` 六档显示、检查项数与异常项数、逐条结果与判定依据）、`abnormal`（异常项清单，含异常检查项明细）、`missed`（漏检清单）、`conflicts`（记录冲突，定位到检查项）、`counts`（含 `sixTier` 六档计数、`special`/`specialAbnormal` 特护计数）、`changed`（有 --prev 时的状态变化）。
4. **撰写"设备状态分析"** —— 读 `references/digest-rules.md` 的表述口径，撰写 200~400 字，按"总体状态 → 异常项与影响（特护设备优先）→ 漏检与数据缺口 → 需上报或跟进事项"结构，替换 `digest.md` 中 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字。**设备数量、异常计数一律引用 status.json，不得自行统计。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `digest.md` 与 `status.json`。异常项需要登记缺陷、开维修通知单时，提示用户可接 `defect-intake-grading` 技能；异常需要初判原因时接 `anomaly-triage-advisor`。

## 预期结果
- `digest.md`：车间设备日状态一览，含 一、状态概览（六档 + 特护 + 漏检 + 冲突）、二、异常项清单、三、漏检清单、四、记录冲突、五、未判定项、六、状态变化、七、设备状态分析 七个部分，另有"附：数据提示"（有 warnings 时）与声明行。
- `status.json`：逐台设备状态与异常明细，供 `equipment-daily-report` 等下游技能使用；`summary.json`：脚本末行摘要。
- 必须保留声明行："本材料由脚本汇总、模型成文，仅供设备员复核参考，不替代审批、定性、验收与签字；厂内制度与系统数据为准。"（脚本已写入 md 末尾，不得删除）。
- 交付时向用户说明：数据来源文件与来源类型、判定依据、异常数量（其中特护几台）、漏检数量、记录冲突数量、脚本 warnings（如有）、分析段需设备员复核。

## 不适用范围
- 不重新判定巡检结论（以记录表中执行人填写的结论、报警标志或限值为准），不替执行人补填未检项。
- 不做故障原因诊断与处置决策（异常初判用 anomaly-triage-advisor），异常定性由专业工程师归口。
- 不做跨日趋势分析（趋势用 parameter-trend-alert），不生成维修工单（工单由计划员/维修单位在 SAP 创建，设备员提报的是维修通知单）。
