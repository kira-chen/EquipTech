# 泄漏点登记与修复跟踪（leak-point-tracker）

面向中石化体系炼化厂**车间（运行部）设备员**，把 LDAR 系统检测结果与现场发现的跑冒滴漏统一登记，跟踪到修复闭环，并按静/动密封点分别核算泄漏率（‰）。**泄漏认定、修复时限、超期与泄漏率一律由脚本按规则算出，模型只负责成文说明；不得手工计算时限、放宽判定或估算泄漏率。**

## 适用条件
- 用户说"登记漏点 / 漏点台账 / LDAR 数据处理 / 哪些漏点超期没修 / 泄漏整改进度 / 本月静密封点泄漏率多少"，并给出（或即将给出）泄漏检测数据或漏点记录表。
- 覆盖两类来源：LDAR 系统（仪器）检测数据（含净检测值 μmol/mol）、现场巡检发现的可见泄漏（滴漏/渗漏，无检测值）。
- **车间设备员可做的部分**：漏点登记与台账、修复进度跟踪催办、超期与延迟修复清单、静/动密封点泄漏率统计、需维修的提 SAP PM **维修通知单**、向车间设备主任 / 公司设备管理部门汇报。
- **由 XX 归口（本技能只记录不判定）**：法定 LDAR 检测与检测报告编制、泄漏率考核线与排放达标判定由公司环保（HSE）部门及生态环境主管部门归口；延迟修复的审批由厂内 LDAR 管理流程归口，脚本只看台账里有没有批准日期；工单创建与定工时由计划员/维修单位归口。
- 不适用：废气废水排放浓度的日常达标核查（用 emission-daily-check）；泄漏根本原因分析；法定 LDAR 检测报告与备案材料编制。

## 前提条件
- 输入：一个 `.xlsx`（或同结构 CSV 目录，UTF-8 或 GBK），含工作表「检测记录」「漏点记录」或「LDAR检测数据」，字段见 `references/input-spec.md`。LDAR 系统 / SAP PM 导出列名（密封点标签号、功能位置、设备、工厂区段、组件子类型、密封类型、检测方法、检测净值、是否不可达、复测日期、延迟修复批准日期）可直接读取。
- 必填信息：车间名称、统计截止日期（YYYY-MM-DD）。可选：历史漏点台账（续跟踪）、密封点总数（算泄漏率，`--seal-points`）、厂内泄漏率考核线、厂内阈值与时限口径。
- 环境：可执行 Node.js ≥ 18，脚本仅用内置模块，无需 npm 安装。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得手工判定泄漏、计算时限或估算泄漏率。**

## 操作步骤
1. **确认车间、截止日期与口径** —— 从用户消息或文件名中提取。泄漏认定阈值按介质类型区分（见 `references/ldar-rules.md`），用户若指定厂内口径则用参数覆盖并在产出中注明。要算泄漏率必须有密封点总数：问用户要密封点台账或"静 N / 动 M"两个数；要判是否达标必须有厂内考核线，**没有就只列泄漏率不判**。
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/track.js" --input "<xlsx路径>" --workshop "<车间名>" --date <YYYY-MM-DD> --out "<输入同目录>/漏点跟踪"
   ```
   可选：`--ledger "<历史漏点台账xlsx>"`、`--seal-points "<密封点台账xlsx>"` 或 `--seal-points "静:12000,动:800"`、`--static-limit <‰>`、`--dynamic-limit <‰>`、`--threshold-voc <阈值>`、`--threshold-liquid <阈值>`、`--repair-days <首次修复时限天数>`、`--final-days <最终修复时限天数>`。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（缺表/缺列/检测值无法解析/密封点编号重复/状态取值非法/未提供密封点总数/静动密封无法识别等）。脚本用法详见 `scripts/README.md`。
   - 检测值为空或无法解析的记录：输出 null（显示 —）并归入 `undetermined`（未判定）单列一节，**绝不按 0 计为不泄漏**。带单位的值（如「3200ppm」）会剥离单位取数。
   - 无检测值的可见泄漏（滴漏/渗漏）：按定性口径单独处理，不与仪器检测值混算。
   - 状态为「延迟修复」：有批准日期的单列「延迟修复（经批准）」不计超期；**无批准日期的进未判定**，既不按已批准也不按超期。
   - 不可达点无检测值：进未判定，不按不泄漏。
   - 未提供 `--seal-points`：泄漏率为 null，报告单列「未提供密封点总数」，不得写 0‰。
3. **读取 leaks.json** —— 从 `<输出目录>/leaks.json` 获取：`counts`、`metrics.leakRate`（静/动泄漏率、分母来源、考核线与判定）、`newLeaks`、`open`、`overdue`、`delayed`、`repaired`、`undetermined`、`unreachable`、`ledger`（更新后的全量台账）。
4. **撰写"泄漏管理情况说明"** —— 读 `references/ldar-rules.md` 的表述口径，撰写 200~400 字，按"总体情况 → 新增漏点 → 超期未修与延迟修复 → 修复闭环与泄漏率 → 下一步安排"结构，替换 `leak-report.md` 中 `<!-- ANALYSIS_START -->` 与 `<!-- ANALYSIS_END -->` 之间的占位文字。**漏点数量、超期天数、泄漏率一律引用 leaks.json。** 交付对象写车间设备主任 / 公司设备管理部门。
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `leak-report.md`、`leaks.json` 与更新后的台账 `ledger.xlsx`。**报告中的合规提示行与制度出处行不得删除或改写。**

## 预期结果
- `leak-report.md`：泄漏点管理报告，九节：一、总体概览（含静/动密封点泄漏率表与两类来源分列）；二、本期新增漏点；三、超期未修清单；四、未修复（期限内）；五、延迟修复（经批准）；六、未判定清单；七、本期修复闭环；八、编号重复与数据提示；九、泄漏管理情况说明；有 warnings 时附「数据提示」。
- `leaks.json` 与 `ledger.xlsx`：结构化漏点数据与更新后的全量台账（含设备编号、密封类型、检测方法、不可达点、复测日期、延迟修复批准日期等 LDAR 系统字段）；`summary.json`：脚本末行摘要。
- 交付时向用户说明：数据来源、新增/超期/延迟/闭环数量、静/动密封点泄漏率与分母来源、采用的阈值与时限口径、脚本 warnings（如有）。

## 不适用范围
- 不做泄漏根本原因分析与密封选型建议。
- 不编制法定 LDAR 检测报告、备案表与排污许可证执行报告。
- 不核算 VOCs 排放量，不替代环保部门与生态环境主管部门的达标判定；泄漏率考核线以厂内指标为准，脚本不内置考核线。
- 不替代泄漏应急处置流程，不代为下达停车或隔离指令；不替代延迟修复审批。
