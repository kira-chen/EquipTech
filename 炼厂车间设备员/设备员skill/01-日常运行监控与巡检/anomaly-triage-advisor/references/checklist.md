# 交付自检清单

## 脚本执行
- [ ] 末行 JSON 的 `ok` 为 `true`；为 `false` 时已把 `error` 原文告知用户并终止，**未凭印象手工初判**
- [ ] `warnings` 已逐条告知用户
- [ ] `triage.json`、`triage.md`、`summary.json` 均已生成

## 信息完整性
- [ ] 设备类型、现象、发现时间、是否突发、是否影响运行五项已逐一核对
- [ ] 缺项已一次性列出，未逐个追问
- [ ] 未用假设值填补后直接给结论

## 候选原因（最关键一节）
- [ ] 候选原因、可能性排序、规则号全部来自 `triage.json`，**未自行增删或调整排序**
- [ ] 每条原因都带「需核实」标记，**没有出现「确认是」「就是」「基本可以断定」这类定论措辞**
- [ ] 每条原因都注明了依据来源（参数表某行 / 历史记录某条 / 用户提供的现象描述 / 口径文件规则号）
- [ ] 无支持依据的原因已标「**推测，待核实**」，未与有依据的原因混同呈现
- [ ] **未判定项单列一节，且明确说明「仍保留在候选中，不得视为已排除」**
- [ ] **没有因为缺数据就把某个可能原因从候选里删掉**

## 专业结论边界
- [ ] 未判读频谱图、油液分析报告、无损检测报告的专业结论；安全阀未给整定/校验结论（以校验报告为准）
- [ ] 用户已给出的结论性描述（如「频谱以 2 倍频为主」）作为依据采信时，已注明来源为用户提供
- [ ] 需要精密诊断的项已列为核实项，并注明由诊断或检测人员出具结论

## 动作与决策边界
- [ ] **未给出是否停机、是否降负荷、是否抢修的意见**
- [ ] 关注度用 红/橙/黄 三档，**未写成 A/B/C**（与设备重要度撞名），只表述为「建议尽快核实 / 加密监控 / 按计划跟踪」，未表述为处置指令
- [ ] 关注度未判定时，已说明缺哪两项信息，未按最轻或最重默认；特护设备已按红提示并注明
- [ ] 上报建议已说明是建议，上报对象为设备工程师 / 车间设备主任（特护设备同步公司设备管理部门），最终由设备工程师与调度按厂内规定决定
- [ ] 确认为缺陷时，只提示在 SAP 创建维修通知单，未生成工单、未定工时与备件

## 类型覆盖
- [ ] 设备类型未覆盖时，报告第二节已打出提示，**只给通用框架，未编造具体原因**
- [ ] 未把其他设备类型的原因表套用到未覆盖的机型上

## 声明行
- [ ] 报告开头与结尾均保留「**本结论为初判辅助，由脚本汇总、模型成文，不替代专业诊断与停机决策，须由设备工程师或车间设备主任复核；厂内制度与系统数据为准**」，**未删除或改写**
- [ ] 报告不含 emoji，提示用「【注意】」

## 交付说明
- [ ] 已说明本次初判依据了哪些数据（参数几项、历史几条）
- [ ] 已说明哪些原因因缺数据未判定、缺的是哪些字段
- [ ] 已说明补充什么数据后可重新初判
- [ ] 需要查同类历史案例时，已提示可接 `07-隐患事故与合规/failure-case-retrieval`
