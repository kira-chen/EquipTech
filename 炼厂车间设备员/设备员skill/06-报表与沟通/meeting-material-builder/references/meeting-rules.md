# 会议材料口径与表述规范

## 一、听众层级决定详略（核心）

汇报稿写给谁，决定了写多细。**这个参数不设默认值**，必须由用户指定。

听众层级按中石化组织层级三档：**车间（运行部）→ 分厂/作业部（设备科）→ 公司（设备管理部门 / 公司领导）**。各厂名称不同，用 `--audience-spec "<厂内名称>"` 给出，只作展示；需要改详略档位时加 `:high|medium|low`。旧称「设备部」「厂领导」不再接受。

| 层级 | 详略 | 位号 | 时间权重侧重 |
|---|---|---|---|
| 车间 | 高 | 保留具体位号与细节 | 主要工作 30% |
| 分厂 | 中 | 保留关键位号，弱化过程细节 | 存在问题 25% |
| 公司 | 低 | **去除位号、工单号与 SAP 单号，保留设备名称** | 需决策 30%、关键指标 30% |

任何层级都可加 `--hide-tags` 强制去位号（例如材料要外发）。去位号同样作用于需决策事项和上次遗留事项（`--need-decision`、`--pending` 原文里的位号、工单号也会去掉）。`--weights` 可覆盖六个环节的时间权重（六项齐全、和为 1）。

### 为什么公司层级要去位号

公司领导关心的是「哪类设备出了什么性质的问题、要他定什么」，不是「P-1101B」。位号对他是噪声。

但**保留设备名称**：「回流泵B 机封滴漏」比「相关设备异常」有信息量得多。去位号不等于去信息。

### 时间分配

按听众层级加权。公司层级 8 分钟的汇报，需决策事项要占 2.4 分钟；车间 15 分钟的例会，主要工作占 4.5 分钟。这个差异是实质性的：跟领导汇报不讲清要他定什么，这次汇报就白开了。权重来源（默认 / 用户指定）写在提纲与 `outline.json.meta.weightsSource`。

## 二、数字的硬规则

**所有数字来自输入数据，不新增、不修改、不美化。**

| 场景 | 应写 | 不得写 |
|---|---|---|
| 完成率 25% | 「完成率 25%」 | 「完成率约三成」「完成率 25%，较上月有所提升」（除非数据里有上月值） |
| 超期 3 张 | 「超期 3 张」 | 「个别工单超期」 |
| 无该指标 | 不写 | 编一个 |

每个指标在 `outline.json` 中带 `source` 字段，标明来自哪个文件。报告固定带声明行「本稿数字均引自所列数据来源，未做任何新增、修改或美化」。

### 与周报月报的边界

完好率、泄漏率、计划完成率这些指标**在 `equipment-weekly-monthly-report` 里算**，本技能只把它的 `periodic.json` 组织成稿：指标键映射为中文标签（`intactRate` → 设备完好率 %，`staticLeakRate` → 静密封点泄漏率 ‰），为 null 的指标保留 null 写「未计算」，`dataGaps.recompute` 里「需按厂内口径复算」的指标进问题项。本技能不重算、不补算；用户给的是 xlsx 台账时，提示先跑对应报表技能。

## 三、议题无数据支撑

用 `--topics` 指定议题时，若某议题在所提供数据中找不到对应内容：

- 列入 `noData`，稿中写「该议题暂无数据支撑，需补充」
- warning 提示
- **绝不编造内容填充**

领导问到一个你没数据的议题，说「这块数据还没到，下次补」是专业的；编一个数说出去，下次对不上就是事故。

## 四、不代拟的三处

| 章节 | 为什么不代拟 |
|---|---|
| 主要工作 | 本技能看不到实际做了什么，编出来就是虚构工作内容 |
| 下步打算 | 属于汇报人的判断与承诺 |
| 需决策事项的具体内容与方案 | 请求领导定什么、有哪几个选项，只有汇报人清楚 |

这三处留占位符，明确写「由汇报人补充」。

例外：上游数据里已经闭环的事项是事实，不是代拟。隐患跟踪中 `bucket=closed`（已整改且已验收）的重大隐患列在「主要工作」占位符之前，注明「可作为工作成果引用」，不再列入「存在问题」。已整改但未验收的仍算未闭环，留在「存在问题」。

## 五、存在问题的表述

**只陈述事实与影响，不做责任归因。**

| 应写 | 不得写 |
|---|---|
| 「WO-XXX 超期 6 天，责任方检修二队」 | 「二队拖延」 |
| 「完成率 25%」 | 「执行不力」 |
| 「3 台报警器失效未修复」 | 「安全管理松懈」 |

责任归因是考核的事，不是汇报材料的事。写进去只会让会议变成扯皮。

## 六、开场一句话结论

分析段占位符处由模型撰写，要求：

- 一句话，不超过 40 字
- 与下方指标一致，**不得自行拔高或淡化**
- 如「本月设备整体平稳，工单闭环率偏低，有 2 项需协调事项」

## 七、内容量与时长匹配

脚本按「要点数 / 分钟」粗算：

- 大于 3 项/分钟 → 提示内容偏大，建议精简或延长
- 小于 0.5 项/分钟 → 提示内容偏少，可适当补充

这只是提示，不强制截断。

## 八、输入来源

| 来源 | 说明 |
|---|---|
| 上游技能 JSON | 推荐。自动识别巡检汇总、工单跟踪、缺陷登记、隐患跟踪、周报月报（periodic.json）、设备日报（daily.json，含特护设备异常） |
| `.md` 报表 | 作为已有材料引用 |
| `.xlsx` 表格 | **本技能不做二次统计**，warning 提示先用对应报表技能生成 JSON |

识别顺序按特征字段独占性从强到弱。隐患跟踪与工单跟踪 JSON 都带 `counts` / `metrics` / `overdue`，早期样例的隐患 JSON 还带 `metrics.closeRate`，若放在工单跟踪之后会被误判，因此先判 `majorHazards`。隐患闭环率读 `metrics.closureRate`（hazard-closure-tracker 的实际字段），兼容旧字段 `closeRate`。

## 九、PPT 交付

本技能输出 Markdown 文字稿与提纲，另在 `outline.json` 的 `slides` 数组给出逐页 `title / bullets / notes` 的结构化提纲（封面 + 六节 + 无数据议题）。用户要 PPT 时把 `slides` 交给 pptx 相关技能或工具转换，**不得手写 pptx XML**。产出 md 不用 emoji，醒目提示用「【注意】」。
