# 交付自检清单

## 脚本执行
- [ ] 末行 JSON 的 `ok` 为 `true`；为 `false` 时已告知用户 `error` 原文并终止，未手工成文
- [ ] `warnings` 已逐条告知用户
- [ ] `notice.json`、`notice.md`、`summary.json` 均已生成

## 要素完整性
- [ ] 七要素逐项核对过（位号、时间、经过、当前状态、影响、已采取措施、后续安排）
- [ ] `missing` 中的缺失要素已**一次性**列给用户，未逐个追问
- [ ] **未用推测填补任何缺失要素**：影响没填没写成「无影响」、状态没填没按「已恢复」写、时间没填没按发现时间倒推、措施没填没写成「正在处理」
- [ ] 影响一栏按生产、安全、环保三方面分别写明；确无影响的已明确写「无」，不是留空

## 原因（硬约束）
- [ ] 原因分析情况一节写的是「**原因正在分析中**」
- [ ] 通报正文中**没有任何原因推测**——包括「初步判断」「可能是」「怀疑」一类的软推测
- [ ] 用户提供的原因判断未写入正文；确有正式调查结论的，已用 `--cause-confirmed` 并注明结论来源

## 推测性/定性表述（硬约束）
- [ ] `speculative` 数组中每一条都已处理，**没有一条原样留在通报里**
- [ ] 归因类（S11~S16）：已删去因果表述，改为时序陈述
- [ ] 责任类（S21~S26）：已删去责任认定，改为客观的操作动作与参数陈述
- [ ] 厂家质量类（S31~S33）：已改为「待检测鉴定后确认」一类的表述
- [ ] 定性类（S41~S43）：**通报中没有出现「事故」一词**（除非已正式定性并注明定性文号）
- [ ] 程度夸大类（S51~S53）：保留的每一处「严重/重大」都有量化依据；无依据的已换成数值描述
- [ ] 个人追责类（N1）：**通报中没有指向个人的追责性表述**，一律写岗位或班组

## 上报流程
- [ ] `escalationHint` 为 `true` 时，已向用户提示「**请按厂内规定判断是否需走事故快报流程，可使用 incident-flash-report 技能**」
- [ ] 已说明脚本只提示不判定，是否构成需上报事故由用户按厂内规定判断
- [ ] 通报中**未对事件性质下任何结论**（未写「构成 XX 事故」「属于 XX 级」）
- [ ] 已说明：没触发提示也不等于不用上报，检测靠关键词，可能漏检
- [ ] `unplannedShutdownHint` 为 `true` 时，已提示「可能构成非计划停工事件，按《炼化企业非计划停工管理规定》另行报送，与事故快报分开」，通报中未写「构成非计划停工事件」结论
- [ ] `--scope` 为 车间 / 分厂 / 公司 之一，厂内名称用 `--scope-name` 给出
- [ ] 传了 `--hazard-level-confirmed` 的，通报中已注明隐患分级依据（文号或台账编号）

## 成文
- [ ] 七节结构齐全：概况、经过、影响、措施、原因分析情况、后续安排、举一反三
- [ ] 「举一反三」一节只写可执行的检查动作，**未作原因推断、未作责任评价**
- [ ] 后续安排含责任岗位、完成时限、验证方式三要素
- [ ] **末尾保留声明行「本通报为情况告知，事件原因与性质以正式调查结论为准」，一字未改**
- [ ] 产出无 emoji，醒目提示用「【注意】」
- [ ] md 中的时间、位号、数值均与 `notice.json` 一致，未自行增删
