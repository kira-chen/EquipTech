# 通报措辞规范与禁用表述清单

## 一、根本原则

设备事件通报是**情况告知**，不是调查结论，也不是处理决定。通报里只能出现三样东西：

1. **已确认的客观事实**——看到的现象、读到的数值、做过的动作、现在的状态。
2. **已完成的处置**——谁在什么时间做了什么，做完之后是什么状态。
3. **下一步安排**——什么时间由哪个岗位做什么，怎么验证。

不能出现的：**原因结论、责任认定、性质定性、程度评价**。这四类要么等正式调查结论，要么写「待核实」，要么根本不写。

### 原因一栏的唯一写法

原因未经调查确认时，通报的「原因分析情况」一节**只能写「原因正在分析中」**。

这不是措辞谨慎的问题。通报一旦发出就在车间里传开，写进去的推测会被当成结论用——后面调查出别的结论，纠正的成本远大于当初多等两天。脚本对此做了硬拦截：`--cause` 传进来的内容，除非同时给 `--cause-confirmed`（声明原因已由正式调查确认），否则不会写进 md 正文，只在 warning 里提示。

## 二、禁用表述清单（脚本逐条检测，带规则号）

> **规则同源说明**：本清单 S1x~S4x（归因 / 责任 / 厂家质量 / 定性）与 `07-隐患事故与合规/failure-investigation-assistant/scripts/lib/rules.js` 的 C1~C8、J1~J5 是同一套口径（未经调查不得归因、定性、认定责任）。S41 的「事故」负向排除词表（事故池 / 事故柜 / 事故罩 / 事故照明 / 事故状态 / 事故应急 / 事故预案 / 事故柴油 / 事故泵 / 事故排放 / 事故水 / 事故阀 / 事故排污 / 事故电源 / 事故风机 / 事故隔离）两边必须一致。目前两处各自维护、没有单一事实源：**改一处须同步另一处**，对方 selftest 2.1z 会比对两边 J1/S41 正则。

### 归因类 S1x —— 未经调查不得写因果

| 规则号 | 禁用表述 | 为什么不能写 | 替代写法 |
|---|---|---|---|
| S11 | 由于…… | 在调查结论出具前陈述因果关系 | 删去因果连接词，只按时间顺序陈述：「08时20分发现……，08时35分切换备用泵」 |
| S12 | 因为……、因而、系因 | 同上 | 同上 |
| S13 | 导致、致使 | 断言了尚未确认的因果链条 | 「其后出现……」「随后……」——只说先后，不说因果 |
| S14 | 造成 | 同上 | 「现场出现……」，原因一节写「原因正在分析中」 |
| S15 | 原因是、原因为、起因是、根本原因 | 在正式调查结论前给出原因结论 | 统一写「原因正在分析中」 |
| S16 | 系……所致、……所致 | 同上 | 统一写「原因正在分析中」 |

**注意**：不是所有「导致」都错。如果写的是已被确认的物理事实（如「切断电源后泵停运」），用「随后」「其后」照样说得清，没必要冒险用因果词。规则一律报出来，由人判断是否改。

### 责任类 S2x —— 通报不做责任认定

| 规则号 | 禁用表述 | 为什么不能写 | 替代写法 |
|---|---|---|---|
| S21 | 操作不当、操作失误、误操作 | 属于责任认定，须由调查组结论确定 | 客观描述当时的操作动作与参数：「当班人员于08时30分执行了……操作，此时出口压力为……」 |
| S22 | 违章、违规、违反操作规程 | 属于责任认定与定性 | 如确有检查发现，引用检查记录编号并写「待核实」；否则删去 |
| S23 | 失职、渎职、履职不到位 | 属于责任认定 | 删去。责任认定以正式调查结论为准 |
| S24 | 未按规程、不按规程、未执行规程 | 属于责任认定，须有核查依据 | 陈述实际操作步骤与规程要求的差异，并标注「待核实」 |
| S25 | 疏忽、大意、麻痹 | 对人员主观状态的推断，无从核实 | 删去，只陈述客观事实 |
| S26 | 把关不严、监管不力、管理缺失、管理不到位 | 属于管理责任认定 | 删去。如需提管理改进，放进「举一反三」一节，写成建议而非评价 |

### 厂家质量类 S3x —— 涉及外部责任，未经鉴定不得断言

| 规则号 | 禁用表述 | 为什么不能写 | 替代写法 |
|---|---|---|---|
| S31 | 厂家质量问题、厂家责任、制造质量问题 | 涉及外部责任认定，须经检测鉴定；写进通报可能影响后续索赔与法律关系 | 「部件失效形式待检测鉴定后确认」 |
| S32 | 设备本身缺陷、设计缺陷、先天缺陷、固有缺陷 | 涉及设计制造责任认定，须经鉴定 | 「设备状态待进一步检查确认」 |
| S33 | 质量不合格、不合格产品、以次充好、假冒伪劣 | 涉及质量判定与外部责任，须有检验报告 | 有检验报告则引用报告编号；否则删去 |

### 定性类 S4x —— 事件性质由正式调查确定

| 规则号 | 禁用表述 | 为什么不能写 | 替代写法 |
|---|---|---|---|
| S41 | 事故 | **「事故」是正式定性用语**，未经定性不得使用 | 「事件」「故障」「异常」「险肇事件」 |
| S42 | 严重违反、恶意、蓄意、故意 | 属于性质与主观故意的认定 | 删去 |
| S43 | 重大隐患、重大问题、重大风险 | 「重大」是分级定性用语，须依据隐患分级标准（隐患等级只认 重大隐患 / 一般隐患，由安全环保部门归口） | 已按厂内标准分级的，传 `--hazard-level-confirmed` 并在通报中注明分级依据（文号或隐患台账编号）；否则写「已发现的问题」 |

### 程度夸大类 S5x —— 需有量化依据（severity = review）

这一类不是绝对禁用，而是**必须有依据才能用**。脚本把它标为 `review`：有数据支撑就留着，没有就换成量化描述。

| 规则号 | 表述 | 使用条件 | 替代写法 |
|---|---|---|---|
| S51 | 严重 | 须有量化依据（数值、范围、时长） | 「泄漏量约 0.5 kg」「停车 4 小时」「影响产量约 XX 吨」 |
| S52 | 重大 | 须依据厂内分级标准 | 引用分级结论，或改为中性描述 |
| S53 | 恶劣、极其、非常严重、十分严重、大面积 | 须有量化依据 | 同 S51 |

### 个人追责类 N1

| 规则号 | 检测方式 | 替代写法 |
|---|---|---|
| N1 | 「人员身份标记（操作工/班长/主操/钳工…或后置的师傅/班长）+ 姓名 + 追责性表述」三者同时出现 | 删去姓名，改为岗位或班组的客观事实陈述：「当班操作人员按……执行」「甲班于……完成……」 |

通报是发给一车间人看的。写上「操作工王某某操作不当」，在调查结论出来之前就把人钉在那儿了；就算后来查明不是他的问题，通报也收不回来。**一律写岗位，不写姓名。**

事实陈述里出现姓名不算违规——「已通知钳工班组张师傅到场确认」是在说谁做了处置，不是在追责。脚本要求追责词与姓名同时出现才报，就是为了区分这两种情况。

## 三、替代写法对照表（速查）

| 想表达的意思 | 不要写 | 改写成 |
|---|---|---|
| 说明事件怎么发生的 | 「由于机封失效导致泵内漏」 | 「巡检发现机封处滴漏，其后泵出口压力由 1.8 MPa 降至 1.2 MPa」 |
| 说明是人的问题 | 「操作工操作不当」 | 「当班操作人员于 08:30 执行了 XX 操作，该操作与规程要求的差异待核实」 |
| 说明是设备的问题 | 「设备本身有缺陷」 | 「设备状态待进一步检查确认」 |
| 说明是厂家的问题 | 「系厂家质量问题所致」 | 「部件失效形式待检测鉴定后确认」 |
| 说明后果 | 「造成严重影响」 | 「装置降量运行约 4 小时，影响产量约 XX 吨」 |
| 说明性质 | 「本次事故」 | 「本次设备故障事件」 |
| 说明问题大小 | 「构成重大隐患」 | 「已发现的问题，已按缺陷流程登记，编号 QX-XXXXXXXX-XXX」 |
| 说明还没查清 | 「初步判断是轴承磨损」 | 「原因正在分析中」 |
| 需要提醒别人注意 | 「各岗位吸取事故教训」 | 「建议同类机泵近期加强机封处巡检，重点关注出口压力与电流变化」 |

## 四、与 `incident-flash-report` 的边界

这两个技能都写"事件"，但是两回事，不要混用。

| | `equipment-event-notice`（本技能） | `incident-flash-report`（`skill-pack/【炼化】事故事件快报/`） |
|---|---|---|
| 性质 | **内部情况通报**，信息共享 | **法定事故快报**，向上级与监管部门报送 |
| 依据 | 厂内信息通报惯例 | 法规与厂内事故管理制度，有法定格式与**时限要求** |
| 读者 | 车间 / 分厂 / 公司设备管理部门范围（`--scope` 三档） | 上级单位、监管部门 |
| 时限 | 以厂内规定为准（通常无统一硬性时限） | 以《中国石化设备事故管理规定》与厂内规定的时限为准，**数值以厂内文件为准，技能不判定** |
| 定性 | **不做定性**，不用「事故」一词 | 按事故等级标准填报 |
| 原因 | 一律「原因正在分析中」 | 按快报要求填「初步原因」栏（仍须标注初步） |
| 责任 | 不涉及 | 不涉及（调查报告才涉及） |

**判断顺序**：先判断是否达到需上报的标准——如果达到，**先走 `incident-flash-report`**（时限以厂内规定为准），内部通报可以随后再发。本技能的 `escalationHint` 就是提醒这件事的。是否构成设备事故及其等级，按《中国石化设备事故管理规定》与厂内规定由公司设备管理部门/调查组判定。

### 非计划停工事件（与事故快报分开）

描述中出现 E4（全厂/装置/非计划/紧急/联锁停车、停工）时，脚本另给 `unplannedShutdownHint`：「描述中提到装置停车/停工，可能构成非计划停工事件，请按《炼化企业非计划停工管理规定》与厂内规定判断并另行报送（与事故快报分开），本技能不判定」。非计划停工事件与设备事故是两条报送线，通报里不写「构成非计划停工事件」「X 级非计划停工」这类结论。

### escalationHint 的定位

脚本在描述里检测到下列情形时给出提示，**只提示，不判定**：

| 规则号 | 触发情形 |
|---|---|
| E1 | 人员受伤、烧伤、烫伤、中毒、窒息、骨折、送医、伤亡 |
| E2 | 着火、起火、火灾、明火、过火、爆炸、闪爆、爆燃 |
| E3 | 泄漏外排、进入河沟管网土壤、环保超标、污染 |
| E4 | 全厂/装置/非计划/紧急/联锁停车、停工 |
| E5 | 爆管、爆裂、大量泄漏、喷出、喷溅、物料外泄 |

命中后固定提示：**「请按厂内规定判断是否需走事故快报流程，可使用 incident-flash-report 技能」**，并附一句「是否构成设备事故及其等级按《中国石化设备事故管理规定》与厂内规定判定，报送时限以厂内规定为准」。

脚本不知道厂内的事故分级标准，也不知道这次泄漏到底多少公斤、伤者伤到什么程度。**是否构成需上报事故，由用户按厂内规定判断**，脚本只负责不让这件事被忘掉。反过来，没触发提示也不等于不用上报——检测靠的是关键词，说法换一种就可能漏掉。

## 五、通报七节写法

| 节 | 写什么 | 注意 |
|---|---|---|
| 一、事件概况 | 位号、名称、区域、时间、类型、当前状态 | 时间精确到分；类型用「故障/险肇/异常」，不用「事故」 |
| 二、事件经过 | 按时间顺序陈述现象与处置动作 | 只写观察到的和做过的；带上关键参数数值 |
| 三、影响情况 | 分生产、安全、环保三方面逐项写 | **无影响也要明确写「无」**，不能留空；不能因为没填就当作没影响 |
| 四、已采取措施 | 谁在什么时间做了什么 | 写岗位不写姓名；写完成的，不写打算做的 |
| 五、原因分析情况 | 未确认时固定写「原因正在分析中」 | 见第一节 |
| 六、后续安排 | 什么时间由哪个岗位做什么，怎么验证 | 要有责任岗位、时限、验证方式三要素 |
| 七、举一反三提示 | 同类设备排查范围、需关注的参数与巡检要点 | 只写可执行的检查动作；**不作原因推断、不作责任评价** |

产出 md 不用 emoji，醒目提示一律用「【注意】」。末尾必须保留声明行，一字不改：

> 本通报为情况告知，事件原因与性质以正式调查结论为准

## 六、要素缺失怎么办

缺要素就补，**不要用推测填补**。

脚本把缺失的必需要素列进 `missing`，每项带追问话术。常见的错误处置：

- 影响情况没填 → 写「无影响」。**错**。没填不等于没影响，要问清楚。
- 当前状态没填 → 按「已恢复」写。**错**。设备现在什么状态是能问出来的事实。
- 时间没填 → 按发现时间倒推。**错**。发生时间和发现时间是两件事。
- 已采取措施没填 → 写「正在处理」。**错**。这是在编造处置动作。

一次性把缺的都列给用户，补齐再成文。实在补不齐的，在通报里明确标「待核实」，不要让读者以为这是已确认的信息。
