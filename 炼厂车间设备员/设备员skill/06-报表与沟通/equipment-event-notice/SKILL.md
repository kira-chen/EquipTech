# 设备事件通报起草（equipment-event-notice）

面向中石化体系炼化厂车间（运行部）设备员，起草面向车间 / 分厂 / 公司内部的设备故障、异常与险肇事件情况通报。**只陈述已确认的事实，不做原因定性与责任认定；未经核实的内容一律标注"待核实"。**

## 适用条件
- 用户说"写个设备故障通报 / 起草情况通报 / 发个通知说明这次故障 / 内部通报"，并说明事件情况。
- 适用于内部通报：车间内、分厂（作业部）、公司设备管理部门范围的情况告知、经验分享、举一反三提示。
- 车间设备员可做：事实整理与通报稿起草。**不做**（技能须声明由谁归口）：事故定性与等级认定（按《中国石化设备事故管理规定》由公司设备管理部门/调查组归口）、非计划停工事件的定性与报送（按《炼化企业非计划停工管理规定》，与事故快报分开）、责任认定与处理决定（调查组）、隐患等级认定（安全环保部门）。
- **与 `incident-flash-report` 的区别**：那个是向上级与监管部门报送的事故快报，有规定格式与时限（时限以厂内规定为准）；本技能是内部情况通报。可能构成需上报事故时先走那个技能。
- **与 `failure-investigation-assistant` 的区别**：那个是故障调查材料整理与调查报告框架；本技能只做情况告知，原因一律写"原因正在分析中"。两者的禁用表述规则同源（见 `references/notice-rules.md`）。
- 不适用：法定事故快报；事故调查报告；事故定性、责任认定与处理决定；隐患台账登记。

## 前提条件
- 输入：用户对事件的说明（必需）。可选：设备台账、运行记录、处理过程记录。
- 必填信息：设备位号与名称、事件发生时间、事件经过、当前状态、已采取措施。可选：影响范围、后续安排、通报范围（车间 / 分厂 / 公司，可用 `--scope-name` 给厂内名称）。
- 环境：可执行 Node.js ≥ 18（用于要素完整性校验与表述检测）。**若环境无法执行 node（无 Bash 工具或 `node --version` 失败），明确告知用户并终止，不得基于文字手工成文或自行判定（硬约束 2）。**

## 数据获取（MCP）

平台接入了业务系统 MCP 服务时，按下表调用工具取数，不再请用户上传导出文件；未接入时按操作步骤请用户提供系统导出文件。工具全部只读，不在业务系统里创建或修改任何单据。

| 服务 | 工具 | 参数 | 交给脚本 |
|---|---|---|---|
| 设备资产管理 | `get_notifications` | `open_only=true`；`workshop`：车间名；`tag`：用户说了位号时填 | 填命令行参数（见下） |

取数后：

1. 工具返回的表格内容直接读取即可，不需要保存为文件。
2. `get_notifications`：选一条与用户所说事件对应、状态为 OSNO 或 NOPR（未关闭）的通知单，取位号、设备名称、描述、发现时间作 `--tag`、`--name`、`--desc`、`--time`；发现时间「YYYY-MM-DD HH:mm」改写成「YYYY-MM-DDTHH:mm:00+08:00」。
3. 通知单里的「原因代码」「损坏代码」是登记时的初判，不是调查结论，不得写进 `--cause`；当前状态、影响情况、已采取措施通知单里没有，按操作步骤 1 向用户补问，不要用通知单状态（NOPR 等）代替。
4. 找不到对应的未关闭通知单（如用户说的事刚发生、还没报修建单）时，不要套用别的单据，事件时间与经过按用户口述传参。

## 操作步骤
1. **核对通报要素** —— 按 `references/intake-questions.md` 逐项核对：位号、时间、经过、当前状态、影响（对生产、安全、环保）、已采取措施、后续安排。**要素缺失时一次性列出需补充项；"原因"一项若未经调查确认，一律写"原因正在分析中"，不得填入推测。**
2. **运行脚本** —— 技能目录以平台实际加载路径为准（Windows 路径加双引号）：
   ```bash
   node "<技能目录绝对路径>/scripts/notice.js" --tag "<位号>" --time <ISO 8601 带时区> --desc "<事件经过>" --status "<当前状态>" --impact "<影响情况>" --measures "<已采取措施>" --out "<工作目录>/事件通报"
   ```
   可选：`--scope <车间|分厂|公司>`、`--scope-name "<厂内层级名称，如 烯烃厂设备科>"`、`--type <故障|险肇|异常>`、`--followup "<后续安排>"`、`--name/--workshop/--area`、`--cause "<原因>" --cause-confirmed`（仅原因已由正式调查确认时）、`--hazard-level-confirmed`（仅"重大隐患"已按厂内隐患分级标准确认时，须注明分级依据）。建议始终传 `--out`，否则写到系统临时目录。
   读取末行 JSON 摘要（同时写入 `<out>/summary.json`）：`ok` 必须为 `true`，`ok:false` 时把 `error` 告知用户并终止；`warnings` 非空时逐条告知用户（要素缺失/时间格式异常/描述含推测性表述/上报提示/非计划停工提示等）。脚本用法详见 `scripts/README.md`。
   - **脚本会检测描述中的推测性与定性表述**（如"由于操作不当""因为厂家质量问题""本次事故"），命中时 warning 提示，**模型必须改写为客观事实陈述或标注"待核实"**。
   - 可能需上报事故：脚本给出 `escalationHint` 但不判定，**必须提示用户"请按厂内规定判断是否需走事故快报流程，可使用 incident-flash-report 技能"**；是否构成设备事故及其等级按《中国石化设备事故管理规定》与厂内规定判定。
   - 描述中提到装置停车/停工：脚本另给 `unplannedShutdownHint`，提示可能构成非计划停工事件，按《炼化企业非计划停工管理规定》另行报送（与事故快报分开），技能不判定。
3. **读取 notice.json** —— 从 `<输出目录>/notice.json` 获取：`elements`（通报要素及完整性）、`missing`、`speculative`（检出的推测性表述，含规则号与建议改法）、`hazardLevelKept`、`escalationHint`、`unplannedShutdownHint`、`cause`、`counts`。
4. **起草通报** —— 按 `assets/templates/notice-template.md` 成文，结构为"标题 → 事件概况 → 事件经过 → 影响情况 → 已采取措施 → 原因分析情况（未确认时写正在分析）→ 后续安排 → 举一反三提示"。**措辞客观中性，不出现个人姓名的追责性表述，不使用"事故"一词除非已正式定性并注明文号。**
5. **交付前自检** —— 对照 `references/checklist.md` 逐项检查；通过后交付 `notice.md` 与 `notice.json`。**必须保留声明行："本通报为情况告知，事件原因与性质以正式调查结论为准"，不得删除或改写。**

## 预期结果
- `notice.md`：设备事件通报稿，正文七节（概况、经过、影响、措施、原因分析情况、后续安排、举一反三），附录按需出现：附一缺失要素、附二检出的推测性/定性表述、附二之一按厂内分级确认保留的隐患等语、附三上报流程提示、附四非计划停工事件提示、附数据提示；末尾固定声明行。无 emoji，醒目提示用「【注意】」。
- `notice.json`：要素完整性与检出项；`summary.json`：脚本末行摘要（含 `scope`、`escalationHint`、`unplannedShutdownHint`）。
- 交付时向用户说明：要素完整性、缺失要素、检出的推测性表述、是否提示走上报流程、是否提示非计划停工事件、通报范围。

## 不适用范围
- 不做事故定性、等级认定、原因认定与责任划分。
- 不替代法定事故快报与上报流程；不判定非计划停工事件。
- 不点名批评个人，不使用追责性表述。
- 不在原因未确认时给出原因结论。
