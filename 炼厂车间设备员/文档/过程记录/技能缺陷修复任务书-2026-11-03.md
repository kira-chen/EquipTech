# 技能缺陷修复任务书

日期：2026-11-03
来源：Mock MCP 对接后的 50 个技能全量核验（报告原文：`MCPServer/test/全量核验报告-2026-11-03.md`）
执行方：维护设备员技能的会话

## 一、背景

用阿里云服务器上的 Mock MCP 数据和平台知识库文档，对 50 个技能做了端到端核验：50 个技能都能跑通，关键数字与数据真值一致。核验中发现 17 项技能自身缺陷，都不会让技能报错，但会让个别指标缺失、匹配不准或判为未判定。

核验期间没有修改技能目录。缺陷以 `MCPServer/test/e2e-knowledge.js` 中"已知缺陷：…"开头的检查项固化，当前断言的是缺陷行为。修好后这些检查项会变红，届时把它们改成断言正确行为。

## 二、优先修（演示时用户能直接看到）

| # | 技能 | 位置 | 现象 | 建议修法 |
|---|---|---|---|---|
| 1 | meeting-material-builder | scripts/build.js:86 | 读 `metrics.closeRate`，hazard-closure-tracker 实际输出 `metrics.closureRate`，汇报稿的隐患闭环率始终缺失。examples 和 selftest 用的也是 closeRate，所以测不出来 | 改读 `closureRate`，兼容 `closeRate`；selftest 改用真实 hazard.json 结构 |

| 3 | technical-document-finder | scripts/find.js:203 | 台账的"设备名称"被当作关联线索，A/B 两台泵同名"进料泵"时，查 P-2101B 会把 P-2101A 专属资料（技术协议、检修规程）也带进来 | 设备名称在台账中不唯一时不作线索，或只作排序参考 |

## 四、验收

1. 各技能 selftest 全部通过，全量合计不少于 9407 条。
2. 每修一项，在 selftest 里加一条能复现原缺陷的断言，确保先红后绿。
3. 用 Mock MCP 做端到端回归：在 `MCPServer/` 下运行 `node test/e2e-skills.js`，59 个用例全部通过。e2e-knowledge.js 中对应的"已知缺陷：…"检查项改为断言正确行为。
4. 改动技能的输入列名、输出 JSON 字段时，同步告知 MCP 会话，因为 MCP 工具的输出列和验收用例依赖这些口径。

## 五、注意

- `MCPServer/` 目录不入库（.gitignore），只在本机。
- 改共享库 `scripts/lib/common.js` 要同步到全部 50 个技能，并跑全量回归。

超出任务书的改动：

- meeting-material-builder：超期工单“责任方”改取承修单位（vendor），原来会写成个人姓名。
- repair-plan-assistant：数值冲突只比同一参数，消除了不同参数数值不同被判冲突的误报。
- technical-document-finder：规格型号与名称同样，在台账中不唯一时不作关联线索；修复“内容中出现位号”时 relatedClue 缺失。
- worklog-todo-manager：润滑 owner 原来一直为空，已改读；交接“待明确”占位不再当成位号或人名；待办表“未完成”行原来被误跳过。
- overhaul-process-check-bridge：样例改为依赖技能的真实输出后，selftest 在没有 skill-pack-local 的环境会崩溃。已改为找不到依赖技能时改用已入库的 examples/，跳过 17 条需要依赖技能的断言并在结尾说明（有依赖时 177 条，无依赖时 160 条通过）。

- self-audit-form-filler：备用设备算在用，在用 = 运行 + 备用。
- meeting-material-builder：已闭环（已整改且已验收）的重大隐患不进“存在问题”，改列“主要工作”作为可引用的成果；已整改未验收仍算问题。outline.json 新增 `doneItems`、`counts.done`。
- shift-handover-record、worklog-todo-manager：中文“已删除”与 DLFL 同口径，交接列入待确认并写明已取消，待办表不进待办并 warning。在两个技能内处理，未改共享库。
- worklog-todo-manager：README 改为实际汇集的 7 个上游技能；巡检派工任务单当班执行，不进设备员个人待办。
